# 4.3 — Bedrock Guardrail em Terraform

Aprovação: modo autônomo pedido pelo dono.

## Contexto

O Guardrail `mia-robustness` (prompt attack + PII + tópico negado + palavras de injeção) já existe na conta: foi criado por `scripts/create_guardrail.py` na 2.8a, e o id/versão estão em `config/guardrails.yaml` (`7vx5e8ajtid1`, versão `1`), lidos pelas avaliações do conjunto D. Esta tarefa coloca esse recurso sob o Terraform (TRD, "Infraestrutura": linha Guardrails; "Segurança e LGPD"), sem trocar o id.

## Requisitos

- R1. `infra/guardrail.tf` DEVE declarar `aws_bedrock_guardrail` `mia-robustness` com a mesma política do `guardrail_request()` do script (tópico `fora_da_entrevista`, `PROMPT_ATTACK` HIGH na entrada, 4 palavras, PII ANONYMIZE ×4 e BLOCK ×2, regex `cpf`, mensagens de bloqueio).
- R2. QUANDO o `terraform plan` roda, o guardrail e a versão `1` DEVEM ser IMPORTADOS por blocos `import` cujo id vem de `config/guardrails.yaml` (`yamldecode`), sem criar recurso novo nem mudar a versão publicada.
- R3. O output `guardrail` DEVE expor `{id, version}`, e um teste DEVE garantir que o id/versão importados são os de `config/guardrails.yaml` (a fonte que o código lê).

## Fora de escopo

- Ligar o guardrail ao entrevistador em produção (hoje só as avaliações o passam a `llm.py`): o plano não pede; ver Perguntas.
- Mudar a política (seria versão nova + reavaliação do conjunto D).
- Apagar `scripts/create_guardrail.py` (fica como registro da 2.8a).

## Design

**Arquivos**

| Arquivo | Ação | Conteúdo |
| --- | --- | --- |
| `infra/guardrail.tf` | criar | `locals` com `yamldecode(file("../config/guardrails.yaml"))`, 2 blocos `import`, `aws_bedrock_guardrail`, `aws_bedrock_guardrail_version` |
| `infra/outputs.tf` | alterar | output `guardrail` |
| `tests/test_infra.py` | alterar | R1–R3 comparando com `create_guardrail.guardrail_request()` |

**Decisões**

- Importar (opção recomendada) em vez de criar outro: mantém o id que as avaliações e os resultados da Fase 2 citam e não paga dois guardrails.
- `aws_bedrock_guardrail_version` com `skip_destroy = true`: a versão 1 é referência de experimento e não deve sumir num `destroy`.
- Plan "limpo" = só imports; uma diferença cosmética de formato do provider é aceitável se registrada, mudança de política não.

## Plano de testes

| Caso | Entrada | Esperado |
| --- | --- | --- |
| política igual ao script | `guardrail_request()` × HCL | nome, tópico, 4 palavras, 6 tipos de PII com ação, padrão CPF e mensagem presentes |
| import pela config | HCL | 2 blocos `import` usando `local.guardrail_config.robustness.id`/`.version` |
| proteção | HCL | `skip_destroy = true` na versão |
| real | `terraform plan` | `2 to import, 0 to add, 0 to change, 0 to destroy` (ou mudança in-place só cosmética) |

## Critérios de aceite

- [ ] ID do guardrail lido por config — `terraform -chdir=infra output guardrail` igual a `config/guardrails.yaml`
- [ ] `apply` só importa (nenhuma criação/destruição)
- [ ] `uv run pytest` e `uv run ruff check .` passam

## Notas de implementação

- Passo 1: import do guardrail com id `<id>,DRAFT` e da versão com `<arn>,<versão>`, os dois montados a partir de `config/guardrails.yaml`. A mensagem de bloqueio fica literal (sem `local`), para o teste comparar com o script. O padrão do CPF exige `\` no HCL. `terraform plan` → `2 to import, 0 to add, 2 to change, 0 to destroy`; as 2 mudanças são só a tag `project = mia` (default_tags) no DRAFT e o `skip_destroy`, que fica só no state. A política e a versão 1 não mudam.
