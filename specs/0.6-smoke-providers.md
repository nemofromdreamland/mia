# 0.6 — Smoke test de provedores

## Contexto

A Fase 0 quer descobrir cedo se cada provedor funciona nesta conta antes de escrever o produto (`docs/IMPLEMENTATION_PLAN.md`, Fase 0 e Gate 0; `docs/TRD.md`, "Fase 0: validação e planos B"). Esta tarefa manda o mesmo prompt para os 5 modelos do catálogo (Claude Haiku, Nova Lite e Mistral Large 3 no Bedrock; Gemini Flash; gpt-oss-120b no Groq) pelo mesmo `llm.invoke` da 0.5, e grava uma linha de `RunRecord` por modelo em `runs/` (`docs/TRD.md`, "Observabilidade e custo", camada 1). O resultado alimenta o `docs/adr/0001-gate-0.md` (Bedrock passa se "3 modelos respondem pelo mesmo `init_chat_model`; registro em JSONL").

Também fecha as pendências que a spec 0.5 deixou para cá ("Pendências herdadas pela 0.6"): pacotes de provedor, carga do `.env`, `max_retries` por modelo, confirmação dos ids com chamadas reais, substituto do Gemini 2.5 Flash e fonte oficial do preço do Nova 2 Lite.

Estado atual (`5b2d4d8`): `llm.py` completo para texto, com testes que só usam modelo falso; `config/models.yaml` com os 5 modelos e preços; nenhum pacote de provedor instalado; `scripts/` e `runs/` não existem; `runs/` não está no `.gitignore`.

## Requisitos

- R1. QUANDO uma entrada de `config/models.yaml` tem `max_retries`, O SISTEMA DEVE carregá-lo no `ModelSpec` (inteiro ≥ 0); QUANDO não tem, DEVE usar o padrão 2; QUANDO é negativo ou não inteiro, DEVE levantar `ModelConfigError` citando arquivo e campo.
- R2. QUANDO o modelo levanta exceção e depois responde dentro do limite de `max_retries` novas tentativas, O SISTEMA DEVE devolver o texto e gravar exatamente **um** `RunRecord` de sucesso (`error = null`), com a latência total, incluindo as esperas.
- R3. QUANDO o modelo falha em todas as `1 + max_retries` tentativas, O SISTEMA DEVE gravar exatamente um `RunRecord` com `error` preenchido (última exceção) e relançar essa exceção, como na R7 da 0.5.
- R4. QUANDO `build_chat_model` é chamado com os pacotes de provedor instalados e credenciais falsas no ambiente, O SISTEMA DEVE devolver a classe de chat do provedor certo (`bedrock` → `ChatBedrockConverse`, `gemini` → `ChatGoogleGenerativeAI`, `groq` → `ChatGroq`), sem chamada de rede.
- R5. QUANDO `scripts/smoke_providers.py` roda sem argumentos, O SISTEMA DEVE chamar `llm.invoke` uma vez para cada modelo do catálogo, na ordem do arquivo, com o mesmo `system`/`user`, `prompt_name="smoke"`, `prompt_version=1` e `experiment="smoke-providers"`, gravando em `runs/<AAAA-MM-DD>_smoke-providers.jsonl`.
- R6. QUANDO um modelo falha, O SISTEMA DEVE registrar a falha (o `invoke` já grava o `RunRecord` com `error`), seguir para os próximos modelos e, no fim, sair com código 1; QUANDO todos respondem, sair com código 0.
- R7. QUANDO o script termina, O SISTEMA DEVE imprimir uma tabela com, por modelo: referência, `ok`/`erro`, tokens de entrada e saída, latência (ms), custo (USD) e o início da resposta ou da mensagem de erro; e o caminho do `.jsonl` gravado. Nenhuma chave ou variável de ambiente aparece na saída.
- R8. QUANDO o script recebe `--model <ref>` (uma ou mais vezes), O SISTEMA DEVE rodar só esses modelos; QUANDO a referência não está no catálogo, DEVE sair com código 2 e mensagem clara, antes de chamar qualquer modelo.
- R9. (Pronto quando) QUANDO o smoke test roda de verdade com o `.env` e o perfil AWS `mia`, O SISTEMA DEVE deixar em `runs/` 5 linhas de sucesso, uma por modelo, cada uma com `input_tokens > 0`, `output_tokens > 0`, `latency_ms > 0` e `cost_usd > 0`.

**Decisões**

- **Pacotes de provedor (dependências novas, justificativa):** `langchain-aws` (Bedrock Converse: Claude, Nova, Mistral), `langchain-google-genai` (Gemini) e `langchain-groq` (Groq) são as integrações que o `init_chat_model` carrega para os provedores do TRD ("Stack e decisões"). Só `llm.py` as usa, e só de forma indireta, pelo `init_chat_model`; o teste de arquitetura da 0.5 continua valendo.
- **Retry com `with_retry` do LangChain**, não o `max_retries` de cada pacote: é o mesmo mecanismo para os três provedores (o `ChatBedrockConverse` controla retry por outra configuração, a do boto3) e dá para testar com o modelo falso. Espera exponencial com jitter ("jitter" = um pequeno atraso aleatório para que várias chamadas não tentem de novo no mesmo instante), de 1 s até 20 s, o que cobre o 429 do Groq gratuito (`docs/TRD.md`: "pausa e nova tentativa quando der erro 429"). Os testes trocam `RETRY_WAIT` por `{"initial": 0, "max": 0}` para não dormir.
- **Um `RunRecord` por chamada de `invoke`, não por tentativa:** o registro descreve a chamada que o resto do sistema fez; as tentativas internas não viram linhas. A latência inclui as esperas, porque é o tempo que o usuário sentiria. O `RunRecord` não muda.
- **Retry para qualquer exceção** (padrão do `with_retry`): erro de credencial também é tentado de novo, o que custa alguns segundos no smoke test, mas mantém o código simples. Filtrar só erros temporários fica para quando houver um caso real (ver P5).
- **`max_retries` padrão 2** e `groq:openai/gpt-oss-120b` com 4 (limite de 8 mil tokens/min no plano gratuito).
- **Testes do script sem rede:** `run_smoke` recebe `chat_models` (referência → modelo falso `GenericFakeChatModel`) e repassa ao `invoke`; o `main` é testado com `run_smoke` trocado por um dublê. O teste carrega o script com `importlib` (a pasta `scripts/` não é pacote), sem mexer no `pyproject.toml`. O script não entra na cobertura (a meta de 80% é de `src/mia/`), mas tem testes, porque o passo 3 depende dele.
- **Carga do `.env` com `uv run --env-file .env`**, sem `python-dotenv`: o uv já lê o arquivo e põe as variáveis no ambiente do processo; nenhuma dependência nova, e nenhum código do MIA lê o `.env`. As integrações leem `GOOGLE_API_KEY`, `GROQ_API_KEY`, `AWS_PROFILE` e `AWS_REGION` do ambiente (ver P1).
- **Prompt do smoke test como constante no script** (P2): o carregador de prompts é da 1.2, e este prompt não entra em experimento de qualidade. `prompt_name="smoke"`, `prompt_version=1` no `RunRecord`.
- **Params `{"temperature": 0}` e sem `max_tokens`:** no Gemini 2.5 Flash os tokens de raciocínio contam como saída, e um teto baixo pode cortar a resposta antes do texto. O prompt pede uma frase só, então a saída fica curta.
- **Ids confirmados na prática (passo 3):** se um modelo do Bedrock recusar o id sem prefixo de região em us-east-1 (erro do tipo "on-demand throughput isn't supported"), o agente para, mostra o erro e propõe o id do perfil `us.` com o preço da fonte oficial; só troca no `config/models.yaml` com a sua aprovação. O mesmo vale para preço divergente da fonte oficial.

O teste das classes reais usa credenciais falsas no ambiente e roda sem rede. Avisos `SyntaxWarning` vêm de dentro do pacote `google-genai`, não do MIA. Resultado: `uv run pytest` → **58 passed**, cobertura **100%**; `ruff check` e `ruff format --check` limpos.
- Passo 2: testes vistos falhando antes do script (`FileNotFoundError` ao carregar `scripts/smoke_providers.py`). Como a pasta `scripts/` não é pacote, o teste carrega o arquivo com `importlib` e o registra em `sys.modules` antes de executá-lo (o `@dataclass` procura o módulo lá). Decisões além da spec: (1) `run_smoke` lê o resultado da última linha do `.jsonl`, porque `invoke` só devolve o texto; para não confundir a linha do modelo anterior, conta as linhas antes e depois de cada chamada, e, quando o erro acontece antes de existir `RunRecord` (pacote faltando, por exemplo, já que `build_chat_model` fica fora do `try` do `invoke`), monta o resultado a partir da exceção, com tokens e custo 0 (teste próprio); (2) função pública `make_preview` (texto numa linha só, até 60 caracteres), usada pela tabela e testada à parte; (3) no `__main__`, a saída padrão passa a UTF-8, porque no Windows a saída redirecionada usa cp1252 e quebrava os acentos do `--help`; (4) `BaseChatModel` só é importado para tipagem (`TYPE_CHECKING`), e o script não importa nada de provedor. Prompt fixo e fictício: sistema "Você é um assistente objetivo. Responda em português, em uma única frase." e usuário "O que um recrutador costuma avaliar numa entrevista comportamental?".
