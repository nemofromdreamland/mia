# 1.9 — Grafo de relatório

## Contexto

Depois do encerramento (status `scoring`), um grafo LangGraph transforma os turnos da entrevista no `Report` do candidato e no `CandidateSummary` anônimo do recrutador: garante nota para todo turno respondido → agrega por competência → pontos a melhorar → resumo. Fontes: IMPLEMENTATION_PLAN (1.9), TRD §módulos (linha "grafo de relatório"), APP_FLOW "Fluxo 3", BACKEND_SCHEMA "Validações feitas pelo código" e "Tela do recrutador: regras".

## Requisitos

- R1. QUANDO um turno tem `answer_text` e `score is None`, O SISTEMA DEVE chamar o `Scorer` (1.7/1.8) com a pergunta do plano (`question_id`) e gravar a nota no turno; turnos sem resposta (ex.: encerramento) são ignorados.
- R2. QUANDO o `Scorer` falhar para um turno, O SISTEMA DEVE deixar esse turno sem nota e seguir (ver P1); turno sem nota não entra na agregação.
- R3. QUANDO não houver nenhum turno com nota após R1, O SISTEMA DEVE levantar `ReportError` sem chamar os prompts.
- R4. QUANDO houver turnos com nota, O SISTEMA DEVE calcular por código a nota de cada competência (média das notas dos turnos cujas perguntas têm aquela `competency`, arredondada a 1 casa) e a `overall_score` (ver P2). Competência sem nenhum turno com nota não aparece.
- R5. QUANDO o prompt `report` responder, O SISTEMA DEVE sobrescrever `overall_score` e o `score` de cada `CompetencyScore` com os valores de R4, descartar competências que não estão em R4 e manter só o `summary` redigido pelo LLM; competência de R4 ausente na resposta → `ReportValidationError`.
- R6. QUANDO uma `Improvement` citar um `question_id` que não existe entre os turnos respondidos, O SISTEMA DEVE descartá-la.
- R7. QUANDO o prompt `candidate_summary` responder, O SISTEMA DEVE descartar todo `SummaryPoint` cujo `answer_quote` não exista literalmente (via `checks.quote_in_source`) no texto mascarado de alguma resposta; se `strengths` ou `concerns` ficar vazio, levantar `ReportValidationError` (ver P3).
- R8. QUANDO `headline`, `summary`, `point` ou `next_step_reason` do resumo contiverem dado pessoal (placeholders/padrões do `pii.py`: e-mail, telefone, CPF, URL, `[NOME]`) ou menção a gênero ou idade (lista de padrões, ver P4), O SISTEMA DEVE levantar `ReportValidationError` com a lista de problemas.
- R9. ANTES de chamar qualquer prompt, O SISTEMA DEVE mascarar as respostas com `pii.mask_text`; a transcrição vai entre os delimitadores `<transcricao>` já existentes nos prompts.
- R10. QUANDO tudo passar, `run_report` DEVE devolver `ReportResult` com `report`, `summary` e os `turns` com as notas preenchidas; cada chamada a modelo grava `RunRecord` (já garantido por `llm.py`).
- R11. QUANDO um prompt devolver JSON inválido mesmo após reparo, O SISTEMA DEVE propagar `LLMInvalidOutputError` (como na 1.6).

## Fora de escopo

- Status da sessão (`scoring` → `completed`/`failed`), persistência em DynamoDB/S3, `headline` na `Session` (tarefas de repositório/API).
- Média do caso, `is_above_case_avg`, tela do recrutador (`recruiter.py`).
- CLI (1.10) e avaliação de qualidade dos textos (Fase 2).
- Novas versões dos prompts, salvo se a rodada real exigir (ver P5).

**Interfaces**

```python
# src/mia/report_graph.py
REPORT_PROMPT: Final = ("report", 1)
SUMMARY_PROMPT: Final = ("candidate_summary", 1)

class ReportError(Exception): ...

class ReportValidationError(ReportError):
    problems: list[str]

class ReportResult(BaseModel):
    report: Report
    summary: CandidateSummary
    turns: list[Turn]

class ReportState(TypedDict, total=False):
    plan: InterviewPlan
    turns: list[Turn]
    competency_scores: dict[str, float]
    overall_score: float
    transcript: str            # masked
    report: Report
    summary: CandidateSummary
    problems: list[str]

def ensure_scores(plan: InterviewPlan, turns: list[Turn], scorer: Scorer) -> list[Turn]: ...  # R1, R2
def aggregate_scores(plan: InterviewPlan, turns: list[Turn]) -> tuple[dict[str, float], float]: ...  # R3, R4
def build_transcript(plan: InterviewPlan, turns: list[Turn]) -> str: ...  # R9 (masked)
def apply_report_rules(
    report: Report, competency_scores: dict[str, float], overall: float, answered_ids: set[str]
) -> Report: ...  # R5, R6
def verify_summary(summary: CandidateSummary, answers_masked: list[str]) -> CandidateSummary: ...  # R7
def personal_data_problems(summary: CandidateSummary) -> list[str]: ...  # R8
def build_report_graph(
    *,
    scorer: Scorer,
    model: str | None = None,
    experiment: str | None = None,
    session_id: str | None = None,
    runs_dir: Path = DEFAULT_RUNS_DIR,
    chat_model: BaseChatModel | None = None,
) -> CompiledStateGraph: ...
def run_report(plan: InterviewPlan, turns: list[Turn], **graph_options: Any) -> ReportResult: ...
```

Nós em linha reta: `_ensure_scores` → `_aggregate` → `_report` → `_summary` → `_validate`.

**Decisões**

- **Mesmo padrão da 1.6:** funções puras testáveis sem LLM; nós são closures que compartilham as opções de chamada; `_validate` só junta `problems` e `run_report` decide levantar o erro (o LLM redige, o código decide).
- **Notas são do código:** o LLM só redige `summary`, `strengths` e `improvements`; números vêm de R4.
- **Variáveis dos prompts:** `scores` = JSON com `question_id`, `competency`, `score` por turno; `competencies` = nomes de R4 unidos por `", "`; `overall_score` = valor de R4; `transcript` = pergunta + resposta mascarada por turno.
- **Reuso:** `checks.quote_in_source`, `pii.mask_text` e os placeholders do `pii.py`, `prompts.run_prompt_structured`, `Scorer` de `interviewer.py`. `report_graph.py` importa `judge`/`interviewer`, nunca o contrário.
- **Sem dependências novas** (`langgraph` já está no projeto). Nenhum SDK de provedor.

## Plano de testes

| Caso | Entrada | Esperado |
| --- | --- | --- |
| ensure feliz | 3 turnos respondidos, 1 sem nota | scorer chamado 1 vez, turno passa a ter nota; entrada não mutada |
| ensure ignora | turno de encerramento sem `answer_text` | scorer não chamado |
| ensure falha | scorer levanta exceção | turno fica sem nota, sem erro (P1) |
| agregação | q1(comp A)=4, q2(A)=3, q3(B)=5 | `{A: 3.5, B: 5.0}`, overall conforme P2 |
| sem notas | nenhum turno com nota | `ReportError`, modelo falso não chamado |
| regras do report | LLM diz overall 2.0, A=1, comp extra "C" | overall/A do código, "C" removida |
| competência faltando | LLM omite B | `ReportValidationError` |
| melhoria órfã | `question_id="q9"` | descartada |
| citação falsa | 1 de 2 strengths com quote inexistente | sobra 1 strength |
| todas falsas | concerns todos inventados | `ReportValidationError` |
| PII no resumo | headline com `[EMAIL]` / "ela tem 32 anos" | `ReportValidationError` com 2 problemas |
| máscara | resposta com e-mail e telefone | RunRecords sem os dados, com `[EMAIL]`/`[TELEFONE]` |
| grafo feliz | plano + turnos fixture, modelo falso com `report_ok`/`summary_ok` | `ReportResult` válido, 2 RunRecords (report, candidate_summary) |
| JSON inválido | modelo falso devolve lixo 2× | `LLMInvalidOutputError` |

## Perguntas em aberto

- P1. Se o juiz falhar num turno durante o relatório: ignorar o turno (proposta), tentar de novo 1 vez, ou falhar o relatório inteiro? → resposta: ignorar o turno (recomendado).
- P2. `overall_score` = média das competências (cada competência pesa igual — proposta) ou média de todos os turnos com nota? Follow-ups contam como turno com nota própria (proposta: sim, na competência da pergunta)? → resposta: média das competências, peso igual; follow-up conta como turno com nota própria, na competência da pergunta (recomendado).
- P3. Citações inválidas que esvaziam `strengths`/`concerns`: erro (proposta, cai em `failed`) ou nova tentativa do prompt antes do erro? → resposta: erro direto, sem nova tentativa (recomendado).
- P4. Lista de padrões de gênero/idade para R8 (proposta: `\d+\s*anos`, "idade", "jovem", "idoso", pronomes "ele"/"ela" e "o candidato"/"a candidata"?). Pronomes podem dar falso positivo com "ela" no sentido de coisas; aceita a lista ou prefere só idade + `[NOME]`/PII? → resposta: sem pronomes (falso positivo). Idade: `\d+\s*anos`, "idade", "jovem", "idoso"; gênero explícito: "homem", "mulher", "masculino", "feminino", "a candidata"; mais padrões/placeholders do `pii.py` (recomendado).
- P5. Os prompts `report` v1 (max_tokens 2000) e `candidate_summary` v1 (1200) podem truncar no Gemini como aconteceu na 1.6. Se a rodada real truncar, posso criar v2 só com `max_tokens` maior + changelog, dentro desta tarefa? → resposta: sim, v2 só com `max_tokens` maior + changelog, se a rodada real truncar (recomendado).

## Notas de implementação

- Passo 1: testes vistos falhando (`ModuleNotFoundError: mia.report_graph`). O plano reaproveita `tests/fixtures/prep/plan_ok.json` (sem duplicar); só `tests/fixtures/report/turns.json` foi criado (q1 com nota, q2 sem nota, follow-up de q2, q3 com e-mail/telefone fictícios, encerramento sem resposta). `ensure_scores` usa `interviewer.score_answer` (falha do juiz → `None`, P1) e levanta `ReportError` para `question_id` fora do plano. Médias por competência sem arredondar entram na nota geral; só o resultado final é arredondado a 1 casa. Transcrição: `Pergunta (<id>): <fala>` + `Resposta: <mascarada>` por turno respondido. O parâmetro `plan` de `build_transcript` ficou sem uso (mantido pela assinatura da spec). Suíte: 451 passed, cobertura 99,79%.
- Passo 2: testes vistos falhando (`ImportError: ReportValidationError`). `ReportValidationError(problems)` guarda a lista e junta em `str`. `apply_report_rules` reconstrói as competências na ordem de R4 (nota do código, `summary` do LLM) e descarta melhorias órfãs. `verify_summary` checa a citação contra cada resposta mascarada e acusa `strengths`/`concerns` esvaziados (sem retry, P3). `personal_data_problems` dá 1 problema por campo e categoria (PII via `mask_text(texto) != texto` ou placeholder presente; idade/gênero pela regex de P4, sem pronomes). Suíte: 464 passed, cobertura 99,8%.
- Passo 3: grafo em linha reta (`ensure_scores` → `aggregate` → `report` → `summary` → `validate`), mesmo padrão da 1.6. `apply_report_rules` e `verify_summary` rodam dentro dos nós e já levantam `ReportValidationError`; `_validate` só junta os problemas de dado pessoal e `run_report` levanta. Fixtures `report_ok.json` (overall errado de propósito + melhoria órfã `q9`) e `summary_ok.json`. `scores` do prompt = JSON `question_id/competency/score`. Suíte: 470 passed, cobertura 99,81%.
