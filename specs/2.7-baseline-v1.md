# 2.7 — Baseline v1 no Bedrock (conjuntos A e B)

## Contexto

Primeira rodada de comparação entre modelos com os prompts v1: o juiz (conjunto A, 70 itens) e o `follow_up` (conjunto B, 40 momentos) em três modelos do Bedrock (Claude Haiku, Claude Sonnet **ou** Nova Pro, Mistral Large 3). Os números viram a linha de base do PRD ("Métricas de sucesso": as metas são fixadas depois da baseline) e precisam estar commitados antes de seg 14h (`IMPLEMENTATION_PLAN.md`, Fase 2). Fontes: TRD "Avaliação" (conjuntos A/B, divisão Promptfoo × `metrics.py`), specs 2.4/2.5/2.6.

## Requisitos

- R1. QUANDO o Promptfoo roda o conjunto B, O SISTEMA DEVE chamar `interviewer.should_follow_up` (prompt `follow_up` v1, real) para cada `ToolMomentItem` de `evals/datasets/tools.jsonl`, montando `Question` a partir de `evals/datasets/questions.yaml` pelo `question_id`.
- R2. QUANDO um item de B é executado, O SISTEMA DEVE devolver como saída o `ToolDecision` em JSON e, em `metadata`, `item_id`, `split`, `expected_action` e o modelo usado.
- R3. QUANDO o modelo falha ou a saída não valida em `ToolDecision`, O SISTEMA DEVE devolver `{"error": "Tipo: msg"}` sem derrubar a rodada (como o `run_item` da 2.5).
- R4. QUANDO a assertion de ferramenta avalia um item de B, O SISTEMA DEVE passar só se a `action` final for igual a `expected.action`, aplicando a mesma regra do código (`_wants_follow_up`: `follow_up` sem texto ou sem vaga conta como `next_question`).
- R5. QUANDO `expected.action == "follow_up"` e a ação bateu, O SISTEMA DEVE avaliar o argumento (`follow_up_text` cobre os itens de `follow_up_must_address`) pelo critério definido na pergunta P1; nos demais casos o argumento é "não se aplica".
- R6. QUANDO a configuração da baseline roda, O SISTEMA DEVE executar A e B nos três modelos (um provider por modelo, `label` = id do modelo, `config.model` explícito), com experimentos `baseline_v1_set_a` e `baseline_v1_set_b`, cada chamada gravando `RunRecord` em `runs/`.
- R7. QUANDO um modelo da baseline não está em `config/models.yaml`, O SISTEMA DEVE falhar antes de chamar (já é o comportamento de `llm.resolve_model`); o modelo escolhido (P2) entra no catálogo com preço e fonte.
- R8. QUANDO `metrics.py` recebe um export do conjunto B, O SISTEMA DEVE calcular por modelo × split: n, % ação certa, % argumento certo (sobre os `follow_up` esperados), matriz de confusão esperado × obtido e nº de erros.
- R9. QUANDO a CLI de métricas roda com os exports de A e B e os runs dos dois experimentos, O SISTEMA DEVE gravar `results/baseline_v1.md` com as seções da 2.6 para A, as do R8 para B e custo/latência/JSON válido por modelo × prompt.
- R10. QUANDO a rodada termina, O SISTEMA DEVE ter commitados `runs/*baseline_v1*.jsonl`, os exports `results/baseline_v1_set_{a,b}.json` e `results/baseline_v1.md`.

## Fora de escopo

- Conjuntos C e D (D é a 2.8), Guardrails, prompt v2 (2.9), CI (2.10).
- Gemini e Groq na comparação (6.1); nenhum modelo vira padrão novo: `prompt_models` não muda.
- Editar prompts v1 ou datasets; repetição de 3 execuções do conjunto A (se não for pedida em P4).

CLI: `uv run python evals/metrics.py --export results/baseline_v1_set_a.json --export-b results/baseline_v1_set_b.json --runs runs/2026-11-16_baseline_v1_set_a.jsonl runs/2026-11-16_baseline_v1_set_b.jsonl --experiment baseline_v1` → `results/baseline_v1.md` (filtro de experimento por prefixo, ver Decisões).

**Decisões**

- `build_state` monta um `InterviewState` mínimo só com o que `should_follow_up` lê: `follow_ups_used = max_follow_ups − follow_ups_left`; o `history` do item já vem em texto, então o provider passa um estado sem turnos e injeta o texto pronto. Como `should_follow_up` monta o histórico a partir de `state.turns`, a forma de injetar é a pergunta P3 (não mudar `interviewer.py` sem aprovação).
- `TimeStatus` vem de `minutes_left` do item; nada de relógio real.
- A ação "efetiva" segue `_wants_follow_up` (o LLM sugere, o código decide): mede o comportamento do produto, não só a saída crua. A ação crua também vai no `metadata` para o relatório.
- Um YAML por conjunto (A e B têm testes e assertions diferentes); a config da 2.5 continua igual.
- `load_runs` passa a aceitar o experimento como prefixo (`baseline_v1` casa `baseline_v1_set_a/b`), mantendo o caso exato da 2.6.
- Concorrência baixa (`maxConcurrency: 2`) e `cache: true`, como na 2.5, para não estourar cota do Bedrock. Custo estimado: ~(70+40)×3 = 330 chamadas, poucos centavos a ~US$1 conforme P2.
- Nenhuma dependência nova.

## Perguntas em aberto

- P1. Como julgar o argumento do `follow_up` (R5)? Opções: (a) determinístico — cada item de `must_address` tem ≥1 palavra-chave (sem stopwords, normalizada) no `follow_up_text`; barato, mas frágil a sinônimo; (b) `llm-rubric` do Promptfoo com Claude — mais fiel, mas um LLM julgando outro e custo extra; (c) só registrar o texto e não medir argumento agora. Recomendo (a), com o limite explicado no relatório. → resposta: (a), palavras-chave determinísticas.

## Notas de implementação

- Passo 1: argumento (P1a) = cada item de `follow_up_must_address` divide ≥1 palavra-chave com o `follow_up_text`; palavra-chave = minúscula, sem acento, 4+ letras, fora de uma lista curta de stopwords (pt + en), comparada pelos 5 primeiros caracteres (pega "métrica"/"métricas"; sinônimo não casa). Score = fração dos itens cobertos. `effective_action` replica `_wants_follow_up` usando `follow_ups_left` do item. `assert_tool_args` = "não se aplica" (pass) quando o esperado não é `follow_up` ou a ação efetiva errou (o erro já conta em `assert_tool_action`). 778 testes, cobertura 98,88%; Ruff ok.
- Passo 2: `build_state` ganhou o parâmetro `question` (o `InterviewPlan` exige 4+ perguntas; repete-se a do item) e `load_questions()` lê `questions.yaml`. Histórico em texto vira `Turn`s (P3a); teste confirma que `_history_text` devolve o texto original nos 40 itens. Smoke: 3/3 passaram no Haiku (sem acesso a mais modelos ainda). Atenção no passo 5: `cache: true` do Promptfoo pula a chamada (e o `RunRecord`), então a rodada completa deve usar `--no-cache` para chegar a 330 registros; o arquivo de runs do smoke foi apagado. 788 testes, cobertura 99%; Ruff ok.
- Passo 3: `ToolItem.got_action` é a ação efetiva recalculada no `metrics.py` a partir da saída e do `follow_ups_left` do item (não importa `tool_asserts.py`, que troca de interpretador ao importar). `args_ok`: `None` se o esperado não é `follow_up`; `False` se a ação errou; senão o resultado da assertion `assert_tool_args`. Argumento é medido sobre todos os itens que esperam `follow_up` (erro ou ação errada contam como falha). `load_runs` aceita prefixo terminado em `_` (`baseline_v1` casa `baseline_v1_set_a`, não `baseline_v10`). Cabeçalho do relatório mostra itens de A e B em linhas separadas. 802 testes, cobertura 99%; Ruff ok.
