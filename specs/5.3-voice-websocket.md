# 5.3 — WebSocket da entrevista por voz

## Contexto

O navegador precisa falar um protocolo estável da MIA, sem conhecer os eventos nativos do Sonic. Esta tarefa adiciona o `/ws` exigido pelo AgentCore na porta 8080, valida identidade, sessão e eventos, conecta o fluxo da 5.2 e mantém áudio somente em memória. A documentação oficial confirma que o caminho do WebSocket do AgentCore é sempre `/ws` e que frames acima do limite do serviço fecham a conexão; por isso os chunks da MIA ficam deliberadamente pequenos.

## Requisitos

- R1. QUANDO o app FastAPI é iniciado, O SISTEMA DEVE expor `/ws` no mesmo app e porta 8080 de `/ping` e `/invocations`, compatível com o contrato WebSocket do AgentCore.
- R2. QUANDO uma conexão chega a `/ws`, O SISTEMA DEVE obter `visitor_id` exclusivamente do header `X-Visitor-Id`, validá-lo como UUID v4 e nunca aceitar identidade no corpo de um evento.
- R3. QUANDO o primeiro evento chega, O SISTEMA DEVE exigir `session.start {session_id}` e verificar que a sessão pertence ao visitante, tem modo `voice` e está em `ready` ou `in_progress` antes de abrir o Sonic ou aceitar áudio.
- R4. QUANDO um frame JSON é recebido, O SISTEMA DEVE validá-lo por uma união discriminada de schemas Pydantic e recusar tipo, campo, base64, tamanho ou sequência inválidos sem encaminhá-los ao Sonic.
- R5. QUANDO recebe `audio.chunk`, O SISTEMA DEVE aceitar somente PCM 16 kHz, 16 bits, mono em base64, com quantidade par de bytes e chunk decodificado de no máximo 4096 bytes, mantendo cada frame muito abaixo do menor limite de 32 KB documentado pelo AgentCore.
- R6. QUANDO a MIA termina de falar ou é interrompida pelo candidato, O SISTEMA DEVE iniciar no servidor a janela de resposta da 5.2, emitir o estado com `answer_limit_s` e contar tempo monotônico inclusive enquanto o cliente se declara silenciado.
- R7. QUANDO a janela server-side expira, O SISTEMA DEVE parar de encaminhar áudio do turno, finalizar uma única resposta com a transcrição disponível e emitir `answer.expired`; chunks tardios não podem estender o prazo nem criar outra resposta.
- R8. QUANDO recebe `audio.mute`, O SISTEMA DEVE registrar o estado de mute e parar ou retomar o encaminhamento de áudio sem pausar o limite server-side nem confiar no evento para decidir duração.
- R9. QUANDO recebe `hints.request {turn_no}`, O SISTEMA DEVE devolver `hints {turn_no, items}` somente para o turno atual, usando as dicas determinísticas da 5.2 e sem chamar modelo; pedido para outro turno deve ser recusado.
- R10. QUANDO o Sonic produz áudio, transcrição, interrupção ou mudança de estado, O SISTEMA DEVE traduzi-los respectivamente para `audio.output`, `transcript`, `interrupted` e `state`, sem expor eventos, nomes de ferramentas ou payloads do provedor.
- R11. QUANDO uma transcrição é parcial, O SISTEMA DEVE transmiti-la com `final: false` e não persistir; QUANDO a transcrição final do candidato é aceita, O SISTEMA DEVE entregá-la uma única vez à ferramenta da 5.2 e confirmar a persistência com `turn.saved`.
- R12. QUANDO recebe `session.end`, O SISTEMA DEVE encerrar a entrevista pelo fluxo existente, fechar o Sonic em ordem, emitir `session.ended {status: "scoring"}` e fechar o WebSocket normalmente.
- R13. QUANDO o cliente desconecta sem `session.end`, O SISTEMA DEVE fechar áudio e Sonic sem marcar a entrevista como encerrada, preservando o último turno salvo para uma reconexão ou fallback ao texto.
- R14. QUANDO ocorre erro esperado, O SISTEMA DEVE emitir `error {code, message}` sem credenciais, URL assinada, `visitor_id`, detalhes do provedor ou stack trace; erros de protocolo/política fecham com código 1008, frame grande com 1009 e erro interno com 1011.
- R15. QUANDO há produtor ou consumidor lento, O SISTEMA DEVE usar filas limitadas e encerrar com erro recuperável em vez de acumular áudio sem limite na memória.
- R16. QUANDO o teste offline conecta ao `/ws` com Sonic e ferramentas falsos, O SISTEMA DEVE trocar todos os eventos do Backend Schema, inclusive timer e dicas aprovados, e receber ao menos uma transcrição sem AWS ou dispositivo de áudio.
- R17. QUANDO testado no AgentCore com conta AWS nova, O SISTEMA DEVE aceitar a URL SigV4, preservar o header de visitante vinculado pela 5.5 e trocar áudio/transcrição sem gravar áudio bruto.

**Interfaces**

```python
class ClientVoiceEvent(BaseModel): ...
class ServerVoiceEvent(BaseModel): ...
class VoiceConnectionState(BaseModel): ...

class VoiceSessionFactory(Protocol):
    async def open(
        self, visitor_id: str, session_id: str, send: VoiceEventSender
    ) -> VoiceSession: ...

class VoiceEventSender(Protocol):
    async def __call__(self, event: ServerVoiceEvent) -> None: ...

async def voice_websocket(
    websocket: WebSocket,
    deps: ServiceDeps,
    factory: VoiceSessionFactory,
) -> None: ...

def parse_client_event(raw: str) -> ClientVoiceEvent: ...
def websocket_error(exc: Exception) -> tuple[ServerVoiceEvent, int]: ...
async def exchange(url: str, events: AsyncIterator[ClientVoiceEvent]) -> list[ServerVoiceEvent]: ...
```

**Decisões**

- O endpoint fica no FastAPI existente; a middleware que força HTTP 200 em `/invocations` não se aplica ao upgrade WebSocket.
- O primeiro `session.start` apenas identifica a sessão. A identidade continua vindo do header, conforme regra não negociável; a 5.5 deve assinar/vincular esse header para o navegador não poder trocá-lo.
- Eventos têm envelope `{type, payload}` e `extra="forbid"`. O backend nunca repassa JSON do Sonic diretamente.
- O contrato existente é ampliado na implementação para timer e dicas já aprovados: `state.payload.answer_limit_s`, `hints.request`, `hints` e `answer.expired`.
- Filas de áudio são limitadas por quantidade de chunks; overflow encerra a sessão de transporte, mas não a entrevista persistida.
- O prazo começa quando o backend entra em “ouvindo” após a fala da MIA ou barge-in. Mute e silêncio não pausam o relógio, evitando contorno pelo cliente.
- Desconexão não conclui a entrevista. Só `session.end` ou a máquina de estados da 5.2 inicia scoring.

## Plano de testes

| Caso | Entrada | Esperado |
| --- | --- | --- |
| app | `build_app` | `/ping`, `/invocations` e upgrade `/ws` coexistem |
| header ausente/inválido | conexão sem UUID v4 | política recusada; nenhum Sonic aberto |
| primeiro evento inválido | `audio.chunk` antes de `session.start` | `error invalid_input`, close 1008 |
| sessão alheia | header A + sessão de B | `not_found`, sem revelar existência |
| modo/status inválido | sessão texto ou concluída | `invalid_state`, sem Sonic |
| chunk válido | base64 de PCM par até 4096 bytes | encaminhado uma vez ao Sonic falso |
| chunk inválido | base64 ruim, bytes ímpares ou >4096 | erro e nenhum encaminhamento |
| mute | `true`, chunks, `false` | chunks durante mute ignorados; prazo continua |
| expiração | relógio chega ao limite | áudio bloqueado, resposta entregue uma vez, `answer.expired` emitido |
| dicas atuais | `hints.request` do turno atual | 2–3 itens; zero chamada LLM |
| dicas antigas | outro `turn_no` | erro; nenhuma dica exposta |
| transcrição parcial | `final: false` | enviada ao cliente, repositório intacto |
| transcrição final | candidato + ferramenta falsa | `transcript final`, persistência única e `turn.saved` |
| interrupção | candidato fala sobre áudio de saída | reprodução cancelada e `interrupted` emitido |
| encerramento | `session.end` | fecha Sonic, emite `session.ended`, close 1000 |
| queda | disconnect abrupto | recursos fechados; sessão continua recuperável |
| fila cheia | consumidor falso bloqueado | erro recuperável, memória limitada |
| erro inesperado | factory lança exceção | mensagem genérica, close 1011, log sem segredos |
| script offline | sequência com PCM/transcript falsos | recebe `transcript` e termina com código 0 |
| AgentCore | URL assinada em conta nova | `/ws` conecta e troca eventos; nenhum áudio persistido |

## Critérios de aceite

**Offline (não requer AWS)**

- [ ] Script troca eventos e recebe `transcript` usando `/ws`, Sonic e ferramentas falsos — verificar com: `uv run pytest tests/test_api_ws.py tests/test_voice_ws_client.py -v`
- [ ] Header, dono, modo, status, sequência, PCM/base64, limites e schemas são validados antes do Sonic — verificar com: `uv run pytest tests/test_api_ws.py -v`
- [ ] Timer server-side expira uma vez; mute/chunks tardios não o contornam — verificar com: `uv run pytest tests/test_api_ws.py -v`
- [ ] Áudio parcial/final nunca é persistido; somente transcrição final mascarada vira turno — verificar com: `uv run pytest tests/test_api_ws.py -v`
- [ ] `uv run pytest` passa
- [ ] `uv run ruff check .` passa

**Com AWS — depende de uma conta AWS nova**

- [ ] URL SigV4 conecta ao `/ws` do AgentCore e recebe `transcript` — verificar com o script de protocolo.
- [ ] O header de visitante chega vinculado à conexão e uma sessão alheia continua inacessível.
- [ ] Abertura, primeira fala e fechamento são registrados sem áudio bruto nem segredos.

## Perguntas em aberto

1. Como a 5.5 vincula `X-Visitor-Id` à URL assinada para cumprir a regra de header no navegador? → recomendação: parâmetro de custom header do AgentCore incluído antes da assinatura, que o runtime converte em header para `/ws`; resposta: pendente.
2. Qual timeout para receber `session.start` após o upgrade? → recomendação: 5 s, configurável apenas em testes; resposta: pendente.
3. Deve existir uma única conexão ativa por sessão? → recomendação: sim; rejeitar a segunda com `invalid_state`, liberando o slot no disconnect; resposta: pendente.
4. A ampliação do Backend Schema com `{type, payload}`, timer e dicas está aprovada? → recomendação: sim; manter os nomes existentes e adicionar somente `hints.request`, `hints`, `answer.expired` e `answer_limit_s`; resposta: pendente.
5. O erro WebSocket deve incluir `retryable`, como o envelope HTTP, apesar da tabela atual mostrar só `{code, message}`? → recomendação: sim, para o front decidir reconexão sem inferir pelo texto; resposta: pendente.
