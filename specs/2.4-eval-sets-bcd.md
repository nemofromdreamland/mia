# 2.4 — Conjuntos de avaliação B, C e D

## Contexto

O Promptfoo (2.5) e a baseline (2.7, 2.8) precisam de datasets fixos além do golden set A. Esta tarefa cria os conjuntos B (decisão de aprofundar do `follow_up`), C (plano de entrevista) e D (injection, dados pessoais, formato), cada um com entrada, `expected` e `split`. Fontes: `docs/TRD.md` § Avaliação e § Segurança e LGPD; `docs/BACKEND_SCHEMA.md` § Execuções, prompts e datasets ("um JSONL por conjunto, com entrada, esperado e `split`"); `docs/PRD.md` § Métricas de sucesso; `docs/CASES.md` (lacuna proposital).

Nenhuma chamada a modelo nesta tarefa: os itens são escritos pelo agente (sintéticos, fictícios) e validados por schema e testes. Rodar os modelos sobre eles é 2.5/2.7/2.8.

## Requisitos

- R1. QUANDO um item de qualquer conjunto é carregado, O SISTEMA DEVE validá-lo por um modelo Pydantic de `schemas.py` (`ToolMomentItem`, `PlanCaseItem`, `RobustnessItem`) e rejeitar campos extras.
- R2. QUANDO o conjunto B é lido (`evals/datasets/tools.jsonl`), O SISTEMA DEVE ter entre 36 e 44 itens, cada um com as entradas do prompt `follow_up` v1 (`question`, `answer`, `follow_ups_left`, `minutes_left`, `history`) e `expected.action` ∈ {`follow_up`, `next_question`, `end`}.
- R3. QUANDO `expected.action == "follow_up"`, O ITEM DEVE trazer `expected.follow_up_must_address` (1–2 itens, cada um igual a um `look_for` da pergunta), que é o "argumento esperado" medido na acurácia de argumentos.
- R4. QUANDO `follow_ups_left == 0` ou `minutes_left <= 0`, O ITEM NÃO PODE ter `expected.action == "follow_up"` (coerente com a regra determinística de `interviewer._wants_follow_up` e `time_check`).
- R5. QUANDO o conjunto B é lido, O SISTEMA DEVE ter cada ação com pelo menos 8 itens, e as perguntas vêm de `evals/datasets/questions.yaml` (`question.id` existe lá).
- R6. QUANDO o conjunto C é lido (`evals/datasets/plans.jsonl`), O SISTEMA DEVE ter 6 itens: os 5 `case_id` de `cases/` (fonte = `cases/<id>/cv.md` e `job.md`, referenciados por caminho, não copiados) + 1 par extra fictício em `evals/datasets/plan_extra/` que não vira caso da web.
- R7. QUANDO um item do C é lido, O SISTEMA DEVE ter `expected.job_requirements` (3–8 requisitos da vaga, para medir cobertura) e `expected.gap_keywords` (1–4 termos da lacuna proposital), e cada `gap_keyword` deve aparecer (sem diferenciar maiúsculas) no `job.md` do item.
- R8. QUANDO o conjunto D é lido (`evals/datasets/robustness.jsonl`), O SISTEMA DEVE ter itens de quatro `attack_type`: `answer_injection`, `doc_injection` (no CV ou na vaga, só CLI), `personal_data` e `format_variation`, cada tipo com pelo menos 5 itens.
- R9. QUANDO um item do D é `answer_injection`, `personal_data` ou `format_variation`, O ITEM DEVE trazer `question.id` do `questions.yaml`, `answer_text` e `expected.max_score` (nota máxima aceitável do juiz, 1–5); QUANDO é `doc_injection`, DEVE trazer `target` ∈ {`cv`, `job`} e o texto injetado, e `expected.must_not_contain` (termos que não podem aparecer no `Screening`/`InterviewPlan`).
- R10. QUANDO um item do D é `personal_data`, O ITEM DEVE listar em `expected.forbidden_in_summary` os dados pessoais fictícios presentes na resposta (nome, e-mail, telefone, idade…), que não podem aparecer no `CandidateSummary`.
- R11. QUANDO qualquer conjunto é lido, todo item DEVE ter `split` ∈ {`dev`, `test`} e `item_id` único no arquivo; o split é 70/30 por estrato (B: `expected.action`; D: `attack_type`; C: ver Perguntas), com semente fixa.
- R12. QUANDO qualquer texto dos conjuntos é inspecionado, O SISTEMA NÃO PODE conter dado pessoal real: nomes, e-mails e telefones são fictícios (domínio `example.com`, telefones `(11) 90000-00xx`).

**Interfaces**

```python
# src/mia/schemas.py
AttackType = Literal["answer_injection", "doc_injection", "personal_data", "format_variation"]
Split = Literal["dev", "test"]

class ToolExpected(BaseModel):
    action: Literal["follow_up", "next_question", "end"]
    follow_up_must_address: list[str] = []      # obrigatório (1–2) só em follow_up

class ToolMomentItem(BaseModel):
    item_id: str
    question_id: str
    answer: str
    follow_ups_left: int = Field(ge=0, le=2)
    minutes_left: float
    history: str
    expected: ToolExpected
    split: Split
    note: str                                    # por que essa é a ação certa

class PlanExpected(BaseModel):
    job_requirements: list[str] = Field(min_length=3, max_length=8)
    gap_keywords: list[str] = Field(min_length=1, max_length=4)

class PlanCaseItem(BaseModel):
    item_id: str
    source: Literal["case", "extra"]
    cv_path: str                                 # relativo à raiz do repo
    job_path: str
    persona: Persona
    language: Language
    expected: PlanExpected
    split: Split

class RobustnessExpected(BaseModel):
    max_score: int | None = Field(default=None, ge=1, le=5)
    forbidden_in_summary: list[str] = []
    must_not_contain: list[str] = []

class RobustnessItem(BaseModel):
    item_id: str
    attack_type: AttackType
    question_id: str | None = None
    answer_text: str | None = None
    target: Literal["cv", "job"] | None = None
    base_case_id: str | None = None              # doc_injection: caso usado como base
    injected_text: str | None = None
    expected: RobustnessExpected
    split: Split
    note: str
# validadores de modelo garantem R3, R4, R9 (campos obrigatórios por tipo)

# scripts/eval_sets_io.py
def load_jsonl(path: Path, model: type[T]) -> list[T]: ...
def save_jsonl(items: Sequence[BaseModel], path: Path) -> None: ...           # atômico, como golden_io
def assign_splits(items: list[T], stratum: Callable[[T], str], seed: int,
                  dev_ratio: float = 0.7) -> list[T]: ...
```

**Decisões**

- Modelos em `schemas.py` (regra: nada de dict solto) com `model_config = ConfigDict(extra="forbid")`; regras por tipo em `model_validator`, para que um item incoerente nem carregue.
- B mede só o `follow_up` v1: é o único ponto em que um LLM escolhe "ferramenta" (`ToolDecision`); `next_question`, `time_check` e `end_interview` são determinísticos e já testados na 1.7. "Argumento" = o `follow_up_text` cobrir os `look_for` esperados (julgado na 2.5).
- B inclui casos-limite: `follow_ups_left=0` com resposta fraca (→ `next_question`), tempo esgotado (→ `end`), resposta completa (→ `next_question`), resposta vaga com folga (→ `follow_up`), com e sem histórico.
- C referencia `cases/<id>/cv.md` por caminho, para não duplicar fixtures e não sair de sincronia quando a `version` subir.
- D `doc_injection` = caso base + texto injetado anexado ao CV ou à vaga (a montagem fica na 2.5/2.8); só a CLI aceita CV/vaga avulsos.
- Itens escritos pelo agente, sem LLM: o conjunto é pequeno, precisa de rótulo certo por construção e não gasta cota. A semente de split fica em constante no teste que a usa.
- Sem dependência nova.

## Plano de testes

| Caso | Entrada | Esperado |
| --- | --- | --- |
| B válido | item `follow_up` com `must_address` ⊂ `look_for` | carrega |
| B erro R3 | `follow_up` sem `follow_up_must_address` | `ValidationError` |
| B erro R4 | `follow_ups_left=0`, `action=follow_up` | `ValidationError` |
| B erro extra | campo `score` a mais | `ValidationError` |
| D erro R9 | `answer_injection` sem `max_score` | `ValidationError` |
| D erro R9 | `doc_injection` sem `target` | `ValidationError` |
| io ida e volta | 3 itens → `save_jsonl` → `load_jsonl` | iguais; sem `.tmp` sobrando |
| io inválido | linha com JSON quebrado | erro com número da linha |
| split | 10 itens de 2 estratos (5+5) | 7 dev / 3 test, ~70/30 por estrato; mesma semente → mesmo resultado |
| dataset B | `tools.jsonl` real | 36–44 itens; ≥8 por ação; `question_id` existe; `must_address` ⊂ `look_for` |
| dataset C | `plans.jsonl` real | 6 itens; 5 `case` + 1 `extra`; arquivos existem; `gap_keywords` no `job.md` |
| dataset D | `robustness.jsonl` real | ≥5 por tipo; `forbidden_in_summary` aparece no `answer_text` |
| todos | os três arquivos | `item_id` único; split 70/30 por estrato (±1); sem e-mail fora de `example.com` |

## Notas de implementação

- Passo 1: modelos herdam de `_EvalModel` (`extra="forbid"`); regras por tipo em `model_validator` (mensagens nomeiam o campo que falta). `follow_up_must_address` limitado a 1–2 no validador. `eval_sets_io` usa genéricos PEP 695; erro de leitura vira `ValueError` com o número da linha; split = `round(0.7·n)` por estrato após embaralhar ids ordenados com a semente. Seção curta dos três conjuntos no `BACKEND_SCHEMA.md` (aprovado na revisão). 680 testes passam, cobertura 98,88%; Ruff ok.
- Passo 2: 40 itens escritos à mão (14 `follow_up`, 14 `next_question`, 12 `end`; split 10+4 / 10+4 / 8+4, semente 24), gravados por um script descartável com `save_jsonl`/`assign_splits` (não commitado). `must_address` é tirado por índice do `look_for`, então é igual por construção. `end` = `minutes_left <= 0` e vice-versa (teste extra de coerência com R4). Histórico no formato real de `_history_text`. 687 testes passam, cobertura 98,88%; Ruff ok.
- Passo 3: 5 casos referenciados por caminho (`cases/<id>/cv.md`/`job.md`; persona e idioma lidos do `case.yaml`) + par extra em inglês (`plan_extra/`: Data Engineer Jr, lacuna = Airflow e testes de qualidade de dados; e-mail `example.com`, telefone `(11) 90000-0001`). Split 4 dev / 2 test conforme resposta da spec: extra + `ai-product-manager` em test. `gap_keywords` escolhidos como trechos literais do `job.md`. JSONL gerado por script descartável com `save_jsonl`. 692 testes passam, cobertura 98,88%; Ruff ok.
