# 0.7 — AgentCore: exemplo oficial de WebSocket (echo)

## Contexto

A Fase 0 precisa descobrir, antes de escrever o produto, se o Bedrock AgentCore Runtime funciona nesta conta (Free Plan) com WebSocket, que é o transporte da voz (`docs/IMPLEMENTATION_PLAN.md`, tarefa 0.7 e Gate 0; `docs/TRD.md`, "Fase 0: validação e planos B" e "Stack e decisões", linha Execução). O teste passa se "o deploy funciona e responde do navegador" (ou de um script); se falhar, entra o plano B do TRD: Lambda + API Gateway para o modo texto e voz só local. O resultado vai para o `docs/adr/0001-gate-0.md` (Gate 0, fora desta tarefa).

Pela arquitetura (`docs/TRD.md`, "Arquitetura"; `docs/BACKEND_SCHEMA.md`, "WebSocket (modo voz)"), o navegador vai abrir o WebSocket do AgentCore com uma URL assinada por SigV4 e válida por 5 minutos. Por isso o cliente de teste já usa esse mesmo mecanismo: gera a URL assinada com o perfil `mia` e conecta nela.

Estado atual (`1381748`): fase 0.6 concluída; não existe `infra/`, `proxy/` nem nada de AgentCore no repositório. Tarefa marcada "Você + agente": o deploy e a remoção na AWS são feitos/confirmados pelo usuário.

## Requisitos

- R1. QUANDO o servidor echo recebe um JSON `{"inputText": <texto>}` no WebSocket (`/ws`, porta 8080), O SISTEMA DEVE devolver `{"echo": {"inputText": <texto>}}` na mesma conexão (código da página oficial).
- R2. QUANDO o servidor echo recebe `GET /ping`, O SISTEMA DEVE responder 200 (contrato do AgentCore Runtime, `docs/BACKEND_SCHEMA.md`, "API").
- R3. QUANDO `scripts/agentcore_echo_client.py` recebe o ARN do runtime e o perfil/região, O SISTEMA DEVE gerar uma URL `wss://` assinada com SigV4 (validade de 300 s), sem imprimir credenciais nem a assinatura completa.
- R4. QUANDO o cliente conecta e envia uma mensagem, O SISTEMA DEVE imprimir a mensagem enviada, a recebida, se são iguais e a latência de ida e volta em ms; e sair com código 0 se o eco bate, 1 se não bate ou se a conexão falha (com a mensagem de erro, sem credenciais).
- R5. QUANDO o ARN não é informado ou é malformado, O SISTEMA DEVE sair com código 2 e mensagem clara, antes de qualquer chamada de rede.
- R6. (Pronto quando) QUANDO o exemplo está implantado no AgentCore em us-east-1, O SISTEMA DEVE fazer o cliente receber o eco de verdade (saída colada nas Notas de implementação).
- R7. (Pronto quando) QUANDO o teste termina (passando ou não), o runtime de teste e os recursos criados para ele (ECR, role, endpoint) DEVEM ser apagados, com evidência de que não existem mais (comando de listagem colado nas Notas).

## Design

**Arquivos** (local exato depende da P1)

| Arquivo | Ação | Conteúdo |
| --- | --- | --- |
| `experiments/0.7-agentcore-echo/main.py` | criar | servidor echo copiado da página oficial da AWS |
| `experiments/0.7-agentcore-echo/README.md` | criar | origem (link), como rodar local, deploy e remoção |
| `scripts/agentcore_echo_client.py` | criar | cliente: monta URL assinada, conecta, envia, compara, mede latência |
| `tests/test_agentcore_echo_client.py` | criar | testes offline (assinatura com credenciais falsas, validação de ARN, códigos de saída com WebSocket falso) |
| `pyproject.toml` / `uv.lock` | alterar | `bedrock-agentcore` no grupo `dev` (ver P3) |

**Interfaces** (rascunho; nomes finais dependem do exemplo oficial)

```python
def parse_runtime_arn(arn: str) -> str: ...            # valida e devolve o ARN; ValueError se malformado
def build_signed_ws_url(arn: str, region: str, session: boto3.Session, expires_s: int = 300) -> str: ...  # usa AgentCoreRuntimeClient.generate_presigned_url
async def echo_once(url: str, message: str, connect: Connect = websockets.connect) -> EchoResult: ...  # connect injetável nos testes
def main(argv: list[str] | None = None) -> int: ...     # 0 eco ok, 1 falha, 2 argumento inválido

class EchoResult(BaseModel):   # local ao script; não entra em schemas.py (não é saída de LLM)
    sent: str
    received: str | None
    matched: bool
    latency_ms: int
    error: str | None = None
```

**Decisões**

- Script em vez de navegador: o critério permite, é testável offline e reaproveita o perfil `mia`.
- O cliente assina a URL do mesmo jeito que a futura Lambda `voice-url` fará; se funcionar aqui, o caminho da voz está validado.
- Nenhum `RunRecord`: não há chamada a modelo.
- Deploy e destroy são executados só com confirmação explícita do usuário, mostrando antes o que será criado/apagado (`AGENTS.md`, Segurança).

## Plano de testes

| Caso | Entrada | Esperado |
| --- | --- | --- |
| ARN válido | `arn:aws:bedrock-agentcore:us-east-1:123456789012:runtime/echo-abc` | devolvido sem erro |
| ARN malformado | `"foo"` / vazio | `main` sai 2, mensagem clara, nenhuma rede |
| URL assinada | ARN válido, credenciais falsas via env | começa com `wss://`, contém `X-Amz-Signature` e `X-Amz-Expires=300`; saída não contém a secret key |
| eco ok | WebSocket falso que devolve a mensagem | `matched=True`, `main` sai 0 |
| eco diferente | WebSocket falso que devolve outra coisa | `matched=False`, sai 1 |
| conexão falha | WebSocket falso que levanta exceção | `error` preenchido sem credenciais, sai 1 |
| real (manual) | runtime implantado | eco recebido, latência impressa (R6) |

## Notas de implementação

- Passo 1: o servidor é o echo da página oficial da AWS (o repositório de samples não tem pasta de echo separada). A URL assinada usa `AgentCoreRuntimeClient.generate_presigned_url` do SDK oficial (`bedrock-agentcore` 1.26.0, grupo `dev`, que já traz `websockets` e `boto3`) em vez de SigV4 feito à mão; o SDK limita a validade a 300 s. `connect` e `session` são injetáveis para testar sem rede. Mensagens de erro passam por `redact`, que troca os valores `X-Amz-*=` por `***`. O teste do servidor local fica com o usuário (`main.py` + cliente apontando para `ws://localhost:8080/ws`).
- Passo 2: deploy com a CLI oficial `@aws/agentcore` 1.0.3 (`npx`), template `agent-python-minimal` (build `CodeZip`, Python 3.14, sem ECR/CodeBuild no runtime), com o `main.py` do echo no lugar do `main.py` do template. O projeto gerado ficou fora do repositório, em `C:\mia-tmp\MiaEcho07`, porque o caminho do scratchpad passava do limite de 260 caracteres do Windows. A CLI precisa de um uv mais novo que o 0.6.16 local; usei o uv 0.13.8 via `uvx`, só no PATH do comando, sem mudar a instalação. A telemetria da CLI foi desativada (com aprovação). O deploy criou as stacks `CDKToolkit` (bootstrap) e `AgentCore-MiaEcho07-default` e **ativou o CloudWatch Transaction Search na conta** (não estava previsto; reverter no passo 3). Evidência (R6), duas execuções:

```
$ uv run python scripts/agentcore_echo_client.py --arn arn:aws:bedrock-agentcore:us-east-1:<conta>:runtime/MiaEcho07_default_agent-H9t8VpGlOf --profile mia --region us-east-1
sent:     Olá, AgentCore! Teste de eco da tarefa 0.7.
received: Olá, AgentCore! Teste de eco da tarefa 0.7.
matched: True
latency_ms: 6503        (2ª execução: 6458)
```

  A latência inclui o handshake e a criação de uma sessão nova (micro‑VM) a cada execução. Ela não mede a latência entre mensagens numa sessão já aberta; isso fica para o Gate 0/voz.
- Passo 3 (remoção, com aprovação): `agentcore remove all --yes` + `agentcore deploy --yes` apagou a stack do runtime. A `CDKToolkit` foi apagada com `aws cloudformation delete-stack`. O bucket de assets tem `DeletionPolicy: Retain` e ficou para trás: esvaziado (2 versões) e apagado à mão. A chave KMS do bootstrap não pode ser apagada na hora; o CloudFormation a agendou para 30 dias e eu reduzi para o mínimo de 7 (exclusão em 2026-11-22). Transaction Search revertido: destino dos rastros de volta para `XRay` e resource policy `TransactionSearchXRayAccess` apagada. Os 3 log groups criados pelo deploy (runtime, `aws/spans`, `/aws/application-signals/data`) foram apagados. Evidência (R7):

```
--- runtimes            {"agentRuntimes": []}
--- stacks ativas       []
--- buckets cdk         []
--- ecr                 []
--- roles cdk/agentcore []
--- ssm                 InvalidParameters: ["/cdk-bootstrap/hnb659fds/version"]   (não existe)
--- kms                 PendingDeletion 2026-11-22
--- xray                XRay PENDING   (voltando do CloudWatchLogs)
--- log policies        []
--- log groups          []
```

  Para o Gate 0/Fase 4: o deploy pela CLI mexe em configurações da conta (Transaction Search) e cria uma chave KMS (custo mensal enquanto existir). No Terraform da Fase 4 vale decidir isso de forma explícita.
