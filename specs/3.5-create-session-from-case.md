# 3.5 — create_session a partir de um caso

## Contexto

Na web, a sessão nasce de um dos 5 casos prontos: triagem e plano vêm do fixture, sem chamar modelo, e o candidato recebe um número anônimo sequencial por caso (`docs/APP_FLOW.md` passo 4; `docs/BACKEND_SCHEMA.md` §estados, `mia-meta`, regras de `create_session`).
O comportamento principal **já existe**: `service.create_session` (3.1) carrega o caso, passa pelo portão de cotas (3.4), numera com `CandidateCounter` (memória e `DynamoCandidateCounter`) e grava a sessão em `ready`; a API responde 201 (3.2). Esta tarefa fecha o "Pronto quando" com prova forte: **nenhuma** chamada a `llm.py` em todo o caminho HTTP e `candidate_no` sem repetição, também no DynamoDB e entre casos/visitantes.

## Requisitos

- R1. QUANDO `POST /sessions {case_id, mode}` é chamado com caso válido e cota livre, O SISTEMA DEVE responder 201 com `Session` em `ready`, com `case_id`, `case_version`, `persona`, `language`, `job_title` e `fit_score` iguais aos do fixture do caso.
- R2. QUANDO uma sessão é criada (REST ou `/invocations`), O SISTEMA DEVE fazer 0 chamadas a `llm.py` (nenhuma função de chamada a modelo invocada e nenhum `RunRecord` gravado).
- R3. QUANDO N sessões são criadas no mesmo caso, por visitantes iguais ou diferentes, O SISTEMA DEVE atribuir `candidate_no` = 1..N, sem repetição e sem lacunas.
- R4. QUANDO sessões são criadas em casos diferentes, O SISTEMA DEVE numerar cada caso de forma independente (cada um começa em 1).
- R5. QUANDO o contador é o `DynamoCandidateCounter` e várias criações ocorrem em paralelo (threads) no mesmo caso, O SISTEMA DEVE devolver números todos distintos.
- R6. QUANDO a criação é recusada (caso inexistente, demo pausada ou cota), O SISTEMA DEVE não avançar o contador nem gravar sessão (já coberto na 3.1/3.4; aqui só reconfirmado no teste de R3).
- R7. QUANDO a sessão criada é lida com `get_session` em `ready`, O SISTEMA DEVE devolver a triagem do caso (`SessionView.screening`), sem expor o plano.

## Fora de escopo

- Mudar o contrato da API, os schemas ou o portão de cotas.
- Fixar o plano pela `case_version` (ver P1): sem aprovação, `_load_plan` continua lendo o fixture atual.
- Frontend (3.6), voz, relatório.

## Design

**Arquivos**

| Arquivo | Ação | Conteúdo |
| --- | --- | --- |
| `tests/test_create_session_case.py` | criar | R1–R4, R6, R7 via `TestClient` com deps em memória e `llm.py` vigiado |
| `tests/test_repo_dynamo.py` | alterar | R5: concorrência no `DynamoCandidateCounter` (moto) |
| `src/mia/service.py` | alterar só se um teste falhar | nenhuma mudança prevista |

**Interfaces** (só apoio de teste; nada novo em produção)

```python
# tests/test_create_session_case.py
@pytest.fixture
def no_llm(monkeypatch: pytest.MonkeyPatch) -> list[str]: ...
    # troca as funções públicas de mia.llm que chamam modelo por stubs que
    # registram o nome e falham; o teste confere que a lista ficou vazia
def _create(client: TestClient, visitor_id: str, case_id: str) -> dict[str, Any]: ...
```

**Decisões**

- Vigiar `mia.llm` diretamente (não só os fakes `writer`/`report` do `make_deps`): é a regra de arquitetura "único lugar que chama modelo", então zero chamadas ali prova R2 de verdade. Também conferir que `runs/` não ganhou linhas (diretório temporário via `monkeypatch`, se `llm.py` permitir; senão só a lista de chamadas).
- R5 usa `ThreadPoolExecutor` com 10–20 chamadas sobre o moto; o `UpdateItem ADD` atômico já existe, o teste só prova.
- Tamanho P: é tarefa de verificação com testes; se algum teste falhar, a correção entra no mesmo passo.
- Sem dependências novas.
