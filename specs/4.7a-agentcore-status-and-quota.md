# 4.7a — /invocations sempre 200 + limite por visitante configurável

Aprovação: modo autônomo pedido pelo dono; o aumento do limite foi pedido pelo dono ("aumente o limite de sessões").

## Contexto

No primeiro uso real (preparação da 4.7), criar sessão falhou: o container respondeu `201` ao `/invocations`, e o AgentCore trata qualquer status diferente de 200 como erro, então o `invoke_agent_runtime` levantou exceção e a proxy devolveu `500 internal`. Reproduzido com `GET /sessions/<inexistente>` (container 404 → proxy 500) e `GET /sessions` (container 200 → proxy 200). A proxy (3.11, R6) já deriva o status HTTP do código de erro no corpo e da action, então basta o container responder 200 com o mesmo corpo. O visitante gastou as 5 sessões do dia com essas falhas; o dono pediu limite maior.

## Requisitos

- R1. QUANDO o app é montado por `build_app` (o ponto de entrada do container), toda resposta de `POST /invocations` DEVE ter status 200 com o mesmo corpo e content-type que teria (inclusive erros de serviço, validação e erro inesperado); corpo vazio (`delete_session`) continua vazio.
- R2. `create_app` (REST e testes da 3.2) NÃO muda: mesmo status nas duas entradas.
- R3. O limite diário por visitante DEVE vir de `MIA_VISITOR_DAILY_LIMIT` (inteiro ≥ 1) no modo `aws`; ausente → 5 (PRD); valor inválido → erro na inicialização (`ValueError`).
- R4. O Terraform DEVE passar `MIA_VISITOR_DAILY_LIMIT = var.visitor_daily_limit` ao runtime, com padrão 20 (pedido do dono). O limite global (100) não muda.

## Fora de escopo

- Zerar as cotas já gastas hoje (o novo limite já libera); levar `RunRecord` ao CloudWatch (decisão A/B pendente com o dono).
- Mudar a proxy.

## Design

**Arquivos**

| Arquivo | Ação | Conteúdo |
| --- | --- | --- |
| `src/mia/api/main.py` | alterar | middleware que reescreve o status do `/invocations` para 200; limite lido do env |
| `tests/test_api_main.py` | alterar | R1, R3 |
| `infra/agentcore.tf`, `infra/variables.tf` | alterar | env e variável `visitor_daily_limit` |
| `tests/test_infra.py` | alterar | R4 |

**Interfaces**

```python
def visitor_limit(env: Mapping[str, str]) -> int: ...
async def invocations_always_200(request: Request, call_next: Callable[..., Awaitable[Response]]) -> Response: ...
```

**Decisões**

- Normalizar no container (não na proxy): a exceção do boto3 não traz o corpo da resposta.
- Só em `build_app`: a regra é do contrato do AgentCore, não da API; a paridade REST × `/invocations` da 3.2 continua testada em `create_app`.
- Limite por env (não constante nova): o padrão do PRD continua no código; o dono ajusta sem rebuild.

## Plano de testes

| Caso | Entrada | Esperado |
| --- | --- | --- |
| criar | `build_app` (memory) + `create_session` | 200, corpo `Session` |
| erro de serviço | `get_session` inexistente | 200, corpo `{"error": {"code": "not_found", …}}` |
| validação | action desconhecida | 200, `invalid_input` |
| apagar | `delete_session` | 200, corpo vazio |
| REST intacto | `build_app` + `POST /sessions` | 201 |
| limite | env `MIA_VISITOR_DAILY_LIMIT=2` | 3ª sessão → `quota_exceeded` |
| limite inválido (erro) | `"0"`, `"abc"` | `ValueError` |
| terraform | HCL | `MIA_VISITOR_DAILY_LIMIT = tostring(var.visitor_daily_limit)`, padrão 20 |
