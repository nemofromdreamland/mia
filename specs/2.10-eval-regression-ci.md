# 2.10 — Conjunto A no CI com respostas gravadas

## Contexto

O TRD ("Avaliação": "O conjunto A roda no CI como teste de regressão"; "CI/CD": "Pull request: lint, testes, conjunto A em modo rápido com respostas gravadas") pede que o golden set do juiz rode a cada PR sem chamar modelo. As respostas brutas do Haiku já existem nos `RunRecord`s da rodada final da 2.9 (`runs/2026-11-16_judge_v1_vs_v2.jsonl`). Esta tarefa grava essas respostas num fixture versionado (`results/*.json` está no `.gitignore`) e reexecuta o código real do juiz (`judge_answer` → parse/validação → `verify_score`) sobre elas, para pegar regressões no código que decide (schema, citações literais, métricas), não no modelo.

## Requisitos

- R1. QUANDO o script de gravação roda sobre um arquivo de `runs/` com `experiment` e `prompt_version` dados, O SISTEMA DEVE gravar `tests/fixtures/judge_cassette_set_a.jsonl` com uma linha por item do `judge_golden.jsonl` (70), contendo `item_id`, `prompt_version` e a lista ordenada de `output_raw` daquela chamada, sem chamar nenhum modelo.
- R2. QUANDO um item do golden não tem `RunRecord` correspondente (casado por `question` + `answer` mascarado) ou tem mais de um, O SISTEMA DEVE sair com código 1, listar os `item_id`s problemáticos e não gravar o fixture.
- R3. QUANDO `uv run pytest tests/test_eval_regression.py` roda, O SISTEMA DEVE passar cada item por `judge_answer` com um modelo falso que devolve as respostas gravadas (sem rede, sem `.env`, `runs_dir` temporário), e aplicar as três assertions do conjunto A (`assert_schema`, `assert_quotes_verified`, `assert_score_within_one`).
- R4. QUANDO o teste de regressão roda, O SISTEMA DEVE falhar se algum item deixar de produzir `AnswerScore` válido, ou se kappa ponderado, % ±1 ou % de citações verificadas (calculados com `evals/metrics.py`) ficarem abaixo dos valores de referência gravados no fixture, com tolerância 0.
- R5. QUANDO o fixture tem item que não existe mais no golden (ou falta item), O SISTEMA DEVE falhar com mensagem dizendo para regravar o fixture.
- R6. QUANDO um PR ou push para `main` chega ao GitHub, O SISTEMA DEVE rodar um workflow do GitHub Actions com `uv sync`, `uv run ruff check .` e `uv run pytest`, sem segredos da AWS/Groq.
- R7. QUANDO o workflow roda, O SISTEMA DEVE executar `tests/test_eval_regression.py` em menos de 60 s (medido com `--durations`).

## Fora de escopo

- Chamar modelo no CI ou guardar chaves como segredo do GitHub.
- Conjuntos B, C e D no CI.
- `terraform plan` no CI (entra com a infra, Fase 4).
- Trocar a versão do juiz usada pelo produto (`JUDGE_PROMPT`).
- Detectar regressão de qualidade do **modelo** (respostas são fixas por definição).

## Design

**Arquivos**

| Arquivo | Ação | Conteúdo |
| --- | --- | --- |
| `scripts/record_judge_cassette.py` | criar | lê `runs/*.jsonl` + golden, casa registros com itens, grava o fixture com as métricas de referência |
| `tests/fixtures/judge_cassette_set_a.jsonl` | criar (gerado) | 1ª linha: cabeçalho com `prompt_version`, `source_run`, métricas de referência; depois 70 linhas de item |
| `tests/test_record_judge_cassette.py` | criar | testes do script com runs pequenos em `tmp_path` |
| `tests/test_eval_regression.py` | criar | replay do conjunto A + checagem de métricas |
| `.github/workflows/ci.yml` | criar | job único: checkout, `astral-sh/setup-uv`, Python 3.12, `uv sync`, ruff, pytest com `--durations=10` |

**Interfaces**

```python
# scripts/record_judge_cassette.py
class CassetteItem(BaseModel):
    item_id: str
    prompt_version: int
    outputs: list[str]          # output_raw na ordem (1 = sem reparo; 2 = houve repair)

class CassetteHeader(BaseModel):
    prompt_version: int
    source_run: str              # nome do arquivo em runs/
    model: str
    kappa: float | None
    within_one_pct: float | None
    quotes_verified_pct: float | None

def match_records(items: Sequence[GoldenItem], records: Sequence[RunRecord]) -> dict[str, list[RunRecord]]: ...
def build_cassette(items: Sequence[GoldenItem], matched: dict[str, list[RunRecord]], *, prompt_version: int, source_run: str) -> tuple[CassetteHeader, list[CassetteItem]]: ...
def main(argv: Sequence[str] | None = None) -> int: ...
#   --runs <arquivo> --experiment judge_v1_vs_v2 --prompt-version <N> [--out <arquivo>]

# tests/test_eval_regression.py
def load_cassette(path: Path) -> tuple[CassetteHeader, list[CassetteItem]]: ...
def replay_item(item: GoldenItem, recorded: CassetteItem, runs_dir: Path) -> AnswerScore: ...
```

**Decisões**

- Replay com `GenericFakeChatModel` passado em `chat_model=` (mesma injeção que o provider e os testes já usam): exercita `run_prompt_structured`, reparo de JSON, `verify_score` e o `RunRecord`, sem tocar `llm.py`.
- Casamento por `input.question` + `input.answer` do `RunRecord` contra `question.text` + `mask_text(answer_text)`; não usar ordem do arquivo nem `input_hash` (frágil a mudanças de params).
- As métricas de referência são calculadas pelo próprio script a partir do replay no momento da gravação (não copiadas do relatório), para o teste comparar maçã com maçã. Tolerância 0: o replay é determinístico.
- Os tipos `CassetteItem`/`CassetteHeader` ficam no script (são só de teste/eval), não em `schemas.py`, que é para contratos do produto e de LLM.
- O teste importa `evals/assertions/judge_asserts.py` e `evals/metrics.py` como já fazem `test_eval_assertions.py` e os testes de métricas.
- Sem dependências novas (`astral-sh/setup-uv` é action, não pacote).

## Plano de testes

| Caso | Entrada | Esperado |
| --- | --- | --- |
| casamento feliz | 2 itens golden + 2 `RunRecord`s da versão pedida | 2 `CassetteItem`s, `outputs` com 1 string cada |
| filtra versão | records v1 e v2 do mesmo item, `--prompt-version 2` | só o output da v2 |
| reparo | item com 2 records (1º inválido, 2º reparo) | `outputs` com as 2 strings, na ordem de `created_at` |
| item sem record | golden com 3 itens, records de 2 | `main` retorna 1, cita o `item_id`, arquivo não criado |
| record duplicado | 2 chamadas não-reparo para o mesmo item | retorna 1, cita o `item_id` |
| replay feliz | fixture real (70) | 70 `AnswerScore`, 0 erros de schema; kappa, ±1 e citações == cabeçalho |
| regressão de métrica | header com `within_one_pct` acima do real (fixture em `tmp_path`) | função de checagem acusa falha nomeando a métrica |
| saída inválida | `CassetteItem` com `outputs=["não é json"]` | `replay_item` levanta erro de validação e o teste reporta o `item_id` |
| golden mudou | fixture sem um `item_id` do golden | falha com "regrave o fixture" |
| sem rede | `replay_item` | nenhum `RunRecord` vai para `runs/` real (só `tmp_path`) |
| tempo | `pytest tests/test_eval_regression.py --durations=5` | < 60 s local e no Actions |

## Perguntas em aberto

- P1. Qual versão do juiz gravar: v1 (a que o produto usa hoje, `JUDGE_PROMPT`) ou v2 (a vencedora da 2.9)? Proposta: a mesma de `JUDGE_PROMPT`, para o CI testar o que vai para produção. → resposta: v1, a mesma de `JUDGE_PROMPT` (hoje `("judge", 1)`): o CI testa o que vai para produção. O script lê a versão de `JUDGE_PROMPT` como padrão de `--prompt-version`; se o produto passar para a v2, regrava-se o fixture.
- P2. O workflow deve rodar em `push` para `main` e em `pull_request`, ou só em PR? (Hoje você commita direto em `main`.) Proposta: os dois. → resposta: os dois (`push` em `main` e `pull_request`), mais `workflow_dispatch`; `concurrency` cancela execuções antigas do mesmo ref e `timeout-minutes: 10`; `permissions: contents: read`.
- P3. Tolerância 0 nas métricas está ok, ou prefere margem (ex.: kappa −0,02) para o teste não quebrar com mudanças legítimas de parse? → resposta: tolerância 0. O replay é determinístico, então qualquer queda é mudança real de comportamento; mudança legítima = regravar o fixture no mesmo commit (a mensagem de falha diz isso).

## Notas de implementação

- Passo 1: desvios do Design, por causa dos dados reais: (a) o reparo de JSON grava **um** `RunRecord` por chamada (as duas tentativas somadas), então `CassetteItem` tem `output: str` (não lista) e o caso de teste "reparo" virou "exatamente 1 record por item"; (b) `load_cassette` e `replay_item` ficam no script (o script precisa do replay para calcular as métricas de referência) e o teste do passo 2 os importa. Fixture v1 (70 itens): kappa 0,565, ±1 72,9%, citações 65,7% (todos os 70 itens, dev+teste). `--prompt-version` padrão = `JUDGE_PROMPT[1]`. 905 testes, cobertura 98,86%; Ruff ok.
- Passo 2: as 3 assertions rodam sobre o `AnswerScore` reserializado; só `assert_schema` é exigida por item (34% dos itens têm citação não verificada por natureza do Haiku), e `assert_quotes_verified`/`assert_score_within_one` entram como % agregado, conferido contra `reference_metrics` e contra o cabeçalho (tolerância 0, falha nomeia a métrica). Teste de "sem rede" checa que `runs/` real não muda. Mutação (`quotes_verified: False`) derrubou o teste com `quotes_verified_pct: 0.0 < referência 65.7`. Replay ~0,8 s. 910 testes, cobertura 98,86%; Ruff ok.
- Passo 3: `ci.yml` com `push` em `main`, `pull_request` e `workflow_dispatch`, `permissions: contents: read`, `concurrency` e `timeout-minutes: 10`; `setup-uv@v5` + `uv python install 3.12` + `uv sync`, ruff e `pytest --durations=10`, sem segredos. Validado localmente: YAML parseia e a suíte passa (910) num clone limpo, sem `.env`. O tempo no Actions só se prova após o push (verify).
