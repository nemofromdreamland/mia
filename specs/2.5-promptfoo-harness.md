# 2.5 — Promptfoo com provider Python e assertions (conjunto A)

## Contexto

O TRD ("Avaliação") manda rodar os conjuntos pelo Promptfoo chamando o código Python real (custom provider), nunca uma cópia dos prompts, com assertions em Python por caso; `evals/metrics.py` (2.6) vai ler o JSON exportado. Esta tarefa monta esse encanamento para o conjunto A (juiz, `evals/datasets/judge_golden.jsonl`) rodando em um modelo. Conjuntos B, C e D entram nas tarefas que os usam (2.7, 2.8).

## Requisitos

- R1. QUANDO o Promptfoo chamar o provider com um item do conjunto A, O SISTEMA DEVE chamar `mia.judge.judge_answer(question, answer_text, ...)` e devolver como `output` o JSON do `AnswerScore` resultante (já verificado por `verify_score`).
- R2. QUANDO a config do provider trouxer `model` (`provider:model_id`), O SISTEMA DEVE repassá-lo ao `judge_answer`; QUANDO não trouxer, O SISTEMA DEVE usar a rota de `config/models.yaml` (`prompt_models.judge`).
- R3. QUANDO o provider rodar, O SISTEMA DEVE gravar o `RunRecord` em `runs/` com `experiment` igual ao valor configurado (padrão `"promptfoo_set_a"`), e devolver em `metadata` o `item_id`, `variant`, `split`, `human_score` e o `model` usado.
- R4. QUANDO o `judge_answer` levantar erro (ex.: `LLMInvalidOutputError`, erro do provedor), O SISTEMA DEVE devolver `{"error": "<tipo>: <mensagem>"}` em vez de derrubar o processo, para o Promptfoo marcar só aquele caso como falho.
- R5. QUANDO o Promptfoo carregar os testes, O SISTEMA DEVE gerar um teste por item do `judge_golden.jsonl` (via gerador Python), com `vars` contendo o item serializado e `description` = `item_id`; um filtro opcional por `split` (`dev`/`test`/todos) DEVE ser suportado.
- R6. QUANDO a assertion de schema receber o `output`, O SISTEMA DEVE passar só se ele validar como `AnswerScore`.
- R7. QUANDO a assertion de citações receber o `output`, O SISTEMA DEVE passar só se `quotes_verified` for `true` (toda citação é literal na resposta).
- R8. QUANDO a assertion de nota receber o `output` e o `human_score` do item, O SISTEMA DEVE passar se `|score - human_score| <= 1` e devolver `score` numérico = 1 − |diff|/4 e `reason` com as duas notas.
- R9. QUANDO `npx promptfoo eval -c evals/promptfooconfig.yaml` rodar, O SISTEMA DEVE avaliar os 70 itens do conjunto A em um modelo e permitir exportar o resultado em JSON (`-o results/<nome>.json`).
- R10. QUANDO o provider, o gerador e as assertions forem testados no pytest, O SISTEMA NÃO DEVE chamar modelo real (chat model falso injetável).

## Fora de escopo

- Métricas agregadas (kappa, viés, consistência, custo, p95): 2.6.
- Baseline em vários modelos e conjunto B: 2.7. Conjunto D e Guardrails: 2.8. Conjunto C.
- Rodar 3 execuções para consistência (`repeat`): 2.6/2.7.
- Modo CI com respostas gravadas: 2.10.
- Qualquer mudança em `judge.py`, prompts ou schemas.

**Interfaces**

```python
# evals/providers/judge_provider.py
DEFAULT_EXPERIMENT: Final[str]  # "promptfoo_set_a"
def call_api(prompt: str, options: dict[str, Any], context: dict[str, Any]) -> dict[str, Any]: ...
def run_item(item: GoldenItem, *, model: str | None, experiment: str,
             runs_dir: Path = DEFAULT_RUNS_DIR,
             chat_model: BaseChatModel | None = None) -> dict[str, Any]: ...  # núcleo testável

# evals/tests_set_a.py
def generate_tests(config: dict[str, Any] | None = None) -> list[dict[str, Any]]: ...
def item_to_test(item: GoldenItem) -> dict[str, Any]: ...

# evals/assertions/judge_asserts.py
def assert_schema(output: str, context: dict[str, Any]) -> dict[str, Any]: ...
def assert_quotes_verified(output: str, context: dict[str, Any]) -> dict[str, Any]: ...
def assert_score_within_one(output: str, context: dict[str, Any]) -> dict[str, Any]: ...
# retorno: {"pass": bool, "score": float, "reason": str}
```

Leitura do JSONL reaproveita `GoldenItem` e o `load_items` de `scripts/golden_io.py` (P2).

**Decisões**

- Provider fino: `call_api` só lê `options["config"]` e `context["vars"]`, reconstrói o `GoldenItem` e chama `run_item`; toda a lógica fica em `run_item`, testável sem Promptfoo.
- O "prompt" do Promptfoo é só um marcador (`"{{item_id}}"`): o prompt real é `prompts/judge/v<N>.yaml`, carregado pelo `judge.py`. Isso cumpre a regra "nunca uma cópia dos prompts".
- Matriz de modelos: um modelo agora (R9); trocar/adicionar modelo = outra entrada em `providers` com `config.model` (base para 2.7). `label` do provider = modelo.
- Assertion de nota (±1) é por item; o número agregado (kappa etc.) é da 2.6.
- `llm.py` continua sendo o único que chama modelo; o provider só chama `judge.py`. PII já é mascarada dentro de `judge_answer`.
- Nenhuma dependência Python nova. Dependência Node: `promptfoo` (justificada no TRD, linha "Avaliação").

## Notas de implementação

- Passo 1: as três assertions compartilham `_parse`, que transforma saída não-JSON, `{"error": ...}` do provider e falha de schema num resultado reprovado com motivo. `vars.item` é aceito como dict ou string JSON (o Promptfoo pode passar qualquer um). O teste carrega o módulo por caminho (`importlib`), porque `evals/` não é pacote. 710 testes passam, cobertura 98,88%; Ruff ok.
- Passo 2: `run_item` captura qualquer exceção e devolve `{"error": "Tipo: msg"}`; o `model` de `metadata` vem de `resolve_prompt_model` (rota `prompt_models.judge` quando a config não traz modelo). O modelo repassado precisa estar em `config/models.yaml` (senão não há preço para o RunRecord); o teste usa o Nova 2 Lite. Gerador: `vars.item` é dict (`model_dump(mode="json")`), `split` aceita `dev`/`test`, qualquer outro valor = todos. Leitura do JSONL própria em `evals/` (P2). 719 testes, cobertura 98,88%; Ruff ok.
- Passo 3: o Promptfoo usa o Python do PATH para o gerador e as assertions, e esse Python precisa enxergar o pacote `mia`. Por isso a rodada exige o venv no PATH e `PROMPTFOO_PYTHON` apontando para ele (no Windows: `.venv/Scripts`); `pythonExecutable` na config só vale para o provider, não para os testes. Versão fixa `promptfoo@0.125.1`. Rodada real: 70 itens no Haiku (rota `prompt_models.judge`), 2m12s, 0 erros, 33 passaram e 37 falharam (23 citações não literais, 14 notas a mais de 1 ponto do humano). As falhas são medida do juiz, não do encanamento; a análise é da 2.6. 70 `RunRecord` em `runs/2026-11-16_promptfoo_set_a.jsonl`.
