# 0.5 — `llm.py` mínimo

## Contexto

`llm.py` é o único ponto do MIA que chama modelos (`AGENTS.md`, "Regras de arquitetura"; `docs/TRD.md`, princípio 1 e "Componentes do backend"). Esta tarefa cria a versão mínima: escolher provedor e modelo a partir de `config/models.yaml`, chamar via LangChain `init_chat_model` e gravar um `RunRecord` por chamada em `runs/*.jsonl` (`docs/BACKEND_SCHEMA.md`, "Execuções, prompts e datasets"; `docs/TRD.md`, "Observabilidade e custo", camada 1). É a base da 0.6 (smoke test de provedores) e de toda a Fase 1.

Estado atual (`55bf46c`): só existem `src/mia/__init__.py`, `tests/test_package.py` e a configuração da 0.4. Não há dependências de runtime, `schemas.py` nem `config/`.

## Requisitos

- R1. QUANDO um `RunRecord` é criado com os campos e tipos do `docs/BACKEND_SCHEMA.md`, O SISTEMA DEVE aceitá-lo, inclusive com `json_valid_first_try = None` e `repaired = None` (não se aplica: saída em texto); QUANDO `provider` não é `bedrock`, `gemini` ou `groq`, ou falta um campo obrigatório, O SISTEMA DEVE levantar `pydantic.ValidationError`.
- R2. QUANDO `load_models_config()` lê `config/models.yaml`, O SISTEMA DEVE devolver o catálogo de modelos (referência `provedor:modelo` → preços por milhão de tokens de entrada e de saída e `free_tier`) e o modelo padrão; QUANDO o arquivo tem campo faltando, preço negativo ou provedor desconhecido, O SISTEMA DEVE levantar `ModelConfigError` com mensagem que diz o arquivo e o campo.
- R3. QUANDO `resolve_model("gemini:<id>")` recebe uma referência que está no catálogo, O SISTEMA DEVE devolver o `ModelSpec` com provedor, id do modelo e preços; QUANDO a referência não está no catálogo ou não tem o formato `provedor:modelo`, O SISTEMA DEVE levantar `ModelConfigError` (sem preço não há como registrar custo).
- R4. QUANDO `build_chat_model(spec, params)` é chamado, O SISTEMA DEVE chamar `init_chat_model` com o id do modelo, o nome do provedor no LangChain (`bedrock` → `bedrock_converse`, `gemini` → `google_genai`, `groq` → `groq`) e os `params`; nenhum outro módulo de `src/mia/` chama `init_chat_model` nem importa pacote de provedor.
- R5. QUANDO `invoke(...)` chama o modelo com sucesso, O SISTEMA DEVE devolver o texto da resposta e acrescentar exatamente uma linha JSON em `runs/<AAAA-MM-DD>_<experimento>.jsonl`, que valida como `RunRecord`, com: `prompt_name`, `prompt_version`, `provider`, `model`, `params`, `input` e `session_id` recebidos; `output_raw` = texto da resposta; `input_tokens` e `output_tokens` vindos do `usage_metadata` da resposta; `latency_ms` ≥ 0; `cost_usd` = tokens × preço do catálogo (também nos modelos com `free_tier: true`, como custo de referência); `output_parsed`, `json_valid_first_try` e `repaired` = `null`; `error = null`; `created_at` em UTC.
- R6. QUANDO a mesma entrada (mesmas mensagens) é enviada duas vezes, O SISTEMA DEVE gravar o mesmo `input_hash` (SHA-256 das mensagens), e QUANDO a entrada muda, um `input_hash` diferente; cada chamada recebe um `run_id` novo.
- R7. QUANDO o provedor levanta exceção durante a chamada, O SISTEMA DEVE gravar mesmo assim uma linha de `RunRecord` com `error` preenchido (tipo e mensagem da exceção), `output_raw = ""`, tokens e custo 0, e relançar a exceção original.
- R8. QUANDO o arquivo do dia já existe, O SISTEMA DEVE acrescentar a linha no fim, sem apagar as anteriores; QUANDO a pasta `runs/` não existe, O SISTEMA DEVE criá-la.
- R9. QUANDO a resposta não traz `usage_metadata`, O SISTEMA DEVE gravar tokens 0 e custo 0, sem falhar.

**Formato de `config/models.yaml`**

```yaml
# Preços em USD por milhão de tokens. Fonte: <páginas oficiais de preço>, consultadas em <AAAA-MM-DD>.
# free_tier: true = uso grátis nesta conta; o preço é o pago publicado, para a comparação de custo ser justa.
default: gemini:<id-do-flash>        # modelo de desenvolvimento (Implementation Plan, Fase 1)
models:
  gemini:<id-do-flash>:
    usd_per_mtok_input: <preço pago publicado>
    usd_per_mtok_output: <preço pago publicado>
    free_tier: true
  groq:<id-do-gpt-oss-120b>:
    ...
    free_tier: true
  bedrock:<id-do-haiku>:
    ...
  bedrock:<id-do-nova-lite>:
    ...
  # Mistral Large 3 — id: a confirmar na 0.6 (só se o id oficial não for encontrado na implementação)
  # bedrock:<id>:
  #   usd_per_mtok_input: <preço>
  #   usd_per_mtok_output: <preço>
```

A chave já é a referência no formato `provedor:modelo` usado nos prompts (`docs/TRD.md`, exemplo `prompts/judge/v2.yaml`); `ref`, `provider` e `model` do `ModelSpec` são derivados dela ao carregar (divide no primeiro `:`, porque ids do Bedrock também têm `:`).

**Decisões**

- **`RunRecord` em `schemas.py` já agora**: o `docs/BACKEND_SCHEMA.md` o define junto dos outros schemas e o Pronto quando pede um `RunRecord` válido. A 1.1 só acrescenta os outros modelos, sem mexer neste.
- **`ModelSpec` e `ModelsConfig` em `llm.py`**, não em `schemas.py`: são configuração interna de `llm.py`, não saída de LLM nem contrato da API.
- **`invoke` devolve `str`**: na 0.5 não há saída estruturada. Nos campos ligados a ela, grava `output_parsed`, `json_valid_first_try` e `repaired` como `null` ("não se aplica"). Gravar `false` contaria como "JSON inválido" nas métricas e pioraria a taxa de JSON válido sem motivo (P2). A 1.5 preenche os três nas chamadas com `output_schema`, e as métricas da Fase 2 contam só os registros sem `null`.
- **Mistral sem id oficial**: se o id não for encontrado na implementação, a entrada fica comentada no YAML, com "id: a confirmar na 0.6". Uma chave `provedor:modelo` com id inválido passaria na carga e só falharia na chamada real.
- **Modelos gratuitos** (Gemini, Groq): `free_tier: true` e o preço pago publicado como custo de referência. Assim o `cost_usd` dá para comparar entre modelos (P1).
- **Injeção de `chat_model`**: os testes passam um modelo falso do próprio LangChain (`GenericFakeChatModel`, de `langchain_core`), que devolve uma `AIMessage` pronta, com `usage_metadata`. Assim o teste exercita o caminho real de `invoke` sem rede e sem chave. `build_chat_model` é testado à parte, trocando `init_chat_model` por um dublê (`monkeypatch`) que só confere os argumentos.
- **`input_hash` = SHA-256 de `system` + separador + `user`**: identifica chamadas idênticas para cache e consistência nas avaliações (Fase 2), sem guardar o texto duas vezes.
- **`run_id` = `uuid4().hex`**: sem dependência nova. (ULID é a convenção para ids de sessão, não para execuções.)
- **Arquivo do dia**: `runs/<data UTC>_<experiment>.jsonl`, com `experiment = None` → `adhoc` (ver P4). Uma linha por chamada, modo de acréscimo (`"a"`), UTF-8, `RunRecord.model_dump_json()`.
- **Custo** = `input_tokens × usd_per_mtok_input / 1_000_000 + output_tokens × usd_per_mtok_output / 1_000_000`, arredondado a 8 casas.
- **Latência** medida com `time.perf_counter()` só em volta da chamada ao modelo, em milissegundos inteiros.
- **Erro do provedor**: grava o registro com `error = "<TipoDaExceção>: <mensagem>"` e relança (`raise`), para nunca perder o rastro de uma chamada que falhou (`AGENTS.md`: "Toda chamada a modelo grava um RunRecord").
- **Dependências novas (justificativa)**: `langchain` traz `init_chat_model` (escolha do TRD, "Stack e decisões") e `langchain-core` (mensagens, `BaseChatModel`, modelo falso dos testes); `pydantic` para `RunRecord` e a config (já vem junto, mas o código importa direto, então fica declarada); `pyyaml` para ler `config/models.yaml` (e depois os prompts da 1.2).
