# 3.6f — Telas Recrutador e Candidato

## Contexto

Blocos 5 e 6 da seção 14 do Design: `/recrutador` lista, por caso, os candidatos acima da média (anônimos) e `/recrutador/:id` mostra o desempenho de um candidato e o próximo passo sugerido. Fontes: `docs/design/05-telas.md` (6.7, 6.8), `04-componentes.md` (5.14, 5.16, 5.20, 5.24, 5.32), `07` (10.1, 13), `BACKEND_SCHEMA` (`RecruiterList`, `CaseStats`, `RecruiterCandidateRow`, `RecruiterCandidate`, `CandidateSummary`). Regra do `AGENTS.md`: nada que identifique o visitante; o resumo é apoio à decisão.

## Requisitos

- R1. QUANDO `/recrutador` abre, O SISTEMA DEVE chamar `GET /recruiter/candidates` (com `case_id` quando houver `?caso=`) e `GET /cases`, mostrar "TELA DO RECRUTADOR", `h1` "Candidatos acima da média", "Entrevistas feitas nesta demo, anônimas. Cada caso tem a sua média." e, no fim, "Os resumos são gerados pela MIA a partir das respostas da entrevista. São apoio à decisão: quem decide é você.". Aba: "Candidatos · MIA".
- R2. O CaseFilter (`data-testid="case-filter"`, `select` do shadcn, 280 px, largura total no celular) DEVE ter "Todos os casos" + os casos de `list_cases` e gravar o valor em `?caso=<case_id>` (sem parâmetro para "Todos os casos").
- R3. O SISTEMA DEVE mostrar um grupo por caso, na ordem de `list_cases`: `h2` "{title} · {company}" e a linha `small mono muted` "Média do caso 3,4 · 12 entrevistas concluídas" (ou "Média ainda não calculada · {n} entrevistas concluídas" sem média).
- R4. Cada RecruiterRow (`data-testid="recruiter-row"`) DEVE mostrar "Candidato {candidate_no}" (`font-mono`), `ended_at` em `dd/mm/aaaa`, RubricScore `sm` + decimal, "+0,8" (`font-mono tabular-nums`, sem cor e sem seta; "—" sem média), `headline` em 1 linha com reticências e "Ver candidato" (outline → `/recrutador/:id`). No celular vira card ("Candidato 7 · 15/11/2026"; nota e "+0,8 acima da média"; headline em 2 linhas; botão largura total).
- R5. Caso sem concluídas → linha `muted` "Ninguém concluiu este caso ainda." + link "Fazer este caso" (→ `/?caso=<case_id>`); menos de 3 → InlineNotice `neutral` "Mostrando todos os concluídos até haver 3 entrevistas."; com média e ninguém acima → "Nenhum candidato acima da média neste caso por enquanto.".
- R6. Carregando → skeleton (título do grupo + 3 linhas) por caso; erro → InlineNotice `danger` "Não foi possível carregar os candidatos." + "Tentar de novo".
- R7. QUANDO `/recrutador/:id` abre, O SISTEMA DEVE chamar `GET /recruiter/candidates/:id` e `GET /cases` e mostrar: link "← Candidatos", rótulo "CANDIDATO 7 · {TÍTULO DO CASO}", `h1` serifa com `headline`, "{Entrevista técnica} · {data longa} · {18 min}", "NOTA GERAL" com o número em `text-display` + "de 5" + RubricScore `md` com rótulo e "+0,8 acima da média do caso (3,4)" (`small mono muted`). Aba: "Candidato {n} · MIA".
- R8. A página DEVE mostrar "Resumo" (`data-testid="candidate-summary"`, `text-answer`), "Pontos fortes" e "Pontos de atenção" em 2 colunas (empilhadas no celular), cada ponto com `h3` e EvidenceQuote "DA RESPOSTA" — só se o trecho existir literalmente numa resposta —, "Por competência" (CompetencyRow sem "antes"), "Próximo passo sugerido" com NextStepTag (`data-testid="next-step"`, borda `border-strong`, texto `foreground`, sem cor: AVANÇAR PARA A PRÓXIMA ETAPA / AVANÇAR COM RESSALVAS / NÃO AVANÇAR AGORA), `next_step_reason`, "Apoio à decisão. Quem decide é você.", a transcrição completa fechada e "Voltar aos candidatos" (outline).
- R9. `not_found` → tela inteira "Este candidato não está mais disponível." + "Voltar aos candidatos"; outro erro → InlineNotice `danger` "Não foi possível carregar o candidato." + "Tentar de novo"; carregando → skeleton (cabeçalho, nota, 3 parágrafos).
- R10. Nenhuma das duas telas DEVE mostrar `visitor_id`, `session_id` ou outro dado do visitante, mesmo que a API mande campos a mais.

## Fora de escopo

- Login de recrutador, ações de decisão (avançar/reprovar), exportação; estados da 10.2 (3.7).

**Interfaces**

```ts
// lib/types.ts
export type CaseStats = { case_id: string; completed_sessions: number; average_score: number | null };
export type RecruiterCandidateRow = { session_id: string; case_id: string; candidate_no: number; ended_at: string;
  overall_score: number; delta_vs_case_avg: number | null; headline: string };
export type RecruiterList = { stats: CaseStats[]; candidates: RecruiterCandidateRow[] };
export type SummaryPoint = { point: string; answer_quote: string };
export type CandidateSummary = { headline: string; summary: string; strengths: SummaryPoint[]; concerns: SummaryPoint[];
  suggested_next_step: "advance" | "advance_with_caution" | "not_now"; next_step_reason: string };
export type RecruiterCandidate = { row: RecruiterCandidateRow; summary: CandidateSummary; report: Report; turns: Turn[] };

// lib/labels.ts
export function nextStepLabel(step: CandidateSummary["suggested_next_step"]): string;
export function formatDelta(delta: number): string;   // 0.8 → "+0,8"

// components
export function NextStepTag(p: { step: CandidateSummary["suggested_next_step"] }): JSX.Element;
export function CaseFilter(p: { cases: CaseSummary[]; value: string | null; onChange: (caseId: string | null) => void }): JSX.Element;
export function RecruiterRow(p: { row: RecruiterCandidateRow }): JSX.Element;
```

**Decisões**

- Linhas agrupadas por `case_id` no front; dentro do grupo, a ordem da API (maior diferença primeiro).
- A tela renderiza campo a campo (nunca espalha o objeto da API), então campos extras não aparecem (R10).
- Duração no Candidato: `created_at` do primeiro turno até `row.ended_at` (a API do recrutador não traz `started_at`).
- Média no Candidato: `overall_score − delta_vs_case_avg` (a linha não traz a média). Sem média: "Média ainda não calculada" (texto da 6.7).
- Título do caso e persona no Candidato vêm de `list_cases`; se falhar, o rótulo mostra só "Candidato N" e a linha de meta omite o nome da entrevista.
- Tabela única com CSS responsivo (mesmo padrão da `SessionList` da 3.6b).

## Notas de implementação
- Passo 1: "Ver candidato" é um `<Link>` com o visual do botão outline (`buttonVariants`), porque a ação é navegação. Headline num só `<p>`: `line-clamp-2` no celular e `md:truncate` no desktop. `formatDelta` usa o sinal de menos tipográfico para diferença negativa (não acontece na lista, que só tem quem está acima). CaseFilter com `aria-label="Filtrar por caso"` (**Lacuna de microcopy**). `setup.ts` ganhou stubs de `hasPointerCapture`/`releasePointerCapture`/`scrollIntoView` para o Select do Radix no jsdom.
- Passo 2: Grupos montados a partir de `list_cases` (ordem) cruzados com `stats`; caso sem `stats` (filtro ativo) não aparece. Cada grupo é um `<section aria-labelledby>`. Skeleton: 5 grupos (1 com filtro). O filtro grava `?caso=` e refaz o GET com `case_id`. Contagem no singular "1 entrevista concluída" (**Lacuna de microcopy**). `md:table-fixed` para as larguras da 6.7 no desktop.
- Passo 3: Candidato e casos em paralelo; falha de `list_cases` não bloqueia (rótulo "Candidato N" sem título e meta sem o nome da entrevista; persona da transcrição cai para `technical`, que só muda o rótulo "MIA · …"). Duração = 1º turno → `ended_at`; média = nota − diferença. EvidenceQuote "DA RESPOSTA" recebe `verified` = trecho presente literalmente em alguma resposta. "← Candidatos" com `ArrowLeft` do lucide. `FullPageState` (3.6c) reaproveitado no `not_found`.
- Passo 4: Testes de privacidade com uma API "vazando" `visitor_id`, e-mail e `session_id` extras: o `innerHTML` não contém o `visitor_id` nem o e-mail, e o texto visível não contém o `session_id` (ele só aparece no `href` de "Ver candidato", que é o id da rota). Passaram de primeira porque as telas já renderizam campo a campo (passos 2–3). `placeholders.tsx` removido com `git rm` (as 6 telas são reais). `router.test.tsx` não precisou mudar: título e cabeçalho das 6 rotas continuam testados.
