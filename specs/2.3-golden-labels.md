# 2.3 — Notas humanas e split dev/teste do golden set

## Contexto

O conjunto A (`evals/datasets/judge_golden.jsonl`, 70 itens da 2.2) ainda tem `human_score` e `split` vazios. Esta tarefa é do **dono do projeto**: dar a nota 1–5 a cada resposta sem ver a nota do juiz e dividir dev 70% / teste 30% estratificado por nível. O agente só entrega duas ferramentas pequenas para isso ser rápido, cego e reprodutível. Fontes: `docs/IMPLEMENTATION_PLAN.md` (2.3), `docs/TRD.md` § Avaliação / Regras do golden set, `docs/BACKEND_SCHEMA.md` § Golden set, `docs/PRD.md` (riscos: nota humana antes do juiz).

## Requisitos

- R1. QUANDO o dono roda o rotulador, O SISTEMA DEVE mostrar, item a item, só a pergunta (`text`), os `look_for` da pergunta e `answer_text`, sem mostrar `variant`, `paraphrase_of`, `item_id` nem qualquer nota de juiz (ver P1).
- R2. QUANDO o dono digita um inteiro de 1 a 5, O SISTEMA DEVE gravar esse valor em `human_score` do item e passar ao próximo.
- R3. QUANDO o dono digita algo fora de 1–5 (ex.: `0`, `6`, `a`, vazio), O SISTEMA DEVE recusar, mostrar a mensagem de entrada inválida e perguntar de novo, sem gravar nada.
- R4. QUANDO o dono digita `q`, O SISTEMA DEVE sair com código 0 mantendo as notas já dadas.
- R5. QUANDO o rotulador é aberto de novo, O SISTEMA DEVE pular os itens que já têm `human_score` (retomar de onde parou) e, se todos tiverem, avisar e sair com código 0.
- R6. QUANDO grava uma nota, O SISTEMA DEVE reescrever o JSONL inteiro de forma atômica (arquivo temporário + `replace`), validando todas as linhas com `GoldenItem`, para que uma interrupção não corrompa o dataset.
- R7. QUANDO a ordem de apresentação é montada, O SISTEMA DEVE embaralhar os itens com semente fixa, para que as respostas da mesma pergunta não apareçam em sequência de nível (evita ancorar a nota pela ordem).
- R8. QUANDO o dono roda o divisor e todos os 70 itens têm `human_score`, O SISTEMA DEVE preencher `split` de forma determinística (semente fixa): por `variant`, 7 de 10 itens em `dev` e 3 em `test` (total 49/21).
- R9. QUANDO um item `paraphrase` é dividido, O SISTEMA DEVE colocá-lo no mesmo split do item de `paraphrase_of` (ver P2), mantendo as contagens de R8.
- R10. QUANDO o divisor roda com algum item sem `human_score`, O SISTEMA DEVE sair com código 1, mensagem dizendo quantos faltam, e não gravar nada.
- R11. QUANDO o divisor roda e os itens já têm `split`, O SISTEMA DEVE recusar (código 1) a menos que receba `--force`.
- R12. QUANDO o dataset commitado é testado, O SISTEMA DEVE verificar: 70 itens, todo `human_score` em 1–5, todo `split` preenchido, 49 dev / 21 test, 7/3 por `variant` e paráfrase no mesmo split da original.

## Fora de escopo

- Rodar o juiz no golden set ou calcular kappa/erro (tarefas de avaliação seguintes).
- Editar `answer_text` ou regenerar respostas (se uma resposta estiver ruim, ver P4).
- Conjuntos B, C e D (2.4). Promptfoo.
- Alterar `GoldenItem` ou `BACKEND_SCHEMA.md`.

## Design

**Arquivos**

| Arquivo | Ação | Conteúdo |

**Interfaces**

```python
# scripts/golden_io.py
GOLDEN_PATH: Final[Path]
def load_items(path: Path = GOLDEN_PATH) -> list[GoldenItem]: ...
def save_items(items: list[GoldenItem], path: Path = GOLDEN_PATH) -> None: ...  # atômico

# scripts/label_golden.py
SHUFFLE_SEED: Final[int]
def presentation_order(items: list[GoldenItem], seed: int = SHUFFLE_SEED) -> list[int]: ...  # índices sem nota, embaralhados
def render_item(item: GoldenItem, position: int, total: int) -> str: ...  # só pergunta, look_for, resposta
def parse_score(raw: str) -> int | Literal["quit"] | None: ...  # None = inválido
def main(argv: Sequence[str] | None = None, *,
         input_fn: Callable[[str], str] = input,
         path: Path = GOLDEN_PATH) -> int: ...

# scripts/split_golden.py
SPLIT_SEED: Final[int]
DEV_PER_VARIANT: Final[int]  # 7
def assign_splits(items: list[GoldenItem], seed: int = SPLIT_SEED) -> list[GoldenItem]: ...
def main(argv: Sequence[str] | None = None, *, path: Path = GOLDEN_PATH) -> int: ...
```

**Decisões**

- Scripts em `scripts/`, como `build_golden.py`: rodam uma vez, não são produto. Nenhuma dependência nova (`random.Random(seed)`, `argparse`, `input`).
- Cegueira: a tela não mostra `variant` (que é o "nível pretendido") para a nota medir a resposta, não a intenção do gerador. Ainda não existe nota de juiz no dataset, então R1 cobre isso por construção.
- Grava a cada nota (R6): rotular 70 respostas longas leva horas; dá para parar e voltar.
- Split por `variant` com paráfrase acompanhando a original (P2): com 10 itens por variant, o divisor escolhe 7 perguntas para dev em `level_*`/`rambling` de forma que a paráfrase siga a original; se a amarração impedir 7/3 exato numa variant, o teste de R12 falha e o passo para (decisão volta ao dono).
- `input_fn` injetável: testes sem terminal real.

## Plano de testes

| Caso | Entrada | Esperado |
| --- | --- | --- |
| render cego | item `level_5` | texto contém pergunta, cada `look_for` e resposta; não contém `level_5`, `item_id`, `paraphrase_of` |
| nota válida | entradas `"4"`, `"q"` em arquivo de 3 itens | 1º item da ordem com `human_score=4`; resto `None`; código 0 |
| entrada inválida | `"0"`, `"6"`, `"x"`, `""`, `"3"`, `"q"` | só a nota 3 gravada; mensagem de inválido aparece 4 vezes |
| retomar | arquivo com 2 de 3 notados, entrada `"5"` | só o item sem nota é apresentado; ao fim, todos notados, código 0 |
| tudo notado | arquivo completo | aviso "nada a rotular", código 0, arquivo intacto |
| ordem | mesma semente 2× | mesma ordem; difere da ordem do arquivo |
| atômico | `save_items` com item inválido | `ValidationError`; arquivo original intacto |
| split feliz | 70 itens notados (fixture sintético 10 × 7) | 49 dev/21 test; 7/3 por variant; paráfrase = split da original; 2 execuções iguais |
| split incompleto | 1 item sem nota | código 1, mensagem "falta 1", arquivo intacto |
| split já feito | itens com `split`, sem `--force` | código 1; com `--force` regrava |
| dataset real | `judge_golden.jsonl` | todas as checagens de R12 |

## Perguntas em aberto

- P1. Esconder `variant` na tela de rótulo (proposto) ou mostrar? Esconder deixa a nota mais honesta; mostrar é mais rápido. → resposta: esconder (proposta aprovada).
- P2. "Estratificado por nível" = por `variant` (7 dev / 3 test em cada uma das 7, proposto) ou pela `human_score` final? E a paráfrase deve ficar no mesmo split da original (proposto, evita vazar a mesma resposta entre dev e teste)? Alternativa mais simples e sem vazamento: split por pergunta (7 perguntas dev, 3 teste, com as 7 respostas de cada). → resposta: por `variant`, paráfrase no mesmo split da original (proposta aprovada). Todas as paráfrases são de `level_3`, então o 7/3 fecha.
- P3. Garantir mistura técnica/comportamental no teste (ex.: das 3 perguntas/itens por variant, ao menos 1 comportamental)? → resposta: não exigir (sem proposta; fora do pedido).
- P4. Se o dono achar uma resposta inutilizável (ex.: `gq-beh-03-level_1`, que não sai do tema), só dá a nota que ela merece (proposto) ou regenera? Regenerar está fora de escopo desta spec. → resposta: só dar a nota (proposta aprovada).

## Notas de implementação

- Passo 1: `golden_io.py` grava com `.tmp` + `os.replace` e revalida cada item antes. O rotulador importa `golden_io` direto (o Python põe `scripts/` no path ao rodar o script); o teste insere `scripts/` no `sys.path`. Semente de ordem `2303`. Mensagens `INVALID_MSG` e `NOTHING_MSG` viram constantes para o teste. 635 testes passam, cobertura 98,81%; Ruff ok.
- Passo 2: `assign_splits` embaralha (semente `2304`) os ids ordenados de cada variant que não é paráfrase e põe os 7 primeiros em dev; a paráfrase copia o split da original (como as originais são todas `level_3`, o 7/3 fecha). Mensagens: "falta N nota(s)" e aviso de split existente. 640 testes passam, cobertura 98,81%; Ruff ok.
- Passo 3 (mudança pedida pelo dono): o Claude preencheu as 70 `human_score` (padrão por nível, com exceções em gq-beh-03-level_1 = 4 e nos rambling de beh-02/beh-03 = 3); o dono revisa e corrige. Risco registrado: a referência deixa de ser humana independente e vem de um modelo da mesma família do juiz, o que pode inflar a concordância medida na 2.4.
- Passo 4: rodei `split_golden.py` (sem `--force`) no dataset; 49 dev / 21 test, 7/3 por variant, paráfrase no split da original. `test_golden_dataset.py` ganhou 5 testes (R12). 645 testes passam, cobertura 98,81%; Ruff ok.
