# 2.9 — Prompt v2 do juiz (ajuste no dev, número no teste)

## Contexto

O baseline (2.7, `results/baseline_v1.md`) mostrou o juiz v1 no Haiku generoso demais: erro médio +1,06 no dev, viés de verbosidade +1,40 nas respostas "enroladas" e só ~66% de citações verificáveis. Esta tarefa cria `prompts/judge/v2.yaml` ajustado olhando **só o split dev** e reporta v1 × v2 no split teste, incluindo o que piorou (TRD "Avaliação" → "Regras do golden set": "Prompts são ajustados só no split dev; o número reportado vem do split teste"; PRD métrica de concordância "no split de teste"; Implementation Plan 2.9).

## Requisitos

- R1. QUANDO `judge_answer` receber `prompt_version=N`, O SISTEMA DEVE carregar `prompts/judge/vN.yaml`; sem o argumento, DEVE usar a versão de `JUDGE_PROMPT` (comportamento atual inalterado).
- R2. QUANDO o provider do conjunto A receber `config.prompt_version`, O SISTEMA DEVE julgar com essa versão e gravar `prompt_version` no `metadata` da saída; sem a chave, DEVE usar a versão padrão.
- R3. QUANDO o script de análise de erros rodar sobre um export do conjunto A, O SISTEMA DEVE listar só itens com `split == "dev"` (nota humana, nota do juiz, variant, justificativa, citações descartadas) e nunca imprimir item de teste.
- R4. QUANDO o script de análise receber `--split test`, O SISTEMA DEVE recusar com código de saída 2 e mensagem dizendo que o teste não é usado para ajuste.
- R5. QUANDO `prompts/judge/v2.yaml` existir, O SISTEMA DEVE carregá-lo com `output_schema: AnswerScore`, `model` igual à rota de `prompt_models.judge` e um `changelog` que cite os problemas medidos no dev; `tests/test_prompt_models_guard.py` DEVE passar sem incluir v2 em `LEGACY_STALE_MODEL`.
- R6. QUANDO a config `evals/judge_v1_vs_v2.yaml` rodar, O SISTEMA DEVE julgar os 70 itens com dois providers (mesmo modelo Haiku, `prompt_version` 1 e 2, labels `judge-v1` e `judge-v2`) e experimento `judge_v1_vs_v2`.
- R7. QUANDO `evals/metrics.py` receber `--compare judge-v1 judge-v2`, O SISTEMA DEVE gerar uma seção "v1 × v2" com, por split (dev, test oficial, todos): kappa, erro médio, MAE, % ±1, viés de verbosidade, % citações verificáveis, custo médio e p95, cada um com o delta (v2 − v1) e a indicação "melhorou / piorou / igual" segundo a direção boa da métrica.
- R8. QUANDO houver métrica que piorou ou item de teste cujo |juiz − humano| cresceu de v1 para v2, O SISTEMA DEVE listá-los numa subseção "O que piorou" (métrica ou `item_id`, v1, v2); sem pioras, DEVE escrever "Nenhuma piora".
- R9. QUANDO os labels de `--compare` não existirem no export, O SISTEMA DEVE sair com código 1 sem gravar o relatório.

CLI final: `uv run python evals/metrics.py --export results/judge_v1_vs_v2.json --runs runs/<data>_judge_v1_vs_v2.jsonl --experiment judge_v1_vs_v2 --compare judge-v1 judge-v2` → `results/judge_v1_vs_v2.md`.

**Decisões**

- Versão por parâmetro, não por constante nova: o produto continua em v1; só o eval escolhe v2. Custo/latência por versão saem do `prompt_version` do `RunRecord` (já existe no schema) cruzado com o label.
- Direção boa de cada métrica: kappa, % ±1, % citações ↑; |erro médio|, MAE, |viés|, custo, p95 ↓. Delta com |Δ| < 0,005 (ou 0,5 p.p.) = "igual".
- Análise de erro de dev a partir do export Haiku da 2.7 (`results/baseline_v1_set_a.json`, label Haiku): não gasta chamada nova para enxergar o problema.
- "Cegueira" do teste é por processo e por código: o script de análise não imprime teste (R3/R4); as rodadas de iteração usam `config.split: dev` no gerador de testes; o teste só roda na rodada final, uma vez, com v1 e v2 juntos.
- v1 roda de novo na rodada final (mesmo dia, mesmo modelo) em vez de reaproveitar o baseline: comparação justa contra a variação do modelo. Custo estimado: 140 chamadas ≈ US$ 0,50.
- Hipóteses de ajuste (a confirmar no passo 2, não requisito): âncoras da rubrica mais duras (o que *não* é 4/5), penalizar extensão sem conteúdo, citação curta e literal, nota decidida depois das citações.

## Plano de testes

| Caso | Entrada | Esperado |
| --- | --- | --- |
| versão padrão | `judge_answer(q, a, chat_model=fake)` | carrega `("judge", 1)`; `RunRecord.prompt_version == 1` |
| versão 2 | `judge_answer(..., prompt_version=2, chat_model=fake)` | `RunRecord.prompt_version == 2` |
| versão inexistente | `prompt_version=99` | erro do `load_prompt` (arquivo não encontrado) |
| provider com versão | `call_api` com `config={"prompt_version": 2}` + fake | `metadata.prompt_version == 2` |
| provider sem versão | `config={}` | `metadata.prompt_version == 1` |
| análise só dev | export com 2 dev + 2 test | só os 2 `item_id` dev no texto |
| análise min_gap | dev com gaps 0, 1, 2 e `min_gap=2` | 1 item |
| análise recusa teste | `main(["--split", "test", ...])` | retorna 2, mensagem cita "teste" |
| análise erro do juiz | item dev com `response.error` | aparece com `judge_score=None` |
| v2 carrega | `load_prompt("judge", 2)` | `output_schema == "AnswerScore"`, `changelog` não vazio, `model` = rota |
| delta melhorou | MAE v1 1,0 → v2 0,5 | `delta -0.5`, `"melhorou"` |
| delta piorou | kappa 0,6 → 0,5 | `"piorou"` |
| delta igual / n/d | 0,500 → 0,502; v2 `None` | `"igual"`; `"n/d"` |
| regressão de item | teste: humano 2, v1 3, v2 4 | 1 `ItemRegression` |
| sem regressão | v2 mais perto em todos | lista vazia; render com "Nenhuma piora" |
| CLI label ausente | `--compare judge-v1 judge-v9` | sai 1, não grava `.md` |
| render compatível | `render_report` sem `compare` | igual ao da 2.7 (testes existentes passam) |

## Notas de implementação

- Passo 1: `judge_answer(prompt_version=None)` usa `prompt_version or JUDGE_PROMPT[1]`; o produto continua em v1. O provider repassa `config.prompt_version` e grava no `metadata` a versão efetiva (1 quando ausente). Como a v2 ainda não existe, o teste da versão 2 espiona `load_prompt` (confere que pediu `("judge", 2)`); a versão 99 falha com `PromptError`. 876 testes, cobertura 98,86%; Ruff ok.
- Passo 2: o script só lê o export (sem LLM) e filtra `split == "dev"` no próprio parse; `--split` diferente de `dev` retorna 2. `dropped_quotes` vale 0/1 (o export só guarda `quotes_verified`, não quantas citações caíram). Padrão `min_gap=1` incluindo erros do juiz (`judge_score=None`). 882 testes, cobertura 98,86%; Ruff ok.
- Passo 3: `v2.yaml` (1 tentativa, sem precisar de v3): avaliador exigente, citar antes de pontuar, âncoras 4/5 mais duras, extensão não vale nota, citação curta e literal; `model` = rota `prompt_models.judge`. `evals/judge_v1_vs_v2.yaml` tem `config.split: dev` no gerador (o passo 5 remove). Rodar da raiz do projeto (`pythonExecutable` é relativo). Dev (49 itens), v1 → v2: erro médio +1,06 → +0,53; MAE 1,06 → 0,61; ±1 71% → 98%; rambling +1,00 → +0,14. Citações ainda descartadas em 5 itens. Teste não foi tocado.
