# 1.2 — Carregador de prompts

## Contexto

Hoje quem chama `llm.invoke` monta `system` e `user` à mão e informa nome e versão do prompt. Esta tarefa cria `src/mia/prompts.py`, que lê `prompts/<nome>/v<N>.yaml`, valida os campos, preenche os templates e decide o modelo, para que nome, versão, modelo e parâmetros cheguem ao `RunRecord` sem digitação manual. Fontes: `docs/BACKEND_SCHEMA.md` ("Prompt"), `docs/TRD.md` ("Prompts: biblioteca e versionamento", "Componentes do backend"), spec 0.5 ("Fora de escopo").

## Requisitos

- R1. QUANDO `load_prompt(nome, versão)` recebe um arquivo válido, O SISTEMA DEVE devolver um `PromptSpec` com `name`, `version`, `model`, `params`, `output_schema`, `system`, `user` e `changelog`.
- R2. QUANDO o arquivo não existe, O SISTEMA DEVE levantar `PromptError` com o caminho e as versões disponíveis daquele prompt (ou "nenhuma").
- R3. QUANDO o YAML é ilegível ou não é um mapeamento, O SISTEMA DEVE levantar `PromptError` com o caminho.
- R4. QUANDO falta um campo obrigatório (`name`, `version`, `model`, `params`, `system`, `user`), há um campo desconhecido ou um campo tem o tipo errado, O SISTEMA DEVE levantar `PromptError` com `<caminho>: <campo>: <motivo>`.
- R5. QUANDO `name` difere da pasta ou `version` difere do número no nome do arquivo, O SISTEMA DEVE levantar `PromptError` dizendo os dois valores.
- R6. QUANDO `output_schema` está presente e não é o nome de uma classe `BaseModel` de `mia.schemas`, O SISTEMA DEVE levantar `PromptError`; QUANDO está ausente, O SISTEMA DEVE tratar a saída como texto livre (`None`).
- R7. QUANDO `version >= 2` e `changelog` está ausente ou vazio, O SISTEMA DEVE levantar `PromptError`.
- R8. QUANDO `system` ou `user` está vazio ou tem chaves malformadas (ex.: `{pergunta` sem fechar), O SISTEMA DEVE levantar `PromptError` já ao carregar.
- R9. QUANDO `model` não está no formato `provedor:modelo` ou não existe no `config/models.yaml`, O SISTEMA DEVE levantar `PromptError` ao carregar (o custo precisa ser registrável).
- R10. QUANDO `render(prompt, variáveis)` recebe exatamente as variáveis dos templates, todas `str`, O SISTEMA DEVE devolver `system` e `user` preenchidos; o valor é inserido como texto, mesmo que contenha `{` ou `}`.
- R11. QUANDO falta variável, sobra variável ou um valor não é `str`, O SISTEMA DEVE levantar `PromptError` listando os nomes.
- R12. QUANDO o modelo do prompt é resolvido, O SISTEMA DEVE usar a ordem: argumento explícito > sobrescrita por config (ver P1) > `model` do YAML; e o resultado precisa existir no catálogo.
- R13. QUANDO `run_prompt` é chamado, O SISTEMA DEVE chamar `llm.invoke` com `prompt_name`, `prompt_version`, o modelo resolvido, os `params` do YAML e `input = variáveis`, de modo que o `RunRecord` gravado traga nome, versão, provedor, modelo e parâmetros do prompt.

## Fora de escopo

- Os prompts reais (`prompts/*/v1.yaml`): tarefa 1.3. Aqui os testes usam fixtures em `tests/fixtures/prompts/`.
- Saída estruturada, validar a resposta contra `output_schema`, reparo de JSON: tarefa 1.5. Aqui `output_schema` só é conferido como nome válido e `run_prompt` devolve `str`.
- Mascarar PII (tarefa 1.4): `run_prompt` recebe as variáveis já mascaradas, como o `invoke` atual.
- Gravar `Session.prompt_versions` (Fase 3) e impedir edição de prompt já usado em experimento (é regra de processo, não de código).
- Validar as chaves de `params` por provedor: vão como estão para `init_chat_model`.

**Interfaces**

```python
# src/mia/prompts.py
DEFAULT_PROMPTS_DIR: Path  # <raiz do repo>/prompts

class PromptError(Exception): ...

class PromptSpec(BaseModel):          # extra="forbid"
    name: str
    version: StrictInt                # >= 1
    model: str                        # "provedor:modelo"
    params: dict[str, Any]
    output_schema: str | None = None  # nome de classe em mia.schemas
    system: str
    user: str
    changelog: str | None = None      # obrigatório se version >= 2
    path: Path                        # arquivo de origem (para mensagens); preenchido pelo carregador
    variables: frozenset[str]         # nomes {x} de system + user; preenchido pelo carregador

class RenderedPrompt(BaseModel):
    system: str
    user: str

def available_versions(name: str, prompts_dir: Path = DEFAULT_PROMPTS_DIR) -> list[int]: ...
def load_prompt(
    name: str,
    version: int,                     # ver P2
    *,
    prompts_dir: Path = DEFAULT_PROMPTS_DIR,
    models: ModelsConfig | None = None,  # None → llm.load_models_config()
) -> PromptSpec: ...
def output_schema_class(prompt: PromptSpec) -> type[BaseModel] | None: ...
def render(prompt: PromptSpec, variables: Mapping[str, str]) -> RenderedPrompt: ...
def resolve_prompt_model(
    prompt: PromptSpec, models: ModelsConfig, override: str | None = None
) -> ModelSpec: ...
def run_prompt(
    prompt: PromptSpec,
    variables: Mapping[str, str],
    *,
    model: str | None = None,         # sobrescrita explícita (experimentos, Promptfoo)
    experiment: str | None = None,
    session_id: str | None = None,
    models: ModelsConfig | None = None,
    runs_dir: Path = DEFAULT_RUNS_DIR,
    chat_model: BaseChatModel | None = None,  # injeção para testes
) -> str: ...
```

**Decisões**

- **Direção da dependência `prompts.py → llm.py`**: `prompts.py` usa `ModelsConfig`, `resolve_model` e `invoke` de `llm.py`; `llm.py` não importa `prompts.py` (evita import circular). `prompts.py` não importa LangChain de modelos nem SDK; o teste de arquitetura existente (`test_only_llm_module_touches_...`) já varre `src/mia/` e cobre o arquivo novo. `BaseChatModel` aparece só como tipo do parâmetro de injeção, importado de `langchain_core.language_models` — se o teste de arquitetura barrar esse import, o tipo vira `Any` (decidir no passo 3).
- **Templates com `str.format` e `string.Formatter().parse`**: sem dependência nova. As variáveis são extraídas ao carregar (R8) e conferidas no render (R11). Chave literal no template (ex.: exemplo de JSON) se escreve `{{ }}`, convenção do Python, registrada no docstring. Só nomes simples são aceitos: `{a.b}`, `{a[0]}`, `{a!r}` e `{a:>10}` geram `PromptError` (evita acesso a atributos via template).
- **Variáveis só `str`**: quem chama formata listas (ex.: `look_for`) antes. Mantém o `input` do `RunRecord` igual ao texto enviado.
- **Validação do modelo já na carga (R9)**: erro de digitação no YAML aparece ao carregar, não no meio de uma entrevista.
- **`version` do arquivo = número em `v<N>.yaml`**: `available_versions` lista os `v<N>.yaml` da pasta, ordenados; arquivo fora do padrão é ignorado.
- **Mensagens de erro** no formato da 0.5: `<caminho>: <campo>: <motivo>`, reaproveitando a ideia de `_describe` (erros do Pydantic achatados em uma linha).
- **`run_prompt` não valida a saída**: devolve o texto, como `invoke`; a 1.5 troca isso por saída estruturada quando houver `output_schema`.

| render não-str | `{"question": 3, ...}` | `PromptError` |
| chave literal | template com `{{"score": 1}}` | render produz `{"score": 1}`; `{{`/`}}` não viram variáveis |
| resolução | YAML `gemini:a`; sobrescrita config `groq:b`; argumento `bedrock:c` | argumento → `c`; sem argumento → `b`; sem config → `a` |

## Perguntas em aberto

- P1. **Onde fica a "sobrescrita por config" do modelo?** Os docs dizem só "sobrescrevível por config". Proposta: seção opcional `prompt_models:` no `config/models.yaml` (`judge: "groq:openai/gpt-oss-120b"`), lida por `load_models_config` e validada contra o catálogo; mais o argumento `model=` em `run_prompt` para experimentos e Promptfoo (matriz prompt × modelo). Alternativas: variável de ambiente (`MIA_MODEL_<PROMPT>`), ou só o argumento por enquanto. → resposta: proposta aceita (seção `prompt_models:` + argumento `model=`). (15/11)
- P2. **Versão obrigatória ou "a mais recente"?** Proposta: `version` obrigatória em `load_prompt`; cada módulo (juiz, entrevistador…) declara a versão que usa. Assim criar `v2.yaml` não muda o comportamento em produção sem querer. Alternativa: `version=None` → maior `v<N>` da pasta. → resposta: proposta aceita (versão obrigatória). (15/11)
- P3. **`output_schema` aceita qualquer `BaseModel` de `schemas.py`?** Proposta: sim, qualquer classe `BaseModel` definida em `mia.schemas` (inclui `RunRecord`, que nunca seria usado, mas não vale uma lista fixa). Alternativa: lista fechada com os 6 schemas da tabela do TRD (`Screening`, `InterviewPlan`, `ToolDecision`, `AnswerScore`, `Report`, `CandidateSummary`). → resposta: proposta aceita (qualquer `BaseModel` definido em `mia.schemas`). (15/11)

## Notas de implementação

- Passo 1: teste visto falhando (`ModuleNotFoundError: mia.prompts`) antes do código. O YAML é validado por um modelo privado `_PromptFile` (só os campos do arquivo, `extra="forbid"`); `PromptSpec` herda dele e acrescenta `path`, preenchido pelo carregador. Assim o YAML não consegue definir `path` (nem `variables`, que chega no passo 2). Strings com `StrictStr`/`StrictInt`, para que `version: "1"` ou `model: 3` sejam erro em vez de conversão silenciosa. `model_validate(raw)` em vez de `**raw`: uma chave YAML que não é texto (`1: x`) vira `PromptError` em vez de `TypeError`. `output_schema` aceita só classes `BaseModel` definidas em `mia.schemas` (P3): `BaseModel` e `Literal`, importados lá, são recusados. `available_versions` aceita só `v<N>.yaml` sem zero à esquerda. A validação do modelo contra o catálogo (R9) fica para o passo 3. Fixtures válidas em `tests/fixtures/prompts/` (`demo` v1/v2, `free` v1); os casos inválidos são escritos em `tmp_path` pelos testes. Resultado: `uv run pytest` → 217 passed, cobertura 100%; `ruff check` limpo.
- Passo 2: teste visto falhando (`ImportError: render`) antes do código. `PromptSpec.variables` (frozenset) é preenchido pelo carregador a partir de `string.Formatter().parse`; só `{nome}` simples é aceito (sem `.`, `[ ]`, `!r`, `:fmt`, `{}` vazio). `render` confere tipos, faltantes e sobrantes e usa `format_map`, que não reinterpreta chaves dentro dos valores. `RenderedPrompt` criado. Resultado: 235 passed, cobertura 100%; `ruff check` limpo.
