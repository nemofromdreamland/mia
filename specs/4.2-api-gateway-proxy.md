# 4.2 — API Gateway HTTP API + Lambda proxy

Aprovação: modo autônomo pedido pelo dono.

## Contexto

A borda pública do MIA: o navegador chama um API Gateway HTTP API com throttling, que invoca a Lambda proxy da 3.11 (`proxy/handler.py`), que chama o AgentCore com a role `mia-proxy` criada na 4.1. Fontes: TRD ("Arquitetura", "Infraestrutura": linhas Borda pública e Proxy; "Observabilidade": retenção de 7 dias), Backend Schema ("API": 11 rotas, "Identificação"; "Erros e validação").

## Requisitos

- R1. QUANDO `python scripts/build_proxy.py` roda, O SISTEMA DEVE gerar `build/proxy.zip` com o pacote `proxy/` (sem `__pycache__`) e um `boto3`/`botocore` fixado na versão do `uv.lock` (1.44.3), que tem o serviço `bedrock-agentcore`.
- R2. O SISTEMA DEVE criar a Lambda `mia-proxy` (Python 3.12, arm64, handler `proxy.handler.lambda_handler`, timeout 30 s, 256 MB, role `mia-proxy`, env `AGENT_RUNTIME_ARN` de variável e `AGENT_RUNTIME_QUALIFIER=DEFAULT`) e o log group `/aws/lambda/mia-proxy` com retenção de 7 dias.
- R3. O SISTEMA DEVE criar o HTTP API `mia-api` com uma rota explícita para cada uma das 11 operações do Backend Schema, todas integradas à Lambda (payload 2.0); rota fora da lista → 404 do próprio API Gateway, sem invocar a Lambda.
- R4. O stage `$default` (auto-deploy) DEVE limitar a 5 req/s com burst 10.
- R5. CORS DEVE aceitar só as origens da variável `cors_allowed_origins` (o domínio do CloudFront, preenchido na 4.6), métodos `GET, POST, DELETE`, headers `content-type` e `x-visitor-id`; com a lista vazia, nenhum CORS é configurado.
- R6. QUANDO um `curl` com `X-Visitor-Id` válido chega à URL, a requisição DEVE chegar à proxy (log no CloudWatch); QUANDO o header falta, a resposta DEVE ser 422 `invalid_input` (não 400: desvio do texto da 4.2 para seguir o Backend Schema e a 3.11).

## Fora de escopo

- AgentCore Runtime e o ARN real (4.5): até lá, `agent_runtime_arn` fica vazio e uma chamada com header válido responde 500 `internal` genérico depois de chegar à proxy.
- Domínio do CloudFront (4.6), rota de voz (5.5), autenticação de usuário (não existe login), WAF.

## Design

**Arquivos**

| Arquivo | Ação | Conteúdo |
| --- | --- | --- |
| `scripts/build_proxy.py` | criar | monta `build/proxy.zip` (instala boto3 com `uv pip install --target`) |
| `tests/test_build_proxy.py` | criar | zip com instalador falso |
| `infra/lambda.tf` | criar | log group, `aws_lambda_function`, `aws_lambda_permission` |
| `infra/api.tf` | criar | `aws_apigatewayv2_api`, integração, 11 rotas (`for_each`), stage |
| `infra/variables.tf` | alterar | `agent_runtime_arn` (padrão `""`), `cors_allowed_origins` (padrão `[]`) |
| `infra/outputs.tf` | alterar | `api_url` |
| `tests/test_infra.py` | alterar | testes de R2–R5 |

**Interfaces**

```python
BOTO_VERSION: str  # "1.44.3"
def install_boto(target: Path) -> None: ...                      # uv pip install --target
def build_zip(dest: Path, install: Callable[[Path], None] = install_boto) -> Path: ...
def main() -> None: ...
```

**Decisões**

- Script em Python (roda no Windows do dono e no CI), não `.sh`; boto3 é Python puro, então o zip serve para arm64.
- Terraform lê `build/proxy.zip` com `source_code_hash = filebase64sha256(...)`: rodar o script antes de `plan`/`apply`.
- Rotas explícitas (e não `ANY /{proxy+}`): o API Gateway recusa rota desconhecida sem custo de Lambda.
- `throttling_*` no `default_route_settings` do stage. CORS por `dynamic` só quando há origem.
- Arquitetura arm64 (mais barata, mesma do container).

## Critérios de aceite

- [ ] `curl` com `X-Visitor-Id` chega no proxy — `curl -i -H "X-Visitor-Id: <uuid4>" <api_url>/cases` + log em `/aws/lambda/mia-proxy`
- [ ] Sem header → 422 `invalid_input` — `curl -i <api_url>/cases`
- [ ] Rota desconhecida → 404 sem invocar a Lambda — `curl -i <api_url>/nada`
- [ ] `apply` revisado pelo dono (resumo do plan antes)
- [ ] `uv run pytest` e `uv run ruff check .` passam
