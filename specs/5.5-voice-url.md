# 5.5 — URL assinada da entrevista por voz

## Contexto

O navegador não recebe credenciais AWS: ele pede ao proxy uma URL WebSocket SigV4 de curta duração. Esta tarefa adiciona `POST /sessions/{id}/voice-url`, autoriza a sessão pelo backend existente, assina `/ws` por 5 minutos com as credenciais temporárias da Lambda e vincula à assinatura o visitante, o endpoint `live` e a sessão isolada do AgentCore. A documentação oficial confirma `bedrock-agentcore:InvokeAgentRuntimeWithWebSocketStream`, custom headers na query e expiração máxima de 300 s.

## Requisitos

- R1. QUANDO recebe `POST /sessions/{id}/voice-url`, O SISTEMA DEVE validar `X-Visitor-Id` como UUID v4, obter o `session_id` somente da rota e ignorar qualquer identidade ou sessão enviada no corpo.
- R2. QUANDO autoriza a URL, O SISTEMA DEVE chamar a camada de serviço pelo contrato `/invocations` e confirmar que a sessão pertence ao visitante, tem modo `voice`, status `ready` ou `in_progress` e que o kill switch está aberto.
- R3. QUANDO a sessão não existe ou pertence a outro visitante, O SISTEMA DEVE responder `not_found` sem revelar sua existência; modo ou status incompatível deve responder `invalid_state`; demo fechada deve responder `demo_paused`.
- R4. QUANDO uma sessão existente pede URL de voz, O SISTEMA NÃO DEVE consumir novamente as cotas diária global ou do visitante, pois a unidade já foi consumida atomicamente em `create_session`; reconexões devem continuar possíveis dentro da mesma sessão.
- R5. QUANDO a autorização passa, O SISTEMA DEVE gerar um runtime session id determinístico `mia-voice-{session_id}`, com pelo menos 33 caracteres, e usá-lo tanto na autorização HTTP quanto na URL WebSocket para preservar isolamento e reconexão.
- R6. QUANDO assina a URL, O SISTEMA DEVE incluir antes da assinatura o ARN do runtime, qualifier do endpoint `live`, `/ws`, runtime session id e `X-Amzn-Bedrock-AgentCore-Runtime-Custom-X-Visitor-Id` com o visitante validado.
- R7. QUANDO o container recebe a conexão, O SISTEMA DEVE normalizar exclusivamente o custom header assinado para o header lógico `X-Visitor-Id` consumido pela 5.3; valores do corpo ou query não assinada nunca podem substituir a identidade.
- R8. QUANDO a URL é criada, O SISTEMA DEVE usar SigV4 para o serviço `bedrock-agentcore`, região configurada e credenciais temporárias da role da Lambda, com expiração exata de 300 s e sem chaves no código.
- R9. QUANDO responde com sucesso, O SISTEMA DEVE devolver somente `{url, expires_in: 300}`, status 200 e `Cache-Control: no-store`; URL, assinatura, token de sessão e `visitor_id` não podem aparecer em logs, erros ou métricas.
- R10. QUANDO ocorre falha de autorização, credenciais ou assinatura, O SISTEMA DEVE usar o envelope de erro existente, sem devolver ARN, query SigV4, exceção AWS ou detalhes internos.
- R11. QUANDO a infraestrutura é planejada, O SISTEMA DEVE adicionar a rota HTTP explícita, permitir à role da proxy somente `InvokeAgentRuntime` e `InvokeAgentRuntimeWithWebSocketStream` no runtime/endpoint da MIA e permitir no runtime somente o custom header de visitante.
- R12. QUANDO a política de recurso do runtime é avaliada, O SISTEMA DEVE permitir as duas ações apenas à role da proxy e negar outros principals, mantendo o acesso público autenticado somente por URLs assinadas por essa role.
- R13. QUANDO testes offline rodam, O SISTEMA DEVE usar repositório, AgentCore, credenciais e relógio falsos para verificar autorização, query assinada, expiração, IAM, redaction e respostas sem rede ou AWS.
- R14. QUANDO testado com conta AWS nova, O SISTEMA DEVE devolver uma URL que conecta o front ao `/ws`, entrega o visitante correto ao container, rejeita sessão alheia e expira após 5 minutos.
- R15. QUANDO uma nova imagem é implantada para o teste real, O SISTEMA DEVE encerrar sessões/microVMs antigas do AgentCore antes da evidência, evitando validar código anterior como ocorreu na 4.7a.

## Fora de escopo

- Implementar `/ws`, Sonic, ferramentas ou frontend (5.1–5.4).
- Expor credenciais AWS ao navegador, usar OAuth/Cognito ou criar API Gateway WebSocket.
- Consumir nova unidade de cota por reconexão, armazenar URLs ou manter uma tabela de tokens.
- Executar `terraform apply`, deploy, comandos AWS ou encerrar microVMs durante a escrita desta spec.

**Decisões**

- A Lambda não lê DynamoDB e não duplica regras: invoca `authorize_voice` no backend, que usa o repositório e o gate existentes.
- `ensure_open` verifica somente o kill switch. A cota pertence à criação da sessão; incrementá-la novamente impediria reconexões e cobraria duas unidades pela mesma simulação.
- O mesmo `mia-voice-{ULID}` é usado no `InvokeAgentRuntime` de autorização e no WebSocket, mantendo comprimento aceito, isolamento por entrevista e chance de reutilizar a microVM já aberta.
- O signer usa `botocore` já empacotado na Lambda e parâmetros adicionados antes do `SigV4QueryAuth`; não adiciona o pacote completo `bedrock-agentcore` ao zip de produção.
- O parâmetro oficial prefixado chega ao container como header `X-Amzn-Bedrock-AgentCore-Runtime-Custom-X-Visitor-Id`. A borda `/ws` o normaliza, valida e nunca aceita identidade do JSON.
- A resposta pode ser chamada novamente para reconexão, mas nunca é cacheada nem registrada. Throttling existente do API Gateway continua valendo.
- A policy da role e a resource policy listam explicitamente HTTP e WebSocket; ambas continuam restritas ao runtime e endpoint da MIA.

## Plano de testes

| Caso | Entrada | Esperado |
| --- | --- | --- |
| rota | POST correto + UUID/ULID | action `authorize_voice`; ids vêm de header/rota |
| identidade no corpo | `visitor_id`/`session_id` falsos | ignorados; valores canônicos prevalecem |
| dono | sessão do visitante | autorização válida, sem dados pessoais na resposta interna |
| sessão alheia/ausente | visitante diferente | `not_found`; signer não chamado |
| modo texto | sessão `text` | `invalid_state` |
| status | `ready`, `in_progress`, `completed` | dois primeiros passam; último falha |
| demo fechada | store falso fechado | `demo_paused`; signer não chamado |
| reconexão | duas URLs da mesma sessão | nenhum incremento de cota; mesmo runtime session id |
| runtime id | ULID de 26 caracteres | `mia-voice-<ULID>`, 36 caracteres |
| assinatura | credenciais/relógio falsos | `/ws`, qualifier, sessão e custom header aparecem antes de `X-Amz-Signature` |
| adulteração | trocar visitante após assinar | verificação SigV4 falsa falha |
| expiração | signer | `X-Amz-Expires=300`; valor maior é recusado |
| resposta | sucesso | `{url, expires_in: 300}`, status 200, `Cache-Control: no-store` |
| erro AWS | signer lança exceção com ARN/token | `internal` genérico; segredo ausente |
| header no runtime | query assinada simulada | `/ws` recebe identidade normalizada e validada |
| Terraform | arquivos estáticos | rota, allowlist, duas ações e recursos mínimos |
| produção | conta nova | front conecta; sessão alheia falha; URL vencida recebe 403 |

## Critérios de aceite

**Offline (não requer AWS)**

- [ ] Rota valida dono, modo, status e kill switch sem consumir nova cota — verificar com: `uv run pytest tests/test_service.py tests/test_proxy.py -v`
- [ ] URL falsa contém `/ws`, endpoint, sessão e visitante cobertos por SigV4 por exatamente 300 s — verificar com: `uv run pytest tests/test_proxy.py -v`
- [ ] Resposta é `no-store`; erros/logs não expõem URL, assinatura, ARN ou visitante — verificar com testes do proxy.
- [ ] Terraform declara rota, allowlist e permissões mínimas para HTTP + WebSocket — verificar com: `uv run pytest tests/test_infra.py -v && terraform -chdir=infra validate`
- [ ] `uv run pytest` passa
- [ ] `uv run ruff check .` passa

**Com AWS — depende de uma conta AWS nova**

- [ ] Front conecta em produção usando a URL SigV4 de 5 minutos.
- [ ] Custom header entrega o visitante correto; sessão alheia e URL adulterada/vencida são recusadas.
- [ ] Após encerrar microVMs antigas, conversa pelo navegador funciona e nenhuma URL/assinatura aparece nos logs.

## Perguntas em aberto

1. Está aprovada a correção da 5.3 para normalizar o header prefixado oficial do AgentCore, em vez de esperar literalmente `X-Visitor-Id` no container? → resposta: sim; a origem continua sendo exclusivamente o header assinado, nunca o corpo.
2. “Confere a cota” em Backend Schema significa consumir novamente ou comprovar que a sessão já passou pela cota? → resposta: comprovar pela sessão existente e não incrementar; reconexão não é nova simulação.
3. O signer de produção usa `botocore` mínimo ou empacota `bedrock-agentcore`? → resposta: `botocore`, já presente e testável; evita dependências de servidor/áudio no zip da Lambda.
4. A resposta deve incluir `expires_at` além de `expires_in`? → resposta: não; `expires_in: 300` evita dependência de relógios sincronizados e o front pede outra URL na reconexão.
5. O deploy real pode atualizar o runtime existente ou deve criar outro? → resposta: atualizar o existente, encerrar sessões antigas e verificar a versão antes do smoke.
