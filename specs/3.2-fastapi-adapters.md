# 3.2 — FastAPI: rotas REST, `/invocations` e `/ping`

## Contexto

A camada de serviço (3.1) tem as 11 operações; falta expô-las por HTTP. Esta tarefa cria os dois adaptadores finos do Backend Schema ("API"): rotas REST (o que o front chama) e o despachante `POST /invocations` por `action` (contrato do AgentCore Runtime), mais `GET /ping`, com um formato único de erro ("Erros e validação"). Fontes: `docs/BACKEND_SCHEMA.md` (API, Erros e validação), `docs/TRD.md` (Arquitetura, Estrutura do repositório: `src/mia/api/`).

## Requisitos

- R1. QUANDO o app for criado com `create_app(deps)`, O SISTEMA DEVE expor as 11 rotas REST da tabela "API" do Backend Schema, cada uma chamando a operação correspondente de `service.py` e devolvendo o modelo Pydantic dela serializado em JSON.
- R2. QUANDO `POST /sessions` der certo, O SISTEMA DEVE responder `201` com a `Session`; QUANDO `DELETE /sessions/{id}` der certo, `204` sem corpo; as demais, `200`.
- R3. QUANDO uma rota de visitante (todas menos `/cases`, `/recruiter/*`, `/ping`, `/invocations`) chegar sem `X-Visitor-Id` ou com valor que não é UUID v4, O SISTEMA DEVE responder `422` `invalid_input` sem chamar o serviço.
- R4. QUANDO o corpo trouxer `visitor_id` numa rota REST, O SISTEMA DEVE ignorá-lo; o visitante vem só do header.
- R5. QUANDO o serviço levantar `ServiceError(code, ...)`, O SISTEMA DEVE responder com o HTTP da tabela de erros (`not_found` 404, `invalid_input` 422, `invalid_state` 409, `session_limit` 409, `quota_exceeded` 429, `demo_paused` 503, `llm_invalid_output` 502, `provider_unavailable` 503, `internal` 500) e corpo `{"error": {"code", "message", "retryable"}}`.
- R6. QUANDO o corpo ou a query forem inválidos (ex.: `mode` fora de `text|voice`, `answer_text` ausente, JSON quebrado), O SISTEMA DEVE responder `422` `invalid_input` no formato único (não o formato padrão do FastAPI).
- R7. QUANDO qualquer outra exceção escapar, O SISTEMA DEVE responder `500` `internal`, `retryable: true`, com mensagem genérica (sem stack trace nem texto da exceção no corpo).
- R8. QUANDO `POST /invocations` receber `{action, visitor_id?, session_id?, payload?}` com `action` entre as 11 do Backend Schema, O SISTEMA DEVE chamar a mesma operação e devolver o mesmo status HTTP e o mesmo corpo da rota REST equivalente (inclusive erros).
- R9. QUANDO a `action` for desconhecida, faltar `session_id` numa action que precisa dele, ou o `payload` for inválido para a action, O SISTEMA DEVE responder `422` `invalid_input`.
- R10. QUANDO a action for de visitante e `visitor_id` estiver ausente ou não for UUID v4, O SISTEMA DEVE responder `422` `invalid_input`; actions do recrutador e `list_cases` não exigem `visitor_id`.
- R11. QUANDO `GET /ping` for chamado, O SISTEMA DEVE responder `200` `{"status": "Healthy"}` sem tocar no serviço.
- R12. QUANDO uma resposta do recrutador for serializada, O SISTEMA DEVE não conter a chave `visitor_id` em lugar nenhum do JSON.
- R13. QUANDO o mesmo cenário de teste rodar pela porta REST e pela porta `/invocations`, O SISTEMA DEVE produzir o mesmo status e o mesmo corpo ("Pronto quando").

## Fora de escopo

- WebSocket de voz (Fase 5) e URL assinada.
- Montar as dependências de produção (repositórios DynamoDB, `quotas.py`, LLM real) e o `main` do container: Fase 4 (4.5) e 3.4–3.8/3.10. Aqui o app recebe `ServiceDeps` pronto.
- CORS e throttling (ficam no API Gateway, 4.2); Lambda proxy (3.11).
- Mudanças no `service.py`: se algo faltar, paro e pergunto.

**Interfaces**

```python
# app.py
def create_app(deps: ServiceDeps) -> FastAPI: ...      # guarda deps em app.state.deps

# errors.py
HTTP_STATUS: dict[ErrorCode, int]
def error_body(code: ErrorCode, message: str, retryable: bool) -> dict[str, dict[str, object]]: ...
def service_error_response(err: ServiceError) -> JSONResponse: ...
def register_error_handlers(app: FastAPI) -> None: ...  # ServiceError, RequestValidationError, Exception

# visitor.py
def parse_visitor_id(value: str | None) -> str: ...    # UUID v4 canônico ou ServiceError("invalid_input")
def visitor_id_header(x_visitor_id: str | None = Header(default=None)) -> str: ...

# rest.py
class CreateSessionBody(BaseModel):   # extra="ignore" → visitor_id no corpo é descartado
    case_id: str
    mode: Mode
class AnswerBody(BaseModel):
    answer_text: str
router: APIRouter

# invocations.py
Action = Literal["list_cases", "create_session", "list_sessions", "get_session",
                 "start_interview", "send_answer", "end_interview", "get_report",
                 "delete_session", "list_recruiter_candidates", "get_recruiter_candidate"]
class InvocationRequest(BaseModel):
    action: str                       # validado na tabela, para dar invalid_input e não erro do Pydantic
    visitor_id: str | None = None
    session_id: str | None = None
    payload: dict[str, Any] = {}
def dispatch(deps: ServiceDeps, req: InvocationRequest) -> Response: ...
router: APIRouter
```

**Decisões**

- Adaptadores finos: nenhuma regra de negócio na API. Validação de estado, limites e 4.000 caracteres continuam no serviço.
- REST e `/invocations` montam a resposta por uma função comum (`(status, modelo) → Response`), para garantir R13 por construção; os testes provam.
- `/invocations` devolve o mesmo status da rota REST (201/204/4xx/5xx), para a Lambda proxy (3.11) só repassar (ver pergunta 1).
- `X-Visitor-Id`: validado com `uuid.UUID(value)` + `version == 4`; normalizado para minúsculas.
- Ausência do header é tratada por nós (não pelo `Header(...)` obrigatório do FastAPI) para sair `invalid_input` no formato único.
- `send_answer` com `{ended: true}`: devolve `AnswerResult` como está no serviço (`{"turn": null, "ended": true}`) — ver pergunta 2.
- `end_interview` devolve o `dict` do serviço (`{"status": ...}`).
- Dependências novas: `fastapi` (já previsto no TRD: "container FastAPI") e `httpx` só em dev (o `TestClient` exige). Nada de `uvicorn` agora.

## Plano de testes

`deps` com repositório/relatórios/contador em memória, `OpenGate`, decisor/escritor/scorer/relatório falsos (como em `test_service.py`). `V` = UUID v4 válido.

| Caso | Entrada | Esperado |
| --- | --- | --- |
| ping | `GET /ping` | 200 `{"status": "Healthy"}` |
| casos | `GET /cases` sem header | 200, lista de `CaseSummary` dos fixtures |
| criar | `POST /sessions` `{case_id: "<caso real>", mode: "text"}` + `V` | 201, `status == "ready"` |
| visitor_id no corpo | `POST /sessions` com `visitor_id: "outro"` no corpo + `V` | sessão gravada com `visitor_id == V` |
| sem header | `GET /sessions` sem `X-Visitor-Id` | 422 `invalid_input`, `retryable: false` |
| header inválido | `X-Visitor-Id: abc` / UUID v1 | 422 `invalid_input` |
| caso desconhecido | `POST /sessions` `{case_id: "x"}` | 422 `invalid_input` |
| mode inválido | `{mode: "video"}` | 422 `invalid_input` no formato único |
| JSON quebrado | corpo `"{"` | 422 `invalid_input` |
| fluxo feliz | criar → start → turns → end → report | 200 em cada; relatório com `is_above_case_avg` |
| sem vazamento | `GET /sessions/{id}` em `in_progress` | turnos sem `score`, `decision`, `is_follow_up` |
| outro visitante | `GET /sessions/{id}` com outro `V` | 404 `not_found` |
| estado errado | `POST /turns` em `ready` | 409 `invalid_state` |
| limite | sessão com 30 turnos | 409 `session_limit` |
| gate | gate falso que levanta `quota_exceeded` / `demo_paused` | 429 / 503 |
| LLM inválido | relatório falso que falha | 502 `llm_invalid_output`, `retryable: true` |
| inesperado | fake que levanta `RuntimeError("segredo")` | 500 `internal`, corpo sem "segredo" |
| apagar | `DELETE /sessions/{id}` | 204, corpo vazio |
| recrutador | 3 concluídas → `GET /recruiter/candidates` e detalhe | 200; `"visitor_id"` não aparece no texto do JSON |
| action desconhecida | `/invocations` `{action: "drop_table"}` | 422 `invalid_input` |
| sem session_id | `{action: "get_session", visitor_id: V}` | 422 `invalid_input` |
| sem visitor_id | `{action: "list_sessions"}` | 422; `{action: "list_cases"}` → 200 |
| payload inválido | `{action: "send_answer", ..., payload: {}}` | 422 `invalid_input` |
| **duas portas** | os casos acima marcados com fixture parametrizada `porta ∈ {rest, invocations}` | mesmo status e mesmo corpo nas duas |

## Perguntas em aberto

- P1. `/invocations` devolve o mesmo status HTTP da REST (201/204/4xx) ou sempre 200 com o erro só no corpo? Proposta: mesmo status, para a proxy só repassar. → resposta: mesmo status da REST (proxy só repassa; status HTTP correto é a boa prática).
- P2. Quando a entrevista acaba, o Backend Schema diz `{ended: true}`; o `AnswerResult` serializa `{"turn": null, "ended": true}`. Aceito assim, ou devo omitir `turn` quando for `null`? → resposta: manter `{"turn": null, "ended": true}` (formato estável, igual ao schema; o front checa `ended`).
- P3. Mover os fakes de `tests/test_service.py` para `tests/fakes_service.py` (reuso nos testes da API) é aceitável nesta tarefa, já que muda um arquivo de teste da 3.1? → resposta: sim, mover para `tests/fakes_service.py` sem mudar comportamento (evita duplicar fakes).
- P4. `ProviderUnavailable`: o serviço hoje não mapeia erro de provedor para `provider_unavailable` (cai em `internal` pelo handler genérico). Fica assim até a tarefa que trata o modelo reserva? → resposta: sim, fica `internal` (500, retryable); mapear no serviço está fora do escopo desta tarefa.
