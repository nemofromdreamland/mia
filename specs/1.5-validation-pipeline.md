# 1.5 — Pipeline de validação de saída estruturada + citações literais

## Contexto

Hoje `llm.invoke` devolve texto e grava `output_parsed`, `json_valid_first_try` e `repaired` como `None` ("structured output arrives in task 1.5"). Esta tarefa implementa os passos 1–3 e 6 do "Pipeline de validação de cada saída de LLM" (`docs/BACKEND_SCHEMA.md`, seção de erros): parse → 1 reparo → schema Pydantic → `llm_invalid_output`. E cria o util determinístico de citações literais (passo 4, parte "citações"), usado depois por triagem (`cv_quote`), juiz (`evidence_quotes`) e relatório (`answer_quote`). Regra do TRD: "o LLM redige; o código decide".

## Requisitos

- R1. QUANDO `invoke_structured` recebe do modelo um JSON que passa no `output_schema`, O SISTEMA DEVE devolver a instância do schema e gravar um `RunRecord` com `json_valid_first_try=True`, `repaired=False` e `output_parsed` = `model_dump(mode="json")` da instância.
- R2. QUANDO a primeira resposta não é JSON válido ou falha no schema, O SISTEMA DEVE fazer exatamente uma nova chamada ao modelo, reenviando as mensagens originais + a resposta inválida + a mensagem de erro (do `json` ou do Pydantic), e pedir só o JSON corrigido.
- R3. QUANDO a resposta do reparo passa no schema, O SISTEMA DEVE devolver a instância e gravar `json_valid_first_try=False`, `repaired=True`.
- R4. QUANDO a resposta do reparo também falha, O SISTEMA DEVE gravar `json_valid_first_try=False`, `repaired=False`, `output_parsed=None`, `error` com a descrição da falha, e levantar `LLMInvalidOutputError` (mapeado depois para o erro de API `llm_invalid_output`, 502).
- R5. QUANDO o provedor falha (exceção na chamada), O SISTEMA DEVE manter o comportamento atual de `invoke` (RunRecord com `error`, exceção propagada), sem tentar reparo.
- R6. QUANDO `invoke` (texto livre) é chamado, O SISTEMA DEVE continuar gravando `json_valid_first_try=None` e `repaired=None` (decisão da spec 0.5).
- R7. QUANDO `quote_in_source(quote, source)` recebe um trecho que existe no texto de origem, O SISTEMA DEVE devolver `True`; QUANDO o trecho não existe (inventado ou parafraseado), DEVE devolver `False`.
- R8. QUANDO o trecho é vazio ou só espaços, O SISTEMA DEVE devolver `False` (citação vazia não é evidência).
- R9. QUANDO `unverified_quotes(quotes, source)` recebe uma lista, O SISTEMA DEVE devolver, na ordem original, só as citações que não existem na origem.
- R10. `llm.py` continua sendo o único módulo que chama modelo; `checks.py` não importa SDK nem `llm.py`.

## Fora de escopo

- Demais checagens do passo 4 (`criteria_met` ⊂ `look_for`, competências existentes, resumo sem dados pessoais): entram com `judge.py`, `screening`/`plan` e `report_graph.py`.
- Preencher `quotes_verified` ou descartar itens (passo 5): cada módulo consumidor faz isso.
- Mudar `prompts.run_prompt` para usar a saída estruturada (ver P4).
- Modelo reserva / `provider_unavailable`, API HTTP e envio do caso para o dataset de regressão.
- `with_structured_output` / tool calling nativo do provedor (ver Decisões).

## Design

**Arquivos**

**Interfaces**

```python
# src/mia/checks.py
def normalize_for_quote(text: str) -> str: ...
def quote_in_source(quote: str, source: str) -> bool: ...
def unverified_quotes(quotes: Sequence[str], source: str) -> list[str]: ...

# src/mia/llm.py
T = TypeVar("T", bound=BaseModel)

class LLMInvalidOutputError(Exception):
    """Model output failed the schema even after one repair attempt."""

def parse_structured(raw: str, schema: type[T]) -> T:
    """json + Pydantic; raises ValueError (json) or ValidationError."""

def build_repair_messages(
    system: str, user: str, bad_output: str, error: str
) -> list[BaseMessage]: ...

def invoke_structured(
    *,
    output_schema: type[T],
    prompt_name: str,
    prompt_version: int,
    system: str,
    user: str,
    input: dict[str, Any],
    model: str | None = None,
    params: dict[str, Any] | None = None,
    experiment: str | None = None,
    session_id: str | None = None,
    config: ModelsConfig | None = None,
    runs_dir: Path = DEFAULT_RUNS_DIR,
    chat_model: BaseChatModel | None = None,
    on_record: RecordObserver | None = None,
) -> T: ...
```

**Decisões**

- Parse "à mão" (`json.loads` + `schema.model_validate`) em vez de `with_structured_output`: funciona igual nos 3 provedores, deixa medir `json_valid_first_try` de verdade (métrica do PRD) e mantém o texto bruto em `output_raw`.
- Mensagem de reparo: `[System(system), Human(user), AI(bad_output), Human(texto fixo pt-BR com o erro)]`. O erro do Pydantic vai resumido (`loc: msg`, reaproveita `_describe`). O texto fixo fica como constante em `llm.py` (não é prompt versionado; P3).
- Um `RunRecord` por `invoke_structured` (P1): tokens, custo e latência somam as duas chamadas; `output_raw` guarda a última resposta.
- Citações: normalização mínima e igual nos dois lados — Unicode NFC, aspas/apóstrofos tipográficos → retos, espaços em branco consecutivos → 1 espaço, `strip`. **Diferencia maiúsculas** e não ignora pontuação (P2). Assim, quebra de linha diferente não reprova citação, mas paráfrase reprova.
- Sem dependência nova.

## Plano de testes

| Caso | Entrada | Esperado |
| --- | --- | --- |
| citação exata | quote `"usei FastAPI"`, source `"Eu usei FastAPI no TCC."` | `True` |
| espaços/quebras | quote `"usei  FastAPI"`, source `"usei\nFastAPI"` | `True` |
| aspas tipográficas | quote `"o “cache”"`, source `'o "cache"'` | `True` |
| inventada | quote `"liderei 10 pessoas"`, source sem isso | `False` |
| paráfrase | quote `"utilizei FastAPI"`, source `"usei FastAPI"` | `False` |
| caixa diferente | quote `"fastapi"`, source `"FastAPI"` | `False` |
| vazia | quote `"  "` | `False` |
| lista | `["usei FastAPI", "inventado", "TCC"]` | `["inventado"]` |
| parse ok | `'{"...válido..."}'` + schema de teste | instância |
| parse com cercas | JSON válido dentro de bloco markdown json | instância (conta como válido de primeira, P4) |
| parse JSON quebrado | `'{"score": 4,'` | `ValueError` |
| parse schema errado | JSON com campo faltando | `ValidationError` |
| 1ª válida | fake devolve JSON válido | instância; record `True/False`, `output_parsed` preenchido, 1 chamada |
| reparo ok | fake: `"{quebrado"`, depois JSON válido | instância; record `False/True`; 2ª chamada recebeu 4 mensagens com a resposta ruim e o erro |
| reparo falha | fake: 2 respostas inválidas | `LLMInvalidOutputError`; record `False/False`, `output_parsed=None`, `error` preenchido; exatamente 2 chamadas |
| provedor cai | fake levanta exceção | exceção propagada, sem reparo, `error` no record |
| texto livre | `invoke` normal | flags continuam `None` |
| soma | 2 chamadas com tokens 10/5 e 20/7 | record com 30/12 e custo somado |
| arquitetura | varrer `src/mia/` | só `llm.py` importa SDK; `checks.py` não importa `llm` |

Os testes usam um schema pequeno definido no próprio teste (ou `AnswerScore`), modelo falso com respostas em fila e `RETRY_WAIT` zerado.

## Perguntas em aberto

- P1. O reparo é uma segunda chamada ao modelo. Gravar **um** `RunRecord` (somando tokens/custo, flags descrevem o par) ou **dois** (um por chamada, como diz "toda chamada grava um RunRecord")? Recomendo um: o docs define `json_valid_first_try`/`repaired` por registro, o que só faz sentido se o registro cobre as duas tentativas. → resposta: um RunRecord (recomendado, aprovado).
- P2. Comparação de citações: diferenciar maiúsculas/minúsculas e pontuação (proposta: sim, só normalizar espaços, NFC e aspas)? → resposta: sim, diferencia (aprovado).
- P3. O texto da mensagem de reparo fica como constante em `llm.py` ou vira prompt versionado (`prompts/repair/v1.yaml`)? Recomendo constante: não é prompt de experimento e não varia por tarefa. → resposta: constante em `llm.py` (aprovado).
- P4. Resposta envolta em cercas de markdown (```` ```json ... ``` ````), comum em Gemini/Groq: remover antes do parse e contar como "válido de primeira", ou tratar como inválido e deixar o reparo agir? Recomendo remover (determinístico) e contar como válido. → resposta: remover cercas e contar como válido de primeira (aprovado).
- P5. `prompts.run_prompt` deve passar a chamar `invoke_structured` quando o prompt tem `output_schema` já nesta tarefa, ou isso fica para a primeira tarefa consumidora (1.6+)? Proposta: fora de escopo. → resposta: fora de escopo (aprovado).

## Notas de implementação

- Passo 1: testes vistos falhando (`ModuleNotFoundError: mia.checks`) antes do código. Aspas tipográficas cobertas: “ ” „ viram aspas duplas retas e ‘ ’ ‚ viram apóstrofo reto. Testes extras além do plano: acento composto vs decomposto (NFC), apóstrofo curvo, diferença só de pontuação (reprova) e lista vazia. Suíte: 347 passed, cobertura 100%.
- Passo 2: testes vistos falhando (`ImportError: invoke_structured`) antes do código. `invoke` foi dividido em helpers privados (`_start`, `_base_record`, `_call`, `_write_success`) que `invoke_structured` reaproveita. Genéricos em sintaxe PEP 695 (`def f[T: BaseModel]`) em vez de `TypeVar`, porque o Ruff (UP047) exige no Python 3.12. Por ora, saída inválida só propaga o erro de parse (sem RunRecord); reparo e `LLMInvalidOutputError` vêm no passo 3. Suíte: 355 passed, cobertura 100%.
- Passo 3: testes vistos falhando (`ImportError: build_repair_messages`) antes do código. `_write_success` passou a receber `responses` (lista) e `error` opcional: soma tokens/custo das chamadas e grava `output_raw` da última; `invoke` passa lista de 1. Falha após o reparo grava 1 RunRecord com `error="LLMInvalidOutputError: ..."` e levanta a exceção. Se o provedor cair na chamada de reparo, `_call` grava o registro de erro (sem soma) e propaga. Suíte: 361 passed, cobertura 100%.
