# 1.1 — Schemas Pydantic do Backend Schema

## Contexto

Todo o MIA (saídas de LLM, DynamoDB, API, datasets de avaliação) passa por modelos Pydantic de `src/mia/schemas.py`; hoje só existe o `RunRecord` (spec 0.5). Esta tarefa cria os demais modelos exatamente como em `docs/BACKEND_SCHEMA.md` → "Schemas Pydantic" e "Execuções, prompts e datasets" (`GoldenItem`), com testes que cobrem os limites declarados (`ge`/`le`, `min_length`/`max_length`, `Literal`).

## Requisitos

- R1. QUANDO `schemas.py` for importado, O SISTEMA DEVE expor os aliases `Persona`, `Language`, `Mode`, `Level`, `SessionStatus` e `Phase` com exatamente os valores do Backend Schema.
- R2. QUANDO um campo `Literal` (persona, idioma, modo, nível, status, fase, `action`, `suggested_next_step`, `variant`, `split`) receber valor fora da lista, O SISTEMA DEVE levantar `ValidationError`.
- R3. QUANDO uma nota individual (`AnswerScore.score`, `GoldenItem.human_score`) for menor que 1 ou maior que 5, O SISTEMA DEVE levantar `ValidationError`; 1 e 5 DEVEM ser aceitos.
- R4. QUANDO uma nota agregada (`CompetencyScore.score`, `Report.overall_score`) estiver fora de [1.0, 5.0], O SISTEMA DEVE levantar `ValidationError`; 1.0, 5.0 e valores fracionários (ex.: 3.5) DEVEM ser aceitos.
- R5. QUANDO `Screening.fit_score` estiver fora de [0, 100] ou `InterviewPlan.estimated_minutes` fora de [5, 45], O SISTEMA DEVE levantar `ValidationError`; os extremos DEVEM ser aceitos.
- R6. QUANDO uma lista com limite tiver menos itens que o mínimo ou mais que o máximo, O SISTEMA DEVE levantar `ValidationError`: `Screening.strengths`/`concerns` (1–5), `Screening.competencies` (3–6), `Question.look_for` (3–4), `Question.follow_ups` (0–3), `InterviewPlan.questions` (4–12), `CandidateSummary.strengths`/`concerns` (1–3).
- R7. QUANDO uma lista sem limite declarado (`missing_keywords`, `criteria_met`, `evidence_quotes`, `Report.competencies`, `Report.strengths`, `Report.improvements`) vier vazia, O SISTEMA DEVE aceitá-la.
- R8. QUANDO um campo obrigatório faltar, O SISTEMA DEVE levantar `ValidationError`; QUANDO um campo com default for omitido, O SISTEMA DEVE usar o default do Backend Schema (ex.: `Case.language="pt-BR"`, `Turn.is_follow_up=False`, `Session.follow_ups_used=0`, `Session.competency_scores={}`).
- R9. QUANDO dois objetos `Session` forem criados sem `competency_scores`/`prompt_versions`, O SISTEMA DEVE dar a cada um seu próprio dicionário (alterar um não altera o outro).
- R10. QUANDO qualquer modelo válido for serializado com `model_dump_json()` e lido de volta com `model_validate_json()`, O SISTEMA DEVE devolver um objeto igual ao original (inclui `datetime` e modelos aninhados).
- R11. QUANDO um `PublicTurn` for serializado, O SISTEMA NÃO DEVE incluir `score`, `decision`, `is_follow_up` nem `session_id`.
- R12. QUANDO um `RecruiterCandidateRow` ou `CaseStats` for serializado, O SISTEMA NÃO DEVE incluir `visitor_id`.
- R13. QUANDO `CaseStats.average_score` ou `RecruiterCandidateRow.delta_vs_case_avg` for `None`, O SISTEMA DEVE aceitar.
- R14. O `RunRecord` existente DEVE continuar igual e seus testes DEVEM continuar passando.

## Fora de escopo

- Checagens cruzadas feitas pelo código (citação literal no CV/resposta, `criteria_met` ⊆ `look_for`, competência existente no `Screening`, resumo sem dado pessoal): ficam em `checks.py` (1.5), `judge.py` (1.8) e `report_graph.py` (1.9).
- Corpos de requisição/resposta da API (`{case_id, mode}`, `{answer_text}`, `{ended: true}`, formato de erro), eventos do WebSocket e cabeçalho `X-Visitor-Id`: Fase 3/5.
- Schema do arquivo de prompt (`prompts/<nome>/v<N>.yaml`): tarefa 1.2.
- Conjuntos B, C e D de avaliação (formato não definido no Backend Schema): Fase 2.
- Mapeamento para itens do DynamoDB.

**Decisões**

- Cópia fiel do Backend Schema: nenhum campo, limite ou validador a mais do que está lá. Única exceção: `CandidateSummary.headline` ganha `max_length=140` (P1), e o Backend Schema é atualizado junto.
- `Session.competency_scores` e `prompt_versions` usam `Field(default_factory=dict)` em vez de `= {}`: mesmo comportamento no Pydantic, mas deixa explícito que cada objeto tem seu dicionário (R9) e evita a dúvida do "default mutável" na revisão.
- `extra` fica no padrão do Pydantic (campos desconhecidos ignorados), diferente do `ModelSpec` da 0.5 (`forbid`), porque aqui a entrada vem do LLM; ver P2.
- `GoldenItem` entra nesta tarefa porque está no Backend Schema e só depende de `Question`; a 2.x só vai usá-lo.
- Sem dependências novas.

## Plano de testes

Base: cada fábrica `_<modelo>_fields()` devolve um dicionário válido; cada caso altera um campo.

| Caso | Entrada | Esperado |
| --- | --- | --- |
| aliases | `typing.get_args(Phase)` etc. | tuplas iguais às do Backend Schema (R1) |
| literal inválido | `Case(persona="ceo")`, `Session(status="done")`, `Question(phase="intro")`, `ToolDecision(action="skip")`, `CandidateSummary(suggested_next_step="hire")`, `GoldenItem(split="train")` | `ValidationError` (R2) |
| nota individual | `AnswerScore(score=0)`, `score=6`, `GoldenItem(human_score=0/6)` | `ValidationError` (R3) |
| nota individual extremos | `AnswerScore(score=1)`, `score=5` | aceito (R3) |
| nota agregada | `Report(overall_score=0.99)`, `5.01`; `CompetencyScore(score=0.5)` | `ValidationError` (R4) |
| nota agregada válida | `overall_score=1.0`, `3.5`, `5.0` | aceito (R4) |
| fit_score | `-1`, `101` → erro; `0`, `100` → aceito | R5 |
| estimated_minutes do plano | `4`, `46` → erro; `5`, `45` → aceito | R5 |
| listas vazias com mínimo | `Screening(strengths=[])`, `concerns=[]`; `CandidateSummary(strengths=[])` | `ValidationError` (R6) |
| listas acima do máximo | 6 `strengths` no `Screening`; 7 `competencies`; 5 `look_for`; 4 `follow_ups`; 13 `questions`; 4 `strengths` no `CandidateSummary` | `ValidationError` (R6) |
| listas abaixo do mínimo | 2 `competencies`; 2 `look_for`; 3 `questions` | `ValidationError` (R6) |
| listas nos extremos | 3 e 6 `competencies`; 3 e 4 `look_for`; 0 e 3 `follow_ups`; 4 e 12 `questions` | aceito (R6) |
| listas vazias sem limite | `Screening(missing_keywords=[])`, `AnswerScore(criteria_met=[], evidence_quotes=[])`, `Report(competencies=[], strengths=[], improvements=[])` | aceito (R7) |
| obrigatório faltando | `Turn` sem `created_at`; `Evidence` sem `cv_quote`; `Session` sem `visitor_id` | `ValidationError` (R8) |
| defaults | `Case` sem `language`; `Turn` mínimo; `Session` mínimo; `AnswerScore` sem `quotes_verified`; `Question` sem `targets_concern` | `"pt-BR"`; `is_follow_up=False`, `answer_text/decision/score=None`; `follow_ups_used=0`, `turn_count=0`, dicts vazios; `None`; `None` (R8) |
| dict isolado | duas `Session`; `a.competency_scores["x"]=1.0` | `b.competency_scores == {}` (R9) |
| ida e volta | `Screening`, `InterviewPlan` (com `Question`), `Turn` com `ToolDecision` e `AnswerScore`, `Report`, `CandidateSummary`, `Session`, `GoldenItem` | `model_validate_json(x.model_dump_json()) == x` (R10) |
| PublicTurn | `PublicTurn(**campos).model_dump()` | chaves = `{turn_no, question_id, interviewer_text, answer_text, created_at}` (R11) |
| recrutador | `RecruiterCandidateRow` e `CaseStats` válidos | `"visitor_id"` ausente do dump (R12) |
| headline (P1) | `CandidateSummary(headline="a"*141)`; `"a"*140` | `ValidationError`; aceito |
| médias nulas | `CaseStats(average_score=None)`, `RecruiterCandidateRow(delta_vs_case_avg=None)` | aceito (R13) |
| RunRecord | testes atuais | passam sem alteração (R14) |

## Perguntas em aberto

- P1. `CandidateSummary.headline` tem o comentário "uma frase, até 140 caracteres". Viro isso em `Field(max_length=140)` (o modelo que passar disso cai no reparo) ou deixo só no prompt e no comentário? → resposta: `Field(max_length=140)` (limite já declarado no doc; a lista do recrutador depende dele). No passo 3, o comentário do `BACKEND_SCHEMA.md` vira o `Field`. (Recomendação do agente, autorizada pelo usuário em 15/11.)
- P2. Campos extras vindos do LLM: ignorar (padrão do Pydantic, proposta) ou rejeitar com `extra="forbid"` (mais rígido, mais reparos)? → resposta: ignorar (padrão do Pydantic).
- P3. "`follow_up_text` presente quando a ação é `follow_up`" está na lista de validações do código. Faço como `model_validator` no `ToolDecision` agora (vira erro de schema e passa pelo reparo) ou deixo para o `interviewer.py` (1.7)? Proposta: deixar para a 1.7, para manter a cópia fiel. → resposta: fica para a 1.7.
- P4. Os inteiros sem limite no Backend Schema (`Case.estimated_minutes`, `Turn.turn_no`, `Session.turn_count`, `completed_sessions`, `candidate_no`, `latency_ms`) ficam sem `ge=0`/`ge=1`? Proposta: sim, sem limite, para não inventar regra. → resposta: sem limite.
- P5. `GoldenItem` entra aqui (proposta) ou fica para a Fase 2? → resposta: entra aqui (passo 3).
