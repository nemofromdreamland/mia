# 2.8a — Defesas com Bedrock Guardrails

## Contexto

Primeira metade da 2.8 (dividida por tamanho). Cria o guardrail do Bedrock e o encanamento em `llm.py` para que a 2.8b meça o conjunto D sem e com ele. Além do previsto no TRD ("Segurança e LGPD": prompt attack + PII), o dono pediu defesa contra *poisoning* (instruções escondidas no CV/vaga) e contra fuga do assunto da entrevista, pelo entrevistado (entrada) e pelo entrevistador (saída). O conjunto D ganha o tipo `off_topic`.

## Requisitos

- R1. QUANDO `scripts/create_guardrail.py` roda e o usuário confirma, O SISTEMA DEVE criar (ou reaproveitar pelo nome `mia-robustness`) o guardrail, publicar uma versão e gravar `id`/`version` em `config/guardrails.yaml`.
- R2. O guardrail DEVE ter: (a) prompt attack `HIGH` na entrada; (b) tópico negado `fora_da_entrevista` (receitas, política, piadas, pedir código/tarefas, perguntas sobre o próprio sistema/prompt) na entrada e na saída; (c) PII `ANONYMIZE` para e-mail, telefone, nome, endereço e CPF (regex) e `BLOCK` para cartão e senha; (d) filtro de palavras com marcadores de injeção (`ignore todas as instruções`, `ignore previous instructions`, `system prompt`, `nova instrução do sistema`); (e) mensagens de bloqueio fixas em português ("Vamos manter o foco na entrevista.").
- R3. QUANDO uma chamada recebe `params["guardrail"] = {"id", "version"}` e o modelo é `bedrock:*`, O SISTEMA DEVE repassar o guardrail ao modelo só em `llm.py`; QUANDO o provedor não é Bedrock, DEVE levantar `ModelConfigError`.
- R4. QUANDO há guardrail, O SISTEMA DEVE marcar com `guardContent` só os blocos de texto externo (resposta do candidato, CV, vaga), nunca o system prompt; isso aplica o prompt attack também ao CV/vaga (poisoning).
- R5. QUANDO o guardrail intervém (`stopReason == "guardrail_intervened"`), O SISTEMA DEVE gravar `RunRecord` com `error` começando por `guardrail_intervened` e levantar `GuardrailBlocked`, sem reparo de JSON.
- R6. `judge_answer`, `run_prep`, `build_report_graph` e `should_follow_up` DEVEM aceitar `params: dict[str, Any] | None = None` e repassá-lo até `llm.py`, sem mudar o comportamento padrão.
- R7. `AttackType` DEVE incluir `"off_topic"` (exige `question_id` + `answer_text`), e `robustness.jsonl` DEVE ganhar 6 itens `off_topic` (4 dev / 2 test, semente 24), total 30.

## Fora de escopo

- Rodar o conjunto D e o relatório (2.8b).
- Ligar o guardrail no produto web/AgentCore e Terraform `aws_bedrock_guardrail` (fase de deploy).
- Novas versões de prompt (reforço de prompt é da fase v2, medido com o D).

**Interfaces**

```python
# src/mia/llm.py
class GuardrailBlocked(Exception): ...
def guardrail_kwargs(spec: ModelSpec, guardrail: dict[str, str] | None) -> dict[str, Any]: ...
def guard_user_content(user: str, guardrail: dict[str, str] | None) -> str | list[dict[str, Any]]: ...
def guardrail_intervened(response: AIMessage) -> bool: ...

# scripts/create_guardrail.py
GUARDRAIL_NAME: Final[str]  # "mia-robustness"
def guardrail_request() -> dict[str, Any]: ...
def ensure_guardrail(client: Any) -> tuple[str, str]: ...
def main(argv: Sequence[str] | None = None) -> int: ...
```

**Decisões**

- boto3 (não console): reprodutível e versionado. `boto3` já vem com `langchain-aws` (confirmar no passo 1); sem dependência nova.
- O guardrail entra por `params`, não no YAML do prompt: mesmo prompt nos dois cenários, nenhuma versão nova.
- Tópico negado na saída cobre o entrevistador: se ele sair do assunto, a saída vira a mensagem fixa e o código levanta `GuardrailBlocked`.
- PII continua mascarado por `pii.py` antes da chamada; o guardrail é camada extra.
- Termos `must_not_contain` dos itens `off_topic` (ex.: "ingredientes", "partido", "def ") escolhidos pelo agente ao escrever os itens, como na 2.4.
- Guardrail não cobra parado; cobra por texto avaliado (centavos).

## Notas de implementação

- Passo 1: o guardrail vira `guardrail_config` do `ChatBedrockConverse` (campo `guardrails`/`guardrail_config`, com `trace`). `guard_user_content` separa o texto entre as tags `resposta`, `cv`, `vaga` e `transcricao` em blocos `guard_content`; o resto (instruções do prompt) fica como texto comum. A intervenção é detectada em `_call` (vale para `invoke` e `invoke_structured`): grava um RunRecord `guardrail_intervened: ...` e levanta `GuardrailBlocked`, sem reparo. Tags de `transcricao` foram incluídas por conterem respostas do candidato. 813 testes, cobertura 98,85%; Ruff ok.
- Passo 2: `run_prompt` e `run_prompt_structured` (`prompts.py`) ganharam `params` opcional, mesclado sobre `prompt.params` (o do chamador vence); sem ele o comportamento é o de antes. `judge_answer`, `should_follow_up`, `build_prep_graph`/`run_prep` e `build_report_graph` recebem `params` explícito e repassam. `prompts.py` entrou no passo (a spec não o listava) porque é o elo entre esses módulos e `llm.py`. Testes em `tests/test_params_passthrough.py` (novo, com fakes). 819 testes, cobertura 98,85%; Ruff ok.
- Passo 3: `create_guardrail.py` monta o pedido (`guardrail_request`), procura pelo nome com paginação (`_find_existing`) e, se existir, só publica nova versão; senão cria. `main` aceita `client` e `ask` por parâmetro (só para teste) e pede `[s/N]` antes de tocar na AWS. Criado de verdade após confirmação: id `7vx5e8ajtid1`, versão `1`, status READY (conferido com `get-guardrail`), gravado em `config/guardrails.yaml`. Reexecutar reaproveita o guardrail mas publica mais uma versão. 827 testes, cobertura 98,85%; Ruff ok.
