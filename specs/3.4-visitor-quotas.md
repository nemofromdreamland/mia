# 3.4 — Visitante anônimo, cotas diárias e kill switch

## Contexto

A demo é pública e sem login; o custo precisa de teto. A 3.1 deixou o `SessionGate` com um `OpenGate` provisório e o `CandidateCounter` só em memória; a 3.2 já valida o `X-Visitor-Id` em `api/visitor.py`. Esta tarefa cria `quotas.py` (kill switch + cota global + cota por visitante) com armazenamento em `mia-meta` (memória e DynamoDB) e o contador de candidatos em DynamoDB (P2 da 3.3). Fontes: `BACKEND_SCHEMA.md` → tabela `mia-meta`, "Padrões de acesso", "Regras", "Identificação", tabela de erros; `TRD.md` → módulo `quotas.py`, decisão "Identificação", riscos "Abuso da demo".

## Requisitos

- R1. QUANDO o `X-Visitor-Id` está ausente, não é UUID v4 ou não está na forma canônica, O SISTEMA DEVE responder `invalid_input` (422) sem chamar o serviço. (já implementado na 3.2; aqui só se confirma com teste de ponta a ponta)
- R2. QUANDO o corpo de `POST /sessions` ou o `payload` do `/invocations` traz `visitor_id`, O SISTEMA DEVE ignorá-lo e usar só o header/envelope validado.
- R3. QUANDO o item `config`/`demo` de `mia-meta` tem `open = false`, O SISTEMA DEVE recusar `create_session` com `demo_paused` (503, não retentável) sem tocar em nenhuma cota.
- R4. QUANDO a demo está aberta e o contador `quota#global`/`<dia UTC>` já está em 100, O SISTEMA DEVE recusar com `quota_exceeded` (429, não retentável).
- R5. QUANDO a cota global permite e o contador `quota#visitor#<visitor_id>`/`<dia UTC>` já está em 5, O SISTEMA DEVE recusar com `quota_exceeded` e devolver a unidade somada à cota global.
- R6. QUANDO a checagem passa, O SISTEMA DEVE somar 1 aos dois contadores do dia de forma atômica (`UpdateItem` com `ADD count 1` e condição `count < limite`), gravando `expires_at` = início do dia + 2 dias (epoch, segundos).
- R7. QUANDO o dia UTC muda, O SISTEMA DEVE começar contadores novos (a chave `sk` é a data `YYYY-MM-DD` do `clock` injetado).
- R8. QUANDO o mesmo visitante cria 6 sessões no mesmo dia pela API, O SISTEMA DEVE criar as 5 primeiras (201) e recusar a 6ª com `quota_exceeded`.
- R9. QUANDO `DynamoCandidateCounter.next(case_id)` é chamado, O SISTEMA DEVE fazer `UpdateItem` em `counter#case#<case_id>`/`candidate_no` com `ADD value 1` e `ReturnValues=UPDATED_NEW`, devolvendo 1, 2, 3… sem repetição por caso.
- R10. QUANDO o DynamoDB falha com erro que não é de condição, O SISTEMA DEVE levantar `RepositoryError` (vira `internal` na API).
- R11. As implementações em memória e DynamoDB do armazenamento de `mia-meta` DEVEM passar no mesmo conjunto de testes de contrato.

## Fora de escopo

- `create_session` copiando triagem/plano e `candidate_no` ponta a ponta (3.5).
- Cota na URL de voz (`voice-url`, 3.x de voz) e throttling do API Gateway (infra, 4.x).
- Criar a tabela `mia-meta` na AWS (Terraform, 4.1) e um comando para ligar/desligar a demo.
- Limites de 30 turnos e 45 minutos por sessão.

**Interfaces**

```python
# quotas.py
GLOBAL_DAILY_LIMIT = 100
VISITOR_DAILY_LIMIT = 5
QUOTA_TTL_DAYS = 2

class MetaStore(Protocol):
    def is_demo_open(self) -> bool: ...
    def try_increment(self, pk: str, sk: str, limit: int, expires_at: int) -> bool: ...
        # True se somou; False se já estava no limite
    def decrement(self, pk: str, sk: str) -> None: ...   # compensação (R5)

class InMemoryMetaStore:                                  # satisfaz MetaStore
    def __init__(self, demo_open: bool = True) -> None: ...
    def set_demo_open(self, value: bool) -> None: ...     # apoio a testes

def global_key() -> str: ...                              # "quota#global"
def visitor_key(visitor_id: str) -> str: ...              # "quota#visitor#<id>"

class QuotaGate:                                          # satisfaz SessionGate
    def __init__(self, store: MetaStore, clock: Clock,
                 global_limit: int = GLOBAL_DAILY_LIMIT,
                 visitor_limit: int = VISITOR_DAILY_LIMIT) -> None: ...
    def check(self, visitor_id: str) -> None: ...         # ServiceError demo_paused / quota_exceeded

# repo_dynamo.py
META_TABLE = "mia-meta"
class DynamoMetaStore:                                    # satisfaz MetaStore
    def __init__(self, table: Any) -> None: ...
    @classmethod
    def from_env(cls, *, region: str = "us-east-1", table: str = META_TABLE) -> "DynamoMetaStore": ...
class DynamoCandidateCounter:                             # satisfaz CandidateCounter
    def __init__(self, table: Any) -> None: ...
    def next(self, case_id: str) -> int: ...
```

**Decisões**

- Ordem fixa do `BACKEND_SCHEMA`: demo aberta → cota global → cota do visitante. `QuotaGate` só decide; `MetaStore` só guarda (o código decide, o armazenamento é burro).
- "`config/demo.open`" = item `pk=config`, `sk=demo`, atributo `open` de `mia-meta` (é o que a tabela do schema descreve), não um arquivo no repositório. Ver P1.
- Atomicidade: cada contador usa `UpdateItem` condicionado (`attribute_not_exists(#count) OR #count < :limit`); `ConditionalCheckFailedException` → `False`. Se a global soma e a do visitante recusa, `decrement` devolve a unidade da global (P2).
- Dia = `clock().date()` em UTC; `expires_at` = meia-noite UTC do dia + 2 dias, em epoch.
- Mesma tabela, mesmo padrão da 3.3: tabela injetada no construtor, `from_env` para produção, `ClientError` não condicional → `RepositoryError`.
- Sem dependências novas (`boto3` e `moto` vieram na 3.3).

## Plano de testes

| Caso | Entrada | Esperado |
| --- | --- | --- |
| demo fechada | store `demo_open=False`, `check(v)` | `ServiceError("demo_paused")`, contadores intactos |
| primeira sessão | store vazio, `check(v)` | ok; global=1, visitante=1, `expires_at` = dia+2 |
| 6ª do visitante | 5 `check(v)` antes | 6ª → `quota_exceeded`; global continua 5 (compensado) |
| global esgotada | global=100, visitante novo | `quota_exceeded`; contador do visitante não criado |
| visitantes diferentes | v1 ×5, v2 ×1 | todos passam |
| virada do dia | 5 `check(v)` no dia D, clock → D+1 | passa; `sk` novo |
| contrato store | memória e moto: `try_increment` até o limite | `True`×N, depois `False`; `decrement` volta 1 |
| config ausente | moto sem item `config/demo` | `is_demo_open()` segue P1 |
| erro Dynamo | tabela inexistente / `ClientError` genérico | `RepositoryError` |
| contador | `next("c1")`×3, `next("c2")` | 1, 2, 3; 1 |
| API header | `POST /sessions` sem header / UUID v1 / `abc` | 422 `invalid_input` |
| API corpo | header v1 válido + `visitor_id` de v2 no corpo | sessão listada só para v1 |
| API 6 sessões | 6× `POST /sessions` mesmo header | 5×201, 6ª 429 `quota_exceeded`, `retryable=false` |
| API pausada | store fechado | 503 `demo_paused`; `/invocations create_session` igual |

## Perguntas em aberto

- P1. Se o item `config/demo` não existir em `mia-meta`, a demo está aberta ou fechada? Proposta: **aberta** (o schema diz "`false` pausa"; evita ter de semear a tabela no deploy). Alternativa mais segura em custo: fechada até alguém ligar. → resposta: aberta (aprovado).
- P2. Quando a global soma e a do visitante recusa: compensar com `decrement` na global (proposta, simples) ou fazer as duas somas numa `TransactWriteItems` (atômico de verdade, mas mais complexo e precisa ler `CancellationReasons`)? → resposta: `decrement` na global (aprovado).
- P3. A CLI (`visitor_id = "local"`) continua com `OpenGate`, sem cota? Proposta: sim; o `QuotaGate` só é ligado na montagem da web (3.x/4.x). → resposta: sim, CLI com `OpenGate` (aprovado).
- P4. Se a criação da sessão falhar depois do gate (ex.: erro no repositório), a cota fica consumida. Aceitável na demo? Proposta: sim, sem compensação. → resposta: sim, sem compensação (aprovado).
