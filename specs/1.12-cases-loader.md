# 1.12 — Fixtures dos casos, loader e `mia simulate --case`

## Contexto

Na web, a triagem e o plano vêm de fixtures prontas em `cases/`, sem chamar modelo (AGENTS.md; `docs/CASES.md` → "Como as fixtures são geradas"; `docs/TRD.md` → módulo `cases.py`, linha 50). Esta tarefa gera `screening.json` e `plan.json` dos 5 casos da 1.11 com o `prep_graph` (1.6), cria o loader que a API da Fase 3 vai usar e liga a CLI (1.10) aos casos.

## Requisitos

Loader (`src/mia/cases.py`):

- R1. QUANDO `load_case(case_id)` é chamado com um caso existente e completo, O SISTEMA DEVE devolver `LoadedCase` com `Case`, `Screening` e `InterviewPlan` validados pelos schemas de `schemas.py`, sem chamar modelo.
- R2. QUANDO o `case_id` não segue o formato `^[a-z0-9]+(-[a-z0-9]+)*$` ou a pasta não existe, O SISTEMA DEVE levantar `CaseNotFoundError` (impede `../` e caminhos arbitrários).
- R3. QUANDO falta `screening.json` ou `plan.json`, ou um arquivo não valida no schema, O SISTEMA DEVE levantar `CaseError` com o `case_id` e o nome do arquivo na mensagem.
- R4. QUANDO o `case_id` dentro do `case.yaml` difere do nome da pasta, O SISTEMA DEVE levantar `CaseError`.
- R5. QUANDO o plano não passa em `check_plan_coverage(screening, plan, case.persona)`, O SISTEMA DEVE levantar `CaseError` listando os problemas (o código decide, fixture inconsistente não entra).
- R6. QUANDO `list_cases()` é chamado, O SISTEMA DEVE devolver os `Case` de todas as pastas com `case.yaml`, ordenados por `case_id`, lendo só os metadados.
- R7. QUANDO `load_case_texts(case_id)` é chamado, O SISTEMA DEVE devolver `(cv_text, job_text)` lidos de `cv.md` e `job.md` (usado só pelo script de build).

Script (`scripts/build_cases.py`):

- R8. QUANDO o script roda sem argumentos, O SISTEMA DEVE rodar `run_prep` em cada um dos 5 casos (CV = `cv.md`, vaga = `job.md`, `persona`, `level`, `estimated_minutes`, `language` do `case.yaml`) e gravar `screening.json` e `plan.json` na pasta do caso (UTF-8, `indent=2`, `ensure_ascii=False`).
- R9. QUANDO recebe `--case <id>` (repetível), O SISTEMA DEVE processar só esses casos.
- R10. QUANDO o prep de um caso falha (`PrepError`, `PrepValidationError`, `LLMInvalidOutputError`), O SISTEMA DEVE não gravar nada daquele caso, avisar no stderr, seguir para os próximos e terminar com saída 1; sucesso em todos → saída 0; `ModelConfigError` → saída 2.
- R11. QUANDO termina, O SISTEMA DEVE lembrar no stdout de revisar os JSON e subir `version` no `case.yaml` se cv, vaga ou plano mudaram (o script não altera `version` sozinho).

CLI:

- R12. QUANDO `mia simulate --case <id>` é usado, O SISTEMA DEVE carregar o caso com `load_case`, criar a sessão direto em `ready` com `case_id`, `case_version`, `persona` e `language` do caso e `job_title = case.title`, e seguir a entrevista com o plano da fixture, sem chamar o `prep`.
- R13. QUANDO `--case` é combinado com `--cv`/`--job`, ou nenhum dos dois modos é informado, O SISTEMA DEVE sair com código 2 (erro do argparse). `--cv` e `--job` continuam obrigatórios juntos no modo avulso; `--persona` passa a ser obrigatório só no modo avulso.
- R14. QUANDO o caso não existe ou é inválido, O SISTEMA DEVE escrever a mensagem no stderr e sair com código 1, antes de montar dependências de modelo.

Fixtures:

- R15. QUANDO a tarefa termina, os 5 casos DEVEM ter `screening.json` e `plan.json` commitados, revisados pelo dono, e todos carregarem com `load_case` num teste que roda na suíte normal.

## Fora de escopo

- API `GET /cases` e `create_session` com `case_id` (Fase 3); `CaseSummary` não é montado aqui.
- Cotas, kill switch, `visitor_id` (só web).
- Conjunto C de avaliação e golden set.
- Mudar prompts de triagem/planner (se a rodada real falhar, é nova tarefa ou passo corretivo aprovado).
- Reconferir citações da triagem no loader (já checadas pelo `prep_graph` contra o CV mascarado na geração).

## Design

**Arquivos**

| Arquivo | Ação | Conteúdo |
| --- | --- | --- |
| `src/mia/cases.py` | criar | erros, `LoadedCase`, `list_cases`, `load_case`, `load_case_texts`, `write_fixtures` |
| `scripts/build_cases.py` | criar | `argparse`, laço sobre os casos, chama `run_prep` (injetável) |
| `src/mia/simulation.py` | alterar | `start_from_case` (sessão `ready` a partir do caso) |
| `src/mia/cli.py` | alterar | `--case`, grupo de modos, ramo que pula o prep |
| `tests/test_cases.py`, `tests/test_build_cases.py` | criar | loader com pasta temporária; script com prep falso |
| `tests/test_simulation.py`, `tests/test_cli.py` | alterar | modo caso |
| `cases/<id>/screening.json`, `plan.json` (×5) | criar | gerados pela rodada real |

**Interfaces**

```python
# src/mia/cases.py
CASES_DIR: Final[Path]                    # <raiz do repo>/cases

class CaseError(Exception): ...
class CaseNotFoundError(CaseError): ...

class LoadedCase(BaseModel):
    case: Case
    screening: Screening
    plan: InterviewPlan

def list_cases(cases_dir: Path = CASES_DIR) -> list[Case]: ...                 # R6
def load_case(case_id: str, cases_dir: Path = CASES_DIR) -> LoadedCase: ...    # R1–R5
def load_case_texts(case_id: str, cases_dir: Path = CASES_DIR) -> tuple[str, str]: ...  # R7
def write_fixtures(case_id: str, result: PrepResult, cases_dir: Path = CASES_DIR) -> None: ...  # R8

# scripts/build_cases.py
def build_one(case: Case, cases_dir: Path, prep: Callable[[PrepInput], PrepResult]) -> None: ...
def main(argv: Sequence[str] | None = None,
         prep: Callable[[PrepInput], PrepResult] | None = None) -> int: ...      # R8–R11

# src/mia/simulation.py
def start_from_case(deps: SimulationDeps, loaded: LoadedCase) -> Session: ...   # R12
```

**Decisões**

- **`PrepInput` recebe `cv_path`** (a 1.6 extrai o texto do arquivo): o script passa `cases/<id>/cv.md` direto; `load_case_texts` serve só para ler a vaga e para testes.
- **Validação no loader:** schema + `check_plan_coverage` + `case_id` igual à pasta. É barato e roda no boot da API; fixture quebrada falha cedo.
- **Escrita atômica por caso:** `write_fixtures` só é chamado depois do `run_prep` dar certo, e grava os dois arquivos; nada parcial (R10).
- **`version` manual:** o docs diz "suba `version`"; o script só lembra (R11). Decidir quando subir é do dono.
- **`start_from_case`** cria a `Session` já `ready` (como a web fará), reaproveitando `begin`/`reply`/`finish` sem mudança.
- **CLI:** grupo mutuamente exclusivo `--case` × `--cv`; a checagem "`--cv` exige `--job` e `--persona`" é feita depois do parse com `parser.error` (saída 2).
- **Modelo do build:** `run_prep` usa o modelo do prompt/`models.yaml`; o script aceita `--model` opcional repassado a `run_prep` (ver P1).
- Sem dependências novas.

## Plano de testes

| Caso | Entrada | Esperado |
| --- | --- | --- |
| feliz | pasta tmp com `case.yaml` + `screening_ok.json` + `plan_ok.json` (fixtures da 1.6) | `LoadedCase` com os 3 objetos; `chat_model` nunca tocado |
| id inválido | `load_case("../etc")`, `load_case("Prompt")` | `CaseNotFoundError` |
| pasta ausente | `load_case("nao-existe")` | `CaseNotFoundError` |
| sem plano | pasta sem `plan.json` | `CaseError` com `"plan.json"` na mensagem |
| JSON inválido | `screening.json` com `fit_score: 200` | `CaseError` com `"screening.json"` |
| id divergente | pasta `a-b`, yaml `case_id: x-y` | `CaseError` |
| cobertura | plano sem pergunta para um `concern` | `CaseError` com o problema |
| list | 2 pastas (`b`, `a`) + pasta sem yaml | `[a, b]` |
| texts | caso com `cv.md`/`job.md` | tupla com os textos |
| build feliz | prep falso devolvendo `PrepResult` ok, `--case prompt-engineer-jr` em tmp | 2 JSON gravados, recarregáveis com `load_case`; saída 0 |
| build falha | prep falso levanta `PrepValidationError` no 1º de 2 casos | nada gravado no 1º, 2º gravado, saída 1 |
| build config | prep levanta `ModelConfigError` | saída 2 |
| build lê caso | prep falso captura `PrepInput` | `persona`/`level`/`estimated_minutes` do yaml, `cv_path` termina em `cv.md` |
| sim caso | `start_from_case` com relógio fixo | sessão `ready`, `case_id`, `case_version`, `job_title`; `deps.prep` nunca chamado |
| cli caso | `--case prompt-engineer-jr` com deps falsas, stdin `/fim` | saída 0, JSON do relatório no stdout, prep não chamado |
| cli conflito | `--case x --cv a.md --job b.md` / nada | saída 2 |
| cli avulso sem persona | `--cv a --job b` | saída 2 |
| cli caso ausente | `--case nao-existe` | saída 1, mensagem no stderr |
| fixtures reais | `list_cases()` e `load_case` dos 5 ids reais | 5 casos carregam (R15) |
